# 复盘（Retrospect）

对 `.agents/notes/` 与 `.agents/memory/` 做一轮经验治理：聚类增量、去存量归档、
扩展领域资料，并把稳定经验蒸馏为候选技能。产出全程留审计痕迹。

## 核心原则

- **置信度分层**：自己亲历的 notes/memory 是主素材（高置信）；其他 Agent 的记忆仅旁证（低置信，必须标注来源），单一他人经验不得直接采信，公共结论需多案例交叉验证
- **写隔离**：只修改归属自己的文件；他人文件与 `references/` 原文一律只读
- **处置留痕**：每条合并/归档/删除/提炼都要写一行理由，供后续审计
- **宁缺毋滥**：候选技能质量不达标宁可不出，垃圾技能比没有技能更消耗注意力

## 工作流

进入工作流前先 `TaskCreate` 建立任务清单（步骤 1-7 各一项，含每步产出），推进中用 `TaskUpdate` 标记完成状态，中断恢复时用 `TaskList`/`TaskGet` 读取进度，不凭回忆对齐工作点。

### 步骤 1：选模式

- **Light**：notes/memory 合计 < 20 条，或用户只要快速整理 → 只做增量聚类 + 快速去重，不跑质量门
- **Full**：素材明显冗余、用户要求深度复盘、或上次复盘后变化很大 → 三主线全跑 + 质量门全开

不确定时用 AskUser 列出 Light / Full 两种模式让用户选，附各自适用条件与耗时差异。

### 步骤 2：装载素材（按置信度分层）

1. `ls .agents/notes/ .agents/memory/`——文件名四元组（记录时间-agent名-分类-标题）就是索引，先按 Agent 名与分类分组
2. 优先读归属自己的条目（主素材）；他人条目按需抽读，仅作旁证
3. **技能进化履历**：扫描项目级技能目录的 `notes/`（如 `.agents/skills/*/notes/`）——履历中的问题/否决/修正记录是高价值踩坑素材，其根因分类（指令缺失/误导/歧义）直接用作聚类标签；履历只读，不修改不搬移
4. 跳过 `.archive/` 归档目录与已标记 deprecated 的内容
5. **定量验收（Full 模式）**：跑 `mindx metric compare --baseline <上次基线名>`（基线清单 `mindx metric baseline list`）——上轮修订的量表兑现情况是本轮判断的第一素材；劣化因子优先溯源，混杂事件（模型/daemon 变更）先于结论确认（量表是信号不是证明）

### 步骤 3：主线一——经验增量

1. 按 tags 分类与主题聚类相似条目
2. 交叉印证：同一结论在多条独立记录中反复出现 → 稳定可复现路径
3. **候选知识先判形态，再定出口**（三分流，逐条判定）：
   - 有明确触发场景、可写成决策路由（if/else + 动作）→ **技能候选**，走第 4 步
   - 讲得清但不必可执行（机制取舍、决策依据、领域复盘、架构权衡）→ **文章候选**，按本步第 5 条处理
   - 「让人查看、操作某物的需求」反复出现（≥2 次独立记录）→ **插件立项提议**，路由 plugin-planner 判定，对应 notes 保留待立项取证，不按冗余清理
4. 技能候选**必须自包含**（不依赖引用原始记忆，脱离原始上下文也能执行），一个技能只解决一类问题；发现存量技能缺陷时**只产出修订提议**（写入 `.agents/notes/`，按缺口词汇表分类），不直接修改技能文件——修正由 Agent 层路由至技能进化流程执行
5. 文章候选：**只判定不发布**——质量门三条（有一条明确论点、真实出处、说人话；不要求触发词/决策路由/体积上限，叙事体允许），过门即路由独立发布技能 `article-publish`（全局技能，管落位/校验/登录检查/推送全流程），本技能不内嵌任何发布步骤

### 步骤 4：主线二——去存量

只处理归属自己的推论素材，四类清理对象：

| 对象                  | 处置                                                  |
| --------------------- | ----------------------------------------------------- |
| notes 被技能/记忆吸收 | 直接删除（低置信素材价值耗尽即清）                    |
| memory 被技能吸收     | 移入 `.agents/memory/.archive/`（归档留审计，不删除） |
| 冗余重复条目          | 合并为一条主记录，主记录写明合并来源                  |
| 过时失效条目          | 归档，注明失效原因                                    |

条目多到难以取舍时，跑 `python3 {base_dir}/scripts/fapprox.py <agents_dir>` 取引用密度排序——P3 核心保留，P0/P1 进归档。每条处置在归档文件或合并记录中写一行理由。禁止触碰他人文件与 `references/` 原文；references 更新只追加不替换，废弃标记留给质量门。

### 步骤 5：主线三——扩展领域资料

1. 围绕本次复盘涉及的技术领域，用 WebSearch 检索权威资料（官方文档、论文、规范；普通网页与博客不入库）
2. 新增：`references/ref_XXX/`（自增编号，内含 `meta.json`：标题/来源URL/摘要/日期 + 原文）
3. 更新 `references/index.csv` 一行（编号/标题/来源/日期）
4. 引文连锁校验：跑 `python3 {base_dir}/scripts/refcheck.py <agents_dir>`，`broken` 数组即断裂引用——逐条评估引用该公理的 memory/skill 结论是否随公理更新而失效，修订引文或归档失效推论

### 步骤 6：质量门（候选技能必过）

评分方法与棘轮规则详见 `references/quality-gate.md`。要点：

1. **确定性自查**：跑 `mindx skill validate --path <skill_dir>`（唯一实现：skillstore.CheckQuality），覆盖 frontmatter 合规、软化词、体积、引文格式、链接可达——禁止心算，以 CLI 输出为准
2. **独立复评**：派 SubAgent 以纯读者视角给模糊维度（具体性、失败模式）评分，禁止自己写自己评
3. **棘轮**：新稿分数 > 旧版才落位；否则保留旧版，把被拒方案与理由记入技能的 `notes/` 进化履历
4. **单轮只改一个维度**；连续 2 轮无提升即停，不硬凑

### 步骤 7：落位与报告

1. 过门的候选技能写入 `<ProjectDir>/.agents/skills/<name>/`（单 Agent 验证 = 私有技能；需多 Agent 交叉验证后才能提升公共技能——本轮只标记"待交叉验证"）
2. **保存量表基线**：跑 `mindx metric baseline save <基线名>`（如 `round-<日期>`）——本轮修订后的快照，供下轮复盘 compare 验收
3. 向用户输出复盘报告：聚类了几组、归档/删除了几条（附理由摘要）、提炼或更新了哪些技能、拒绝了什么及原因；compare 可用时附上量表对比摘要

## 注意事项

- 归档用移动（mv 到 `.archive/`），notes 才允许删除——两者不可混淆
- 他人记忆里的结论写进候选技能前，必须先在自己的上下文中验证一次
- 复盘判断容易漂移：处置理由必须落盘，禁止只做不记
- references 连锁校验不能偷懒只查一条——引文断裂比记忆过期危害更大
- 一轮复盘不要试图清完所有历史存量，按本次新增素材为界，剩余留给下次

## 反模式

- 自己写候选技能自己打分就算过门（必须 SubAgent 独立复评）
- 为凑技能数量把流水账包装成"经验"
- 归档时顺手改写他人记忆或 references 原文
- 无理由的批量删除
- 候选技能正文依赖"参见某条 memory 文件"而不是自包含
