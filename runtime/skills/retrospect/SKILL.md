# 自省（Retrospect）

对 `.agents/notes/` 与 `.agents/memory/` 做一轮经验治理：先清会话债务，再把增量聚类成稳定结论落进记忆，去存量归档、扩展领域资料，最后把够格的经验蒸馏为技能、文章、规则或角色提议。产出全程留审计痕迹。

## 何时跑（阈值与计量都在此定义，规则文件只留指针）

减债与提纯是两件事，判据分开——不要拿时间把它们粘在一起：

| 动作 | 触发判据 | 说明 |
| --- | --- | --- |
| **减债**（跑 Light） | 任一会话窗口 tokens > 100,000 | 有债就还，与时间、缓存都无关；债务每天都在被重拾 |
| **提纯**（跑 Full） | 本 Agent 在 notes 下的条数达 20 条 | 有 notes 产生时判一次（`scan.py count`）；自省消化后条数回落，自然进入下一轮 |
| 用户显式要求 | 无 | 按用户指定的范围跑，永不被其他条件否决 |

- **触发挂在事件上，不挂在轮询上**：提纯不用定时、不用巡检——随手记写盘那一刻顺手数一次条数即得结论，平时零开销
- **两条判据各管各的**：有债只减债、不必等条数；条数到了只提纯、不必有债。两者同时命中才跑完整 Full

- **两档对应两种范围**：Light 只减债（压超阈会话），不聚类不动素材；Full 减债 + 聚类提纯 + 去存量
- **单轮压量上限 3 个**：按超出量降序取前 3，其余下轮——一次压十个会话就是十次全价重读，账单会失控
- 阈值只在本节维护。项目公共规则文件里写一行指针即可，不要在规则文件里重复数值——规则文件属系统提示前缀，改一个字就让全部在飞会话的缓存失效一次
- **判定跑脚本，不手数**：条数判 `scan.py count --agent <本 Agent>`（写 notes 后调，毫秒级）；债务判 `scan.py debt`（定时任务或自省开始时调）；需要全景时跑 `scan.py status`（会扫全部会话，约十秒，不用于日常巡检）
- **不要用 notes 绝对条数当主判据**：实测存量常是某天批量写进来的，绝对值高只说明那天写得多，不说明该治理了
- **不要在会话里反复查条数**：条数判定是 `scan.py count` 的活，只在写完 notes 后调一次；会话中为确认阈值反复 `ls | wc -l` 或 grep 是每轮白付一次工具往返
- **定时检测只管减债**：债务不会自己消失，也没人会在写 notes 时顺带发现它——定时任务只做债务扫描（`scan.py debt`），提纯不设定时。定时挂工作区级，不挂 Agent 级：自省管的是整个工作区的会话与素材，一个工作区建一个即可；按 Agent 各建一个 cron，会随 Agent 数量线性放大（十个 Agent 就是十份重复自省）

## 核心原则

- **先减债再提纯**：会话窗口未压缩时先压再聚类，否则后续每一步都在为过期摘要付全价
- **置信度分层**：自己亲历的 notes/memory 是主素材（高置信）；其他 Agent 的记忆仅旁证（低置信，必须标注来源），单一他人经验不得直接采信，公共结论需多案例交叉验证
- **写隔离**：只修改归属自己的文件；他人文件与 `references/` 原文一律只读
- **处置留痕**：每条合并/归档/删除/提炼都要写一行理由，供后续审计
- **宁缺毋滥**：候选技能质量不达标宁可不出，垃圾技能比没有技能更消耗注意力

## 工作流

进入工作流前先 `TaskCreate` 建立任务清单（步骤 1-7 各一项，含每步产出），推进中用 `TaskUpdate` 标记完成状态，中断恢复时用 `TaskList`/`TaskGet` 读取进度，不凭回忆对齐工作点。

**清点类动作一律跑脚本，不凭现场数**：会话占用、素材条数、分类分布、命名合规都是确定性计算，心算既慢又不准——`python3 {base_dir}/scripts/scan.py` 一条命令给全（子命令见 `--help`）。判断类（聚类、交叉印证、分流）才留给推理。

### 步骤 1：选模式

- **Light**：未达「何时跑」任一阈值，或用户只要快速整理 → 只做增量聚类 + 快速去重，不跑质量门
- **Full**：素材明显冗余、用户要求深度复盘、或上次复盘后变化很大 → 三主线全跑 + 质量门全开

不确定时用 AskUser 列出 Light / Full 两种模式让用户选，附各自适用条件与耗时差异。`scan.py status` 的 `mode_suggest` 可作默认参考，不替代用户决定。

复盘对象不明时（用户只说"复盘一下"）：先确认是当前项目还是别的项目。本技能只治理当前项目目录下的素材，别的项目要切到那个项目的上下文再跑——不跨目录抓素材，也不凭印象拼别人的账。

范围也可以收窄：用户只要某一路（只清记忆 / 只提炼技能 / 只压上下文）时按那一路跑，不必强行三主线全开。

### 步骤 2：盘债与装载素材（按置信度分层）

**2.1 盘会话债**：跑 `scan.py debt`——脚本逐会话取上下文占用并筛出超阈的，一次输出会话 id / 角色 / 标题 / 窗口 tokens / 已压缩游标。只读、零成本，先做。

**2.2 压超阈会话**：自动执行，不询问用户——先预检再压缩（mindx 环境：`mindx session compact --session-id <id> --dry-run` 预检，`--yes` 执行）。

- 压缩是**游标前移 + 摘要**：旧消息不删、会话文件保留完整历史、摘要落 `.agents/memory/`。数据不丢、摘要留存，属常规维护动作，不需要事前确认——压完再装载素材，否则本轮聚类用的是旧摘要
- **只跳过「正在用」的会话**：最后活动在 30 分钟内的，可能用户正手头在推进，跳过并写进报告留待下轮；其余按债务大小照压。这个 30 分钟只用来判断「是否在用」，不是用来猜缓存——供应商的缓存有效期不公开、各家从数小时到数天不等且随负载变化，任何拿它做判据的推算都是猜
- **不要按「缓存还热所以先别压」迟疑**：缓存期本就极短，债一旦消是永久消；压的唯一代价是所属会话在缓存期内被回用时丢原始细节（摘要仍在 memory），损失有上限，迟疑的代价却是每轮都在付全价
- 预检必须跑（免费）：空窗口、未达阈值会被拒绝，属正常返回，跳过即可
- 压缩真实消耗一次模型调用（约等于把整个窗口重读一遍）：一轮只压超阈的，不顺手压没超的
- 用户明确表示会话可以丢弃时，直接删会话比压缩更省，不必强行走压缩
- **摘要只算线索，不算结论**：摘要落进 `.agents/memory/`，但它是一段会话的压缩，不是跨条目的提炼。聚类时只能当线索，不得直接当结论依据，也不得凭摘要直接升技能或改公共规则——要么回溯原文，要么另有独立记录交叉印证

**2.3 装载素材**：

1. 跑 `scan.py stock` 拿全景：两处各多少条、标准分类怎么分布、哪些文件名分类不在词表、memory 里「提炼条目」与「压缩摘要」各占多少；再 `ls` 定位具体文件。memory 两类必须分开看——摘要只算线索（见 2.2 末条），提炼条目才是资产
2. 按 Agent 名与分类分组优先读归属自己的条目（主素材）；他人条目按需抽读，仅作旁证
3. **技能进化履历**：扫描项目级技能目录的 `notes/`（如 `.agents/skills/*/notes/`）——履历中的问题/否决/修正记录是高价值踩坑素材，其根因分类（指令缺失/误导/歧义）直接用作聚类标签；履历只读，不修改不搬移
4. 跳过 `.archive/` 归档目录与已标记 deprecated 的内容
5. **定量验收（Full 模式）**：跑 `mindx metric compare --baseline <上次基线名>`（基线清单 `mindx metric baseline list`）——上轮修订的量表兑现情况是本轮判断的第一素材；劣化因子优先溯源，混杂事件（模型/daemon 变更）先于结论确认（量表是信号不是证明）

五个来源全部为空时如实告知并终止，不硬凑结论。

### 步骤 3：主线一——经验增量

1. 按 tags 分类与主题聚类相似条目
2. 交叉印证：同一结论在多条独立记录中反复出现 → 稳定可复现路径
3. **先落记忆**——聚类出的稳定结论先写进 `.agents/memory/`，这是提纯的第一站：
   - 命名 `<YYYY-MM-DD>-<agent_name>-<分类>-<标题>.md`，分类取标准词表（决策 / 踩坑 / 经验 / 事实 / 待办 / 偏好，可定位缺口时用六类 `缺口-*`）
   - 正文写「结论 + 识别信号 + 触发动作」，要求换个人、换个会话独立读懂；与 notes 的宽松猜想不同，记忆条目是已确认的
   - **只落已交叉印证的**：跨会话重复 ≥2 次或有多条独立记录支撑；单次偶发、未印证的一律留在 notes 等下一轮，不占记忆层
   - 落了记忆不等于定型：本轮仍可继续判出口，升级成功的按步骤 4 把对应记忆归档
4. **候选知识先判形态，再定出口**（五分流，逐条判定）：
   - 有明确触发场景、可写成决策路由（if/else + 动作）→ **技能候选**，走步骤 6 质量门与步骤 7 落位
   - 讲得清但不必可执行（机制取舍、决策依据、领域复盘、架构权衡）→ **文章候选**，按本步第 6 条处理
   - 「让人查看、操作某物的需求」反复出现（≥2 次独立记录）→ **插件立项提议**，路由 plugin-planner 判定，对应 notes 保留待立项取证，不按冗余清理
   - 跨会话重复 ≥2 次、且能归入「该做的 / 不该做的 / 踩坑经验」三类的行为约束 → **规则修订提议（项目公共规则）**：写成新增哪条、修改哪条、依据是哪几条素材，逐条问用户，授权后按运行环境的规则文件写入流程落盘；本技能不直接改写公共规则文件，保证格式与既有结构一致
   - 角色级缺口 → **招募提议**：三条件同时满足才提——技能承载不了（缺的是职责边界与行为门控，不是操作指令）/ 跨任务反复（≥2 次独立任务）/ 边界可辨（与现有角色并排可区分）；授权后按运行环境的建岗流程执行，本技能不直接创建角色
5. 技能候选**必须自包含**（不依赖引用原始记忆，脱离原始上下文也能执行），一个技能只解决一类问题；发现存量技能缺陷时**只产出修订提议**（写入 `.agents/notes/`，按缺口词汇表分类），不直接修改技能文件——修正由 Agent 层路由至技能进化流程执行
6. 文章候选：**只判定不发布**——成稿前先做二次学习：用 `article-publish` 读侧检索社区三大文章库同主题存量文章（官方→组织→个人），吸收已有论点，新文章注明与存量的关系（补充/深化/商榷），不平行重写；质量门三条（有一条明确论点、真实出处、说人话；不要求触发词/决策路由/体积上限，叙事体允许），过门即路由独立发布技能 `article-publish`（全局技能，管落位/校验/登录检查/推送全流程），本技能不内嵌任何发布步骤

### 步骤 4：主线二——去存量

只处理归属自己的推论素材，五类清理对象：

| 对象                  | 处置                                                  |
| --------------------- | ----------------------------------------------------- |
| notes 被技能/记忆吸收 | 直接删除（低置信素材价值耗尽即清）                    |
| memory 被技能吸收     | 移入 `.agents/memory/.archive/`（归档留审计，不删除） |
| memory 被文章吸收     | 移入 `.agents/memory/.archive/`（同技能处置；文章出口即记忆的共享通道） |
| 冗余重复条目          | 合并为一条主记录，主记录写明合并来源                  |
| 过时失效条目          | 归档，注明失效原因                                    |

条目多到难以取舍时，跑 `python3 {base_dir}/scripts/fapprox.py <agents_dir>` 取引用密度排序——P3 核心保留，P0/P1 进归档。每条处置在归档文件或合并记录中写一行理由。禁止触碰他人文件与 `references/` 原文；references 更新只追加不替换，废弃标记留给质量门。

### 步骤 5：主线三——扩展领域资料

1. 外搜前先查库：检查 `references/` 与社区三大文章库（`article-publish` 读侧）是否已覆盖该领域，命中即复用，不重复入库；未命中再用 WebSearch 检索权威资料（官方文档、论文、规范；普通网页与博客不入库）
2. 新增：`references/ref_XXX/`（自增编号，内含 `meta.json`：标题/来源URL/摘要/日期 + 原文）
3. 更新 `references/index.csv` 一行（编号/标题/来源/日期）
4. 引文连锁校验：跑 `python3 {base_dir}/scripts/refcheck.py <agents_dir>`，`broken` 数组即断裂引用——逐条评估引用该公理的 memory/skill 结论是否随公理更新而失效，修订引文或归档失效推论

### 步骤 6：质量门（候选技能必过）

评分方法与棘轮规则详见 `references/quality-gate.md`。要点：

1. **确定性自查**：跑 `mindx skill validate --path <skill_dir>`（唯一实现：skillstore.CheckQuality），覆盖 frontmatter 合规、软化词、体积、引文格式、链接可达——禁止心算，以 CLI 输出为准
2. **独立复评**：派 SubAgent 以纯读者视角给模糊维度（具体性、失败模式）评分，禁止自己写自己评
3. **棘轮**：新稿分数 > 旧版才落位；否则保留旧版，把被拒方案与理由记入技能的 `notes/` 进化履历
4. **单轮只改一个维度**；连续 2 轮无提升即停，不硬凑

### 步骤 7：落位与报告

1. 过门的候选技能写入 `<ProjectDir>/.agents/skills/<name>/`（单 Agent 验证 = 私有技能；需多 Agent 交叉验证后才能提升公共技能——本轮只标记"待交叉验证"）
2. **保存量表基线**：跑 `mindx metric baseline save <基线名>`（如 `round-<日期>`）——本轮修订后的快照，供下轮复盘 compare 验收
3. 向用户输出复盘报告：会话债务（压缩了哪几个会话、各自释放多少、是否不可逆）、新落了几条记忆（列标题）、聚类了几组、归档/删除了几条（附理由摘要）、提炼或更新了哪些技能与规则、拒绝了什么及原因；compare 可用时附上量表对比摘要

## 注意事项

- 归档用移动（mv 到 `.archive/`），notes 才允许删除——两者不可混淆
- 他人记忆里的结论写进候选技能前，必须先在自己的上下文中验证一次
- 复盘判断容易漂移：处置理由必须落盘，禁止只做不记
- references 连锁校验不能偷懒只查一条——引文断裂比记忆过期危害更大
- 一轮复盘不要试图清完所有历史存量，按本次新增素材为界，剩余留给下次

## 失败模式（现象 → 原因 → 动作）

- 现象：聚类结论全建在旧账上。原因：跳过盘债直接装载素材。
  动作：回步骤 2.1 先盘会话债，压完再装载。
- 现象：会话被压坏，窗口内容找不回。原因：没做预检就压缩，游标前移不可逆。
  动作：先 `--dry-run` 看占用与跳过条件，再报要动哪几个会话。
- 现象：把摘要直接当知识入库。原因：把压缩当成整理。
  动作：压缩只减债，摘要仍是低置信素材，须走步骤 3 聚类。
- 现象：候选技能自评很好看，落位后没人用。原因：自己写自己评。
  动作：派 SubAgent 独立复评，棘轮不过不落位。
- 现象：技能数量涨了质量没涨。原因：为凑数把流水账包装成经验。
  动作：按三条形态门判定，不过不出。
- 现象：他人记忆被改写、引文断裂。原因：归档时顺手改原文。
  动作：只移动不改写，references 只追加不替换。
- 现象：候选技能写「参见某条 memory」，换个会话就跑不动。原因：没做到自包含。
  动作：把结论写进技能正文，memory 只作来源注记。
