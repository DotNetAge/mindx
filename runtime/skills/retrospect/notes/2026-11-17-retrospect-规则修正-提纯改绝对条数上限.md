## 2026-11-17 提纯判定改「本 Agent notes 达 20 条上限」（workbuddy）

- 问题：指令冲突——上一版把提纯做成「与基线比对的增量 ≥10 条」，并把实现细节（脚本名、基线文件、禁止查目录）写进了常驻系统提示。两处都不对：①增量模型要维护基线文件、要读要写、还要处理「无基线」分支，而绝对条数上限配合「自省消化后条数回落」本身就是自限循环，不需要任何基线；②把实现细节写进 AGENTS 是每轮永续付费的 token，规则只该说清「数谁的、多少条、到了做什么」。
- 否决：保留增量模型并继续用状态文件——自省本身会消化并删除已吸收的 notes，条数自动回落，基线是多余的一层；在通用准则里保留脚本调用细节——那是技能内部实现，通用准则只需给出触发条件与动作。
- 修正：公共准则随手记条款改为一句「有 notes 产生时检查本 Agent 在该目录的条数，达到 20 条即加载 `retrospect` 自省——自省消化后条数自然回落，形成循环」，删除原来关于基线比对与禁止查目录的整段；自省路由条目删去判定说明、只留路由；项目规则同步为「触发条件见随手记条款」；技能「何时跑」表把提纯判据改为「本 Agent 在 notes 下 20 条」，删除「距上次 Full ≥30 天」这条时间兜底；`scan.py` 删除 `mark` 与整套 `.review-state.json` 基线机制（连同 `done`），新增 `count --agent` 只数本 Agent 条数并判上限。version 2.4.1 → 2.5.0。
- 验证：`mindx skill validate` 全绿（166 行、soft_rules 0）；`count --agent glm` 实测 19 条未达上限、`count` 按全部计 39 条并触发；`status` 输出两理由（11 会话超阈 + 本 Agent 39 条 ≥ 20）；`grep "scan.py mark\|scan.py done"` 零命中；语法 `ast.parse` 通过。
