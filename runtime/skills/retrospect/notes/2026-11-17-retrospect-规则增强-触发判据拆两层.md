## 2026-11-17 触发判据拆两层：减债有债就还、提纯看增量（workbuddy）

- 问题：指令冲突——原触发表把「减债」与「提纯」混在同一个开关下（债务 / 距上次 7 天且新增 10 条 / notes 30 条兜底），导致只能用时间当粘合剂：有债也要等攒够增量才压，债务白挂一周；而无债时又可能被时间拉起来空跑。时间是四类判据里最弱的一个，却被放在了主判据位置。
- 否决：继续用「距上次 N 天」作减债条件——缓存有效期不可查（供应商各异且可变），任何以时间为轴的减债节奏都是猜；把提纯也改成「有债就做」——提纯需要判断成本，零星一两条素材就聚类等于把成本摊在噪音上。
- 修正：「何时跑」改为两层判据表——减债（Light）判据为「任一会话 >100k」，与时间和缓存无关；提纯（Full）判据为「notes 增量 ≥10 条」，兜底为「距上次 Full ≥30 天」，首次运行无快照时以存量 ≥30 条兜底；新增单轮压量上限 3 个（按超出量降序），避免一次压十个会话的账单失控；`scan.py` 增 `over_by` / `over_total` / `over_count`，`status` 输出 `mode_suggest`（Light 只减债 / Full / Full 只提纯 / 无需）与 `compact_batch`（本轮该压哪几个），参数改为 `--min-notes`、`--full-min-days`、`--max-compact`；定时任务 prompt 按 mode 分派执行范围。version 2.3.2 → 2.4.0。
- 验证：`mindx skill validate` 全绿（165 行、soft_rules 0）；场景一（无快照）实测输出 Full，理由含「首次运行（无快照），存量 39 条 ≥ 30」；场景二（有快照、零增量）输出 Light（只减债），不再被时间拉起；债务总量实测 688,356 tokens、本轮只取前 3 个。
