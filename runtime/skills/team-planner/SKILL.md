# 团队规划师

把"接手一个没有团队的大项目"变成"一支编制合理、各司其责的智能体团队"。

## 何时使用

- 用户接手或打开一个大型项目，说"给这个项目配个团队"、"帮我组建一个团队负责这个项目"
- 项目已有会话与代码，但尚无团队实体负责它

**不使用**：只想创建单个 Agent（走 agent-creator 的单 Agent 工作流）；项目已有团队且运转正常（那是编制修订，走 agent-creator 的审查流程）。

## 前提检查

1. 确认会话工作目录即目标项目（考古与蓝图都落在这里）
2. `mindx team list --json` 与 `mindx agent list --all --json` —— 项目可能已有部分编制：
   - 已有完整团队 → 告知用户并停止
   - 已有零散 Agent → 只为缺口岗位做增量规划，存量 Agent 纳入编制评估而非重复创建

## 工作流

### 步骤 1：项目考古（派 SubAgent 执行）

考古会读大量文件，**必须派 SubAgent 执行**（检索型子任务只返结论），主上下文只聚合判断。考古维度：

- 技术栈与框架（语言、构建工具、依赖清单）
- 模块划分与目录结构（顶层模块、职责边界）
- git 热区（近 30 天改动集中的模块——活跃度即职责权重）
- 外部接口面（API、数据库、部署方式）
- 现有文档与约定（README、AGENTS.md、规范文件）

考古报告落盘为蓝图工件的「项目现状」节。禁止全量读源码——每个维度抽样即可，结论比细节重要。

### 步骤 2：领域拆解（MECE 检验）

把考古结论拆解为互斥且完备的领域清单：

- **互斥**：任一典型任务有且只有一个明确归属领域——拿一个真实任务对照两个相邻领域，若都说"归我"，重新划界
- **覆盖**：领域并集覆盖项目的主要职责面（以 git 热区与目录结构为准，不为冷代码设岗）

### 步骤 3：产出团队蓝图工件

蓝图落盘项目目录下的 `.agents/plans/team-blueprint.md`，结构：

```markdown
# 团队蓝图：<项目名>

## 项目现状（考古摘要）
[技术栈 / 模块 / 热区 / 接口面，各 1-3 句]

## 编制清单
| 岗位 | 职责概览（负责什么/产出什么/什么时候用） | 共享技能 | 独享技能 | 来源（复用/新建） |
| ---- | ---------------------------------------- | -------- | -------- | ----------------- |

## 负责人选定
[谁任 leader 及理由——通常选职责横跨多领域或主导集成度的岗位]

## 团队职责（Profile 要点）
[成员协作规则、验收口径、汇报链路]
```

岗位编写规范（概览三问、共享/独享技能判据）按 agent-creator 技能的「编写方法论」执行。共享技能是全团队一致性的方法论（如代码审查、测试生成、根因调试），独享技能是岗位专有做法（如特定框架开发）——只装配该岗位需要的，每个技能都消耗上下文。

### 步骤 4：老板确认（建制前必过）

把蓝图呈现给用户：岗位清单、每个岗位的一句话概览、来源标记（复用/新建）、负责人选定。**用户确认前不创建任何实体**；用户要求调整则修订蓝图重新确认。

### 步骤 5：复用检索与建制

按蓝图逐岗位执行，**能复用绝不新建**：

1. `mindx market list --kind agent --filter "<领域关键词>"` 检索现成 Agent 包——命中即 `mindx market install agent <name>`
2. 无现成的，按 agent-creator 技能的工作流从零创建（考古结论此时就是它的领域上下文来源）
3. 全部岗位就位后 `mindx team add <team> --leader <lead> --member ...`，蓝图「团队职责」节写入 Team Profile（`mindx team update <team> --profile`）
4. `mindx team hire <team>`

### 步骤 6：交接

向用户汇报：编制清单（谁负责什么）、启动方式（选团队 = 以负责人身份发起会话）、蓝图文件位置。项目后续的日常运转不再需要本技能。

## 注意事项

- **考古抽样即可，禁止全量读码**——考古的产出是领域判断，不是代码清单；细节是工程师接手后的事
- **蓝图是确认门也是审计痕迹**——未经用户确认的蓝图不得落为实体；确认后的修改要更新蓝图文件
- **共享技能宁少勿多**——每个装配的技能都进入该 Agent 的每次会话上下文；判定标准是"没有它会做错"，不是"有了更好"
- **leader 的 SOUL 必须写协调职责**（任务拆解、派发、跟踪、汇报）——团队会话就是与 leader 对话，缺协调职责的 leader 会自己埋头干活
- **存量 Agent 纳入编制评估**——项目已有零散 Agent 时，先评估其概览是否可并入编制，禁止无视存量直接新建

## 反模式

- **跳过考古直接建团队** —— 不了解项目就设岗，岗位与实际职责面必然错位
- **一个岗位包整个项目** —— 与"能单不多"矛盾：真只需一个 Agent 时不要组建团队
- **蓝图未确认就建制** —— 批量创建实体必须先过确认门
- **全岗位配同一堆技能** —— 共享与独享不分，上下文被无关技能撑爆
- **建完就散** —— 不写 Team Profile、不做交接汇报，用户不知道团队怎么用

## 重要说明

- **本技能不直接创建 Agent** —— 建制动作一律按 agent-creator 技能的工作流执行，本技能负责"建什么"的决策与"建成什么样"的蓝图。
- **蓝图工件是唯一交接物** —— 编制决策的全部依据（考古、拆解、确认）都在 `.agents/plans/team-blueprint.md` 里可追溯。
