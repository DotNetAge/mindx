# 架构决策（Architecture Decision）

本 reference 是通用最小架构决策模板，覆盖任意方案取舍场景（架构方案/模块拆分/实现取舍）。与 `tech-selection`（技术栈级选型）和 `spec-driven-development`（Spec 级）互补，不重复定义决策流程。

## 输入要求

1. **决策点**（必填）：需要做出取舍的问题，一句话表述
2. **候选方案**（必填）：至少 2 个真实可选方案（禁止只列 1 个凑数）
3. **约束条件**（可选）：性能 / SLA / 团队能力 / 兼容性 / 成本等硬约束
4. **上下文**（可选）：模块边界、调用方、数据规模、现状代码

## 执行流程

### 第一步：识别决策点

- 明确"要决策什么"，把多个决策点拆开，逐个走本流程
- 判定是否命中复杂度门槛（见下）

### 第二步：列出候选方案

- 至少 2 个真实方案；方案间必须是**不同策略**，而非同策略参数微调
- 单一合理实现（低复杂度改动）→ 可豁免，标注"单一合理实现，跳过反选论证"

### 第三步：逐方案 trade-off

对每个候选方案：

| 维度 | 内容 |
| - | - |
| 优势 | 核心卖点 / 在约束下的匹配度 |
| 劣势 | 代价 / 风险 / 局限 |
| 适用场景 | 什么情况下它是最优 |
| 不适用场景 | 明确排除的情况 |

### 第三步点五：决策质量自检（取舍前必答）

进入选择前先回答三个问题——**答不出就不要进入第四步**：

1. **这个决策可逆到什么程度？** 分四级，按级加码：

   | 级别 | 判定 | 必须追加的动作 |
   | - | - | - |
   | 可逆 | 改配置 / 改代码即可回退，无残留 | 无 |
   | 可回退 | 有迁移脚本或版本化，回退需时间 | 写出回退步骤与耗时 |
   | 难回退 | 数据已变更 / 外部系统已感知 / 有兼容性承诺 | **回退方案先于实现产出** |
   | 不可逆 | 删数据 / 改公开契约 / 涉及资金或品牌 | **用户确认闸门**（对齐 `execution-safety`）+ 灰度 + 预演 |

2. **哪些是事实，哪些是假设？** 逐条拆开列：

   - **事实**：有实测数据 / 官方文档 / 已跑通先例支撑（**须注明来源**）。
   - **假设**：凭经验推断或"应该会"的部分——**每条假设必须写出「如何验证」**，或写明「暂不验证的代价」。
   - 假设条数多于事实 → 信息不足，走问题 3。

3. **现在该决策，还是该先做实验？** 命中任一信号 → 先 Spike/POC，**不拍板**：

   - 候选方案的**性能 / 成本差异无法静态判断**（须实测才能比）
   - 依赖的**外部系统行为未知**（限流、一致性、超时、配额）
   - **团队无该技术 / 该场景的实操经验**
   - 两方案 trade-off 接近，而**选错代价高**

### 第四步：选择与反选论证

- **选择**：首选方案 + 选型理由（基于需求匹配度与约束）
- **反选论证（必填）**：逐条说明「为何不选备选方案」——备选方案的 trade-off 为何在本项目约束下不可接受。只给"首选+理由"视为不完整；反选论证须说明「为何不选 B」，而非仅罗列「为何选 A」（对齐 `tech-selection.md` 反选论证）
- **接受的代价**：首选方案已知的技术债与限制

### 第五步：撤销条件与验证

- **撤销条件**：什么情况下重新评估此决策（数据规模/团队/技术环境变化的触发点）
- **验证**：选择落地后，须按方案执行验证（benchmark / EXPLAIN / 边界用例 / 实测），与 `performance-benchmark.md`、`mysql-database.md` 的验证闭环衔接

### 第五步点五：不做的判断（何时该拒绝引入）

引入任何**新抽象 / 新依赖 / 新技术 / 新模式**前，先回答一句：

> **它解决的是哪个「当前已发生」的问题？**

答不出具体问题 → **不做**。（与 `execution-safety.md`「防 AI 通病五戒」（戒过度工程化 / YAGNI）同源：那里是执行期门禁勾选，此处是引入前的回答判据。）

**必须拒绝的引入信号**（命中任一 → 不做，并记为"暂不引入 + 触发条件"）：

| 信号 | 典型说法 | 动作 |
| - | - | - |
| 未来时 | "以后可能会…""将来要扩展" | 不做；记为待触发项，写明**什么条件出现时才引入** |
| 从众 | "业界都这么做""大厂方案" | 不做；要求给出**本项目**的收益证据 |
| 纯优雅 | "更优雅 / 更现代"，但无当前收益 | 不做；除非同时降低当前成本或风险 |
| 为技术而技术 | 用它解决的是**已有技术已解决**的问题 | 不做 |
| 隐藏复杂度 | 引入后总体复杂度上升，收益只是"少写几行" | 不做 |

**判据**：新增依赖 / 抽象带来的**认知与维护成本是长期持续的**，收益必须**当期可见**——否则它是负债而非资产。

### 第五步点六：决策回填（决策后复盘）

决策不是留痕即结束——**假设命中也要回填**，否则无从判断决策质量：

| 字段 | 内容 |
| - | - |
| 决策 | 引用第三步点五记录的首选方案 |
| 当时的假设 | 逐条抄自「事实 vs 假设」，不得事后改写 |
| 实际结果 | 观察到的结果（指标 / 故障 / 反馈） |
| 假设判定 | 每条假设标：命中 / 落空 / 未验证 |
| 落空后的修正动作 | 改变决策 / 增加监控 / 转技术债（引 `technical-strategy.md` 台账）/ 无 |
| 回填时间 | 撤销条件触发时，或满一个迭代周期 |

- **触发时机**（任一）：撤销条件被触发 / 决策满一个迭代周期 / 相关指标异常。
- **判据**：假设落空但无人回填 → **决策记录视为未闭环**（收口于 SELF-AUDIT「架构自检」行）。
- 与台账联动：落空假设若产生持续成本，转为 `technical-strategy.md` 的技术债条目（带利息）。

### 第六步：留痕沉淀

- 决策记录写入「决策记录」节（见下）
- 经 `project-memory-management` 的 Decision Record 模式沉淀到项目记忆，撤销条件随记录保存

## 复杂度门槛

| 条件 | 动作 |
| - | - |
| 多候选方案 / 跨模块影响 / 高影响决策 | 强制走完整流程并输出决策记录 |
| 单一合理实现 / 低复杂度改动（单文件小功能） | 豁免，输出说明"单一合理实现，无候选方案" |

## 输出格式

```
## 架构决策记录（Architecture Decision Record）

- **决策点**：[一句话]
- **候选方案**：A / B / [C]
- **选择**：[方案]
- **选择理由**：[基于需求与约束]
- **反选论证**：[为何不选 B/C，逐条 trade-off]
- **接受的代价**：[已知技术债 / 限制]
- **撤销条件**：[什么情况下重新评估]
- **验证**：[验证方式 + 预期结果]
```

## 决策记录模板（沉淀到项目记忆用）

```
## Decision Record: [决策名称]

**日期**: [YYYY-MM-DD]
**问题**: [要解决的技术问题]

### 选项分析
| 选项 | 优势 | 劣势 | 适用场景 |
| - | - | - | - |
| [选项A] | ... | ... | ... |
| [选项B] | ... | ... | ... |

### 决策
**选择**: [最终选项]
**理由**: [核心原因]
**Trade-offs**: [接受的代价]

### 撤销条件
[什么情况下重新评估]
```

## 失败回退机制

| 步骤 | 失败条件 | 回退目标 | 最大重试 | 不可恢复时升级路径 |
| - | - | - | - | - |
| 第二步：列候选方案 | 只能想到 1 个方案 | 标注"单一合理实现"，豁免本流程 | 0 | 直接进入实现，交付时说明无候选 |
| 第四步：反选论证 | 备选与首选 trade-off 接近难以取舍 | 输出决策矩阵，标注推荐项与依据 | 2 | 建议 POC 验证后由用户拍板 |
| 第五步：验证 | 验证手段不可用（无环境/无工具） | 标注"验证受限" + 最小可执行验证路径 | 1 | 输出限制说明，交用户决定是否继续 |

## 质量标准

- 决策必须基于实际约束（需求/规模/团队/兼容性），不能泛泛而谈
- 反选论证必须具体：说清"为什么不是 B"，而非"B 也不错"
- 撤销条件必须可操作（可触发、可判定），不能"如有需要再评估"
- 高影响决策未留痕即交付 → 按「无验证证据=未完成」红线处置
