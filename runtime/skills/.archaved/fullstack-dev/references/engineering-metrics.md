# 效能与成本度量（engineering-metrics）

> 工程纪律层专项：把「效率高不高 / 债有多重 / 这套系统贵不贵 / 值不值得做」变成可采集、可判定的数字。不替代 `incident-review`（可靠性 SLO）与 `performance-benchmark`（单点性能基线）。

**触发**：研发效能、DORA、交付周期、部署频率、变更失败率、MTTR、技术债量化、容量、成本、ROI、投入产出、回收期。

## 适用边界

- **加载**：需要量化交付效率、技术债利息、容量水位、单位成本或方案 ROI。
- **跳过**：单次性能调优（走 `performance-benchmark`）；可靠性目标与错误预算（走 `incident-review`）；工时估算与排期（本技能边界外）。
- **范围声明**：本 reference 提供**度量口径与判据**；组织级考核制度、预算审批不在范围。

**铁律**：指标用于定位系统瓶颈，**禁止用于个人绩效评价**（见第二步反模式）。

## 执行流程

### 第一步：DORA 四指标口径

| 指标 | 定义 | 分母 | 采集点 |
| - | - | - | - |
| 交付周期（Lead Time） | 从代码提交到生产可用的时长 | 每次发布 | 提交时间戳 → 部署完成时间戳 |
| 部署频率（Deploy Freq） | 单位时间的生产部署次数 | 按周或按日 | 部署记录 |
| 变更失败率（CFR） | 导致回滚 / 热修 / 事故的部署占比 | **总部署数** | 部署记录关联事故记录 |
| MTTR | 故障从发现到恢复的平均时长 | **故障次数** | 告警时间 → 恢复时间 |

规则：

1. 每个指标必须写清**分母**（哪些请求 / 部署 / 故障计入）；口径不清不给数字。
2. 采集不可得 → **先补埋点**，禁止用估算值冒充实测（对齐 `performance-benchmark.md`「质量标准」：无基线不得声称提升）。
3. 四个指标必须**同时**给出；只给一个（尤其只给部署频率）视为选择性汇报。

### 第二步：度量反模式（先排除，再解释数字）

| 反模式 | 表现 | 后果 |
| - | - | - |
| 考核个人 | 用 DORA 评个人绩效 | 古德哈特定律：指标被操纵（拆小提交刷频率、压制故障上报） |
| 单指标优化 | 只提部署频率 | 变更失败率同步上升，净效果为负 |
| 口径漂移 | 每期统计口径不同 | 趋势不可比，结论无效 |
| 无基线 | 直接说「效率明显提升」 | 结论无效 |

- 输出中须**显式声明**「本组指标不用于个人评价」，并将该声明作为交付物的一部分。

### 第三步：技术债量化（利息法）

- 单条债务利息 = 每月额外成本（人力工时 / 机器成本 / 故障损失，任选**可量化**口径并标注）。
- 台账总利息 = Σ 单条利息，供 `technical-strategy.md` 排序与「破例」判断使用。
- 利息口径须与 `technical-strategy.md` 台账字段一致，**禁止两套算法并存**。

### 第四步：容量与成本

| 项 | 口径 | 门禁（触发动作） |
| - | - | - |
| 容量水位 | 当前峰值 / 设计容量 | > 70% → 触发扩容评估 |
| 单位请求成本 | 月成本 / 月请求量 | 环比上升 > 20% → 触发排查 |
| 成本回归 | 新版本单位成本 vs 上线前 | 上升即视为回归，须书面说明理由 |

- 容量数据缺失 → 输出「需补采集清单」，不臆造水位数字。
- 成本口径须注明是否含网络 / 存储 / 第三方调用（口径不完备时标注而不用近似值）。

### 第五步：ROI 判据

- 年化收益 = 影响人数 × 频次 × 单次收益（或单次损失）。
- 回收期 = 总成本 / 年化收益；**总成本必须含长期维护成本**（一次性开发成本不计入维护）。
- 判据：回收期 > 12 个月 → 须给出战略理由；给不出则改走更轻解法（对齐 `spec-driven-development.md`「更轻的解法」）。
- 禁止：只算收益不算维护成本；把「提升体验」等不可量化项计入收益。

### 第六步：与既有指标的边界（防重复计算）

| 已有机制 | 负责范围 | 本 reference 是否重复 |
| - | - | - |
| SLO / 错误预算 / 燃烧率（`incident-review.md`） | 可靠性 | 不重复 |
| 耗时 / 内存 / QPS 基线（`performance-benchmark.md`） | 单点性能 | 不重复 |
| 本 reference | 交付效率 + 技术债 + 容量成本 + ROI | — |

- 引用其余两处指标时**只引用不重算**，避免同一数字出现两个口径。

## 输出格式

```
## 效能指标（DORA）
| 指标 | 数值 | 分母口径 | 采集点 | 数据来源（实测/待补） |

## 度量声明
本组指标用于定位系统瓶颈，不用于个人绩效评价。

## 技术债利息
| 债务 ID | 每月成本 | 口径 | 总利息 |

## 容量与成本
| 项 | 当前值 | 门禁阈值 | 是否触发 |

## ROI 结论
年化收益 / 总成本（含维护）/ 回收期 / 结论（做 / 改更轻解法 / 不做）
```

## 质量标准

- 四指标须齐全并写明分母；口径不清不得给数字。
- 必须输出「不用于个人评价」声明。
- 技术债利息口径与台账一致；不一致即返工。
- 容量 / 成本数据缺失时给采集清单，禁止臆造。
- ROI 必须含维护成本，回收期判据（12 个月）须显式给出结论。

## 失败回退机制

| 步骤 | 失败条件 | 回退目标 | 最大重试 | 不可恢复时升级路径 |
| - | - | - | - | - |
| 第一步：DORA 口径 | 采集点数据缺失 | 输出埋点需求清单 + 现有可近似指标（须标注为近似） | 2 | 标注「指标待补」，不得给趋势结论 |
| 第二步：反模式排除 | 用户坚持用于绩效考核 | 书面说明风险（古德哈特定律）并保留其决定 | 0 | 标注「已提示风险，用户决定保留」 |
| 第三步：技术债利息 | 单条利息无法量化 | 退为「影响面 × 频次」定性排序 | 1 | 标注「利息待量化」 |
| 第四步：容量成本 | 成本口径不完备 | 输出口径清单与缺口 | 1 | 标注「口径不全」，不给单位成本 |
| 第五步：ROI | 收益无法量化 | 转为定性收益说明 + 明确不可量化 | 1 | 回收期标注「不可计算」，交用户决策 |
| 第六步：边界核对 | 与 SLO / 基线口径冲突 | 以已有机制口径为准并引用，不重算 | 1 | 标注冲突点并交用户裁定 |


## 关联 reference

- **technical-strategy**（技术战略与演进）— 技术债台账利息口径与偿还排序的数据来源
- **performance-benchmark**（性能基准测试）— 单点性能基线，本 reference 不重复
- **incident-review**（事故复盘与 SLO）— 可靠性指标（SLI/SLO/错误预算），本 reference 不重复
- **spec-driven-development**（Spec驱动开发）— 价值判据中的收益 / 回收期引用本 reference 口径
- **production-readiness**（生产就绪）— 容量与成本门禁进入 PRR 检查
- **project-memory-management**（项目记忆管理）— 指标基线与口径变更沉淀
