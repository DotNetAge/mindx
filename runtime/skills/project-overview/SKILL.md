# 项目概况收集

## 何时用

用户想了解全部（或多个）项目的概况——典型问法："所有项目怎么样了"、"盘点一下我的项目"、"各项目进展如何"。用户的工作并不全经秘书安排，很多项目自行推进，所以概况来自**现场收集**，不是秘书的既有记录。

## 核心纪律（红线级）

- **只收集概况，不做探索**：禁止把项目目录里所有文件仔细读一遍。收集对象是**现成的资料与报告**，不是源码与目录树——收集是为了了解概况，不是为了审查项目。
- **查找路径固定，命中即止**：每个项目按顺序只查三处——
  1. `README.md`：项目是什么（frontmatter 的 name/type/abstract 优先）
  2. `.agents/reports/`：既有报告
  3. `.agents/notes/`：备忘记录

  三处都没有资料的项目如实标注"无现成资料"，不猜测、不硬凑，可提议补建档（按 `generate-readme` 技能）。
- **只描述概况不管专业问题**：技术细节、专业判断不展开——那是领域 Agent 的事；本技能产出的是用户一眼能懂的概况。

## 第一步：找到所有项目

```bash
mindx project list          # 全部项目去重清单（含负责人与最近活动）
mindx project list --json   # 结构化输出
```

- 项目从所有会话的工作目录聚合去重而来；`leader` 为空表示用户亲自处理、尚无 Agent 接手
- 需 daemon 运行（已执行 `mindx start`）

## 第二步：逐项目收集

对清单中每个项目，按「核心纪律」的固定路径读取三处资料，每个项目提炼：

- **是什么**：一句话（来自 README）
- **最近动态**：reports/notes 里最近的内容要点（有就写，没有就略）
- **状态**：活跃 / 无现成资料 / 长期未动（结合 project list 的最近活动时间判断）

## 第三步：汇总呈现

- 默认文字汇总：一项目一段，先总后分——共多少项目、多少活跃、多少缺资料，再逐项目概况
- 用户要可视化时按 `dashboard` 技能呈现（项目跟踪场景）
- 发现明显停滞或缺资料的项目，如实指出并提议下一步（补建档 / 安排负责人），不擅自安排
