# 构建组织

组织架构图的生产者唯一是你。老板只看图，不见 XML——所有 XML 的组装、修改、发布都由你完成，老板全程只面对两样东西：一张图，和你的提问。

## 何时使用

- 老板还没有组织：先建组织（名称 + 别名），建好即所有者
- 老板要新建组织架构：从零画出第一张架构图并发布
- 老板要调整现有架构：加减部门、换汇报关系、改职位
- 老板要请人入职：发定向邀请（先把账号补进树再邀请）
- 老板要移除成员：查编号、确认、移除（敏感动作）

## 核心决策路由

### 入口判断（先跑一条命令定分支）

```
mindx org architecture show
```

- 成功输出 XML → 走「修订流程」
- 报错含「尚未发布」→ 走「新建流程」（组织已存在，只缺树）
- 报错含「没有加入任何组织」→ 走「建组织」（见下），建好回本入口重跑
- 报错「cannot connect to daemon」→ 告知 daemon 未启动，等启动后重试

### 建组织（尚无组织时）

1. 问老板两件事（AskUser，问不到不猜）：组织叫什么名字（展示名，中文可）；别名是什么（slug，小写字母/数字/连字符，命令与链接里用它）——老板没给别名时按名字拟一个征得同意
2. `mindx org create "<组织名>" "<别名>"`；服务端拒绝（别名重复/格式不符）时原样转述原因，换别名重试
3. 成功后老板即所有者，回「新建流程」画第一张树

### 新建流程（六步）

1. **问类型**：按下列选项问老板要建哪类组织（AskUser，选项先行，附「其他」兜底）：
   - 微型合伙（3-8 人扁平） / 初创公司（四部门） / 标准中小企业（五部两层） / 贸易电商 / 连锁门店 / 科技研发
2. **取样板**：按所选类型从 `references/templates.md` 取对应样板 XML 作为底稿；老板口述了真实部门/人名的，以口述为准对样板做增删改
3. **补细节**：样板里的 name 是岗位占位名。问老板三件事，问不到的保留岗位占位名，禁猜测具体人名：顶层是老板本人吗（职位怎么写）；哪些位置已有真人（姓名/职位）；还有哪些空位要保留
4. **画图呈现**：按下方「SVG 画图规范」把树画成图发给老板，附一句人话总结（共几人、几个空位、哪些位置待定）
5. **多轮修改**：老板每提一条修改意见 → 改 XML → 重画重发 → 直到老板说「可以」「就这样」
6. **发布**：`mindx org architecture publish --file <路径>`（先把最终 XML 写入临时文件）；发布成功后提示下一步是邀请入职（见「邀请入职」）

### 修订流程（三步）

1. `mindx org architecture show` 取当前树 → 按 SVG 规范画图 → 与老板确认要改哪里
2. 改 XML → 重画重发 → 老板确认
3. `mindx org architecture publish --file <路径>` 发布（整树替换，覆盖前无需另问——图老板已逐轮确认过）

### 邀请入职（发布树之后）

1. 被邀人的**可寻址账号**（用户名/手机号/GitHub 名）必须先填入树中对应节点的 account 属性并重新发布，否则对方入职时找不到自己的位置
2. `mindx org invite <账号> "<职位>"` 发邀请
3. 告知老板：邀请不会自动通知对方（无推送通道）——请线下告知对方「已被邀请」，对方在本机用同一账号登录并跑入职核销后即占座入册；同账号重复邀请会被服务端拒绝（pending 唯一）

### 移除成员（敏感动作）

1. `mindx org members` 拿在册清单（含成员编号）→ 向老板报出「姓名 + 编号」请求确认
2. 老板明确点头后才执行 `mindx org remove <编号>`；报错原样转述给老板（owner 不可移除、admin 不能移 admin 是服务端规则）
3. 移除后告知：坐席已空出可绑新人；架构树里对应节点是否改空位由老板定（要改则走修订流程）

## SVG 画图规范（每次画图必用）

- 输出**单个连续内联 `<svg>` 块**：首行顶格以 `<svg` 开始，整块中间不得出现空行（空行会截断渲染）；必须带 `xmlns="http://www.w3.org/2000/svg"` 与 `viewBox`
- 布局：自顶向下树形。每层一行，层内节点横排；父节点画在子节点组的水平中点上方，正交连线（竖线+横线）
- 节点：圆角矩形（`rx="6"`），宽 150 高 54，水平间距 24，层间距 76。节点内两行文本：上行姓名/岗位名（`font-weight="bold"` 14px），下行职位（12px）
- 配色：实位节点 `fill="#2F6FED"` 白字；空位节点 `fill="#FFFFFF" stroke="#9AA4B2" stroke-dasharray="4 3"` 灰字——空位与否看节点 account 属性是否为空
- 画布：`viewBox="0 0 W H"`，W = 最大层节点数×174 + 40，H = 层数×130 + 40；单层超 8 个节点时分两行或按部门分组重排，别硬拉宽
- 禁止：`<script>`、`on*` 事件属性、外部图片引用、注释里的敏感信息
- 图后必附一句话总结：总人数、空位数、待补账号的人。SVG 无法渲染时（老板说看不到图）改用缩进文本树兜底呈现，流程不变

## XML 格式规则

- 根节点：`<org name="组织名">`；成员节点：`<member name="姓名" title="职位" account="账号">`，子成员嵌套在父节点内
- `name` 必填（每个节点都要有）；`title`、`account` 可空；`account` 留空 = 空位
- 组织上限 500 节点；一人一格——同一账号在树中出现两次会被服务端拒绝
- 服务端拒绝发布时错误信息是人话（如「每个成员节点都必须有姓名」），据此改树重发即可，不用换命令

## 纪律边界

- **发布需明示确认**：老板对当前图说过「可以/就这样/发布吧」才允许 publish；「先这样」「差不多」不算确认，追问一句「我现在发布？」
- **不猜人名**：没有从老板处得到的姓名一律用岗位占位名呈现，并在图后总结里点明「哪些是待定占位」
- **临时文件落 /tmp**：待发布的 XML 写 `/tmp/org-arch-<组织别名>.xml`，不落进任何项目目录
- **移除与发布外不扩权**：本技能只动 `mindx org *` 六条命令；不改组织订阅、不删组织、不碰成员的本机文件

## 失败模式（现象→原因→动作）

- 现象：`create` 被拒。原因：别名重复或格式不符（服务端给的是人话原因）。
  动作：别名只能小写字母/数字/连字符，按原因换别名重试；组织名可原样保留。
- 现象：`architecture show` 报「组织架构尚未发布」。原因：组织新建成，树从未发布过。
  动作：走新建流程，不是故障。
- 现象：`publish` 被拒。原因：树结构不合法（缺 name / 账号重复 / 超 500 节点 / 超 256KB）。
  动作：按服务端人话原因修树重发；改完自查一遍每节点都有 name。
- 现象：`invite` 被拒「已在待邀请中」。原因：同账号已有 pending 邀请。
  动作：告知老板该邀请还在等对方核销，无需重复发。
- 现象：`remove` 被拒。原因：目标 owner / admin 动 admin / 编号不存在。
  动作：原样转述服务端原因；owner 要退出只有转让或删组织两条路（都超出本技能权限，如实告知）。
- 现象：老板说图显示不出来。原因：消息渲染层拦截。
  动作：改用缩进文本树重发一次，继续流程。

## 命令速查

```
mindx org create <组织名> <别名>                       建组织（创建者即所有者）
mindx org architecture show [--org <组织>]            查看当前树（XML 原文）
mindx org architecture publish [--org <组织>] [--file 路径]  发布/覆盖整树
mindx org members [--org <组织>]                      在册成员清单（含编号）
mindx org invite <账号> [职位] [--org <组织>]         发定向邀请
mindx org remove <成员编号> [--org <组织>]            移除成员
```
