# 技术影响力载体（tech-influence）

> 工程纪律层专项：把技术判断转成**可被他人评审、采纳、执行**的文档载体。不替代 `code-review`（审 diff）与 `ai-coding-governance`（为 Agent 定规则）。

**触发**：RFC、技术方案评审、架构评审、评审材料、技术标准、技术规范、规范草案、技术分享、方案对齐、跨团队方案、评审意见处理。

## 适用边界

- **加载**：需要产出给**他人**评审或采纳的技术文档；需要把方案对齐到多个团队；需要把约定固化为可检查的规范。
- **跳过**：仅自己使用的实现说明（走 `doc-generation`）；单个 diff 的合并前审查（走 `code-review`）。
- **范围声明**：本 reference 只产出**载体（文档）与评审流程动作**；组织决策权、资源调配与人员管理不在范围——本 reference 让判断**可被采纳**，不替组织做决定。

**铁律**：评审材料里没有「替代方案」与「回滚路径」的，不得送评审。

## 执行流程

### 第一步：判断是否需要 RFC

| 需要 RFC | 不必 RFC |
| - | - |
| 影响 ≥2 个团队或 ≥2 个服务 | 单模块内实现 |
| 变更公开契约（API / 表结构 / 配置格式） | 内部重构（不改变外部可见行为） |
| 不可逆或难回退 | 可逆改动（`architecture-decision` 可逆性四级中的「可逆」档） |
| 需他人排期配合 | 自闭环、单人可完成 |

- 命中左栏任一行 → 走 RFC；否则直接实现，不制造流程负担。
- 判据不明时按「影响面」优先：说不清影响谁 → 先做第三步的评审前必答。

### 第二步：RFC 七段模板

| 段 | 内容 | 判据 |
| - | - | - |
| 1 背景 | 当前状态 + 事实锚点（工单 / 指标 / 事故） | 不得只写「现状不佳」 |
| 2 问题 | 要解决哪个**已发生**的问题 | 举得出实例 |
| 3 方案 | 具体到接口签名 / 表结构 / 流程 | 可被他人照做 |
| 4 替代方案与反选 | ≥2 个候选 + 为何不选（格式对齐 `architecture-decision.md`） | 空 → 不得送评审 |
| 5 影响面 | 受影响团队 / 服务 / 数据 / 用户，逐项列出 | 无「可能影响部分模块」式泛化 |
| 6 迁移与回滚 | 迁移步骤 + 回滚动作 + 兼容窗口（引 `technical-strategy.md` 窗口判定） | 空 → 不得送评审 |
| 7 评审结论 | 同意 / 反对 / 存疑 + 决议人 + 生效日期 | **评审后回填**，留空视为 RFC 未闭环 |

### 第三步：架构评审前必答 8 问

1. 它解决哪个**已发生**的问题？
2. 不做会怎样？（代价量化优先，不可量化则定性说明）
3. 替代方案是什么，为何不选？
4. 影响哪些团队 / 服务？他们需要做什么？
5. 数据模型变了什么？迁移与回滚怎么做？
6. 失败模式是什么？降级 / 熔断 / 限流怎么设计？
7. 怎么验证？证据类型是什么？何时算成功？
8. 什么条件下重新评估（撤销条件）？

- 答不出的问题标注「待补」并写明补齐方式；**不得带空问题进评审**。
- 第 2、3、6 问为核心项，缺任一项视为材料不完整。

### 第四步：技术规范草案结构

| 段 | 内容 | 判据 |
| - | - | - |
| 适用范围 | 哪些模块 / 语言 / 场景 | 可列举，无「所有代码」式泛化 |
| 条款 | 每条一个断言 | **可 grep / 可 lint / 可测试**三者之一 |
| 例外 | 什么情况下不适用 | 例外须带理由与批准人 |
| 检查方式 | 怎么查（命令 / 工具 / 人工抽查） | 给出具体命令或检查项 |

- 反模式：「代码应保持清晰」不可检查 → 改写为「单函数 ≤ 50 行（可用 lint 检查）」。
- 条款与 `ai-coding-governance.md` 的规则文件对接：可检查条款直接成为规则条目。

### 第五步：评审意见处理

| 意见 | 处理 | 记录 |
| - | - | - |
| 同意 | 采纳并并入方案 | 记入 RFC 第 7 段 |
| 反对 | 要么改方案，要么**书面回应**反对理由 | 反对理由与回应均留档 |
| 存疑 | 转为待验证项 + 验证方式 + 负责人 | 进 RFC 待办，不得静默丢弃 |

- 禁止用「已私下沟通」代替书面结论；无结论的评审视为未完成。
- 评审结论须写清决议人（角色而非只能是人名）与生效日期。

### 第六步：沉淀

- RFC 定稿与规范发布后索引到项目记忆（Decision Record / Convention Capture 两种模式）。
- 规范条款的检查方式交给工程侧固化（lint 规则 / CI 检查项 / 评审清单）。

## 输出格式

```
## RFC: [标题]
1 背景：…  2 问题：…
3 方案：…  4 替代方案与反选：候选 A/B + 为何不选
5 影响面：团队 / 服务 / 数据 / 用户
6 迁移与回滚：步骤 + 回滚 + 兼容窗口
7 评审结论：同意/反对/存疑 + 决议人 + 生效日期

## 评审前必答 8 问
| # | 问题 | 答复 | 状态（已答/待补） |

## 规范草案
| 条款 | 可检查方式 | 例外 |
```

## 质量标准

- 第 4、6 段缺失的材料不得送评审（铁律）。
- 影响面必须逐项列名，禁止「可能影响部分模块」式表述。
- 规范条款必须可检查；不可检查的须改写或标注豁免理由。
- 评审意见三类（同意 / 反对 / 存疑）均须有书面去向，不得静默丢弃。
- 不得声称本 reference 可替代组织决策或人员管理（范围声明）。

## 失败回退机制

| 步骤 | 失败条件 | 回退目标 | 最大重试 | 不可恢复时升级路径 |
| - | - | - | - | - |
| 第一步：是否需要 RFC | 影响面无法判定 | 先执行第三步必答 4（影响哪些团队） | 1 | 按「保守走 RFC」处理并标注 |
| 第二步：RFC 七段 | 替代方案想不出第 2 个 | 引 `architecture-decision.md` 第二步（至少 2 个真实方案） | 2 | 标注「单一合理实现」，豁免反选并说明 |
| 第三步：必答 8 问 | 第 6 问（失败模式）无法回答 | 引 `threat-modeling.md` 补失败模式分析 | 1 | 标注「待补」并明确补齐责任人 |
| 第四步：规范草案 | 条款无法转为可检查项 | 降级为「评审清单项 + 人工抽查频率」 | 1 | 标注「不可自动检查」，列入人工审计 |
| 第五步：意见处理 | 反对意见无法回应 | 保留反对记录 + 标注未达成一致 | 0 | 上交决议人裁决，不得静默推进 |
| 第六步：沉淀 | 项目记忆不可用 | 输出本地文件并标注未沉淀 | 1 | 提示用户手动保存 |
