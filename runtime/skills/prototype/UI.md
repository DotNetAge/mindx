# UI 原型

在同一路由下生成**多套差异明显的 UI 变体**，通过悬浮底栏切换。用户在浏览器里来回翻看，选中一个（或从每套里各偷一点），然后扔掉其余的。

如果问题是关于逻辑/状态而非外观 —— 分支错了。用 [LOGIC.md](LOGIC.md)。

## 什么情况下适合这个形态

- 「这个页面应该长什么样？」
- 「在敲定之前，我想看看这个仪表盘的几个方案。」
- 「给设置页换个布局试试。」
- 任何用户原本要花一天时间在脑子里三张模糊草稿之间纠结的场景。

## 两种子形态 —— 强烈优先子形态 A

UI 原型在**紧贴应用其余部分**时最容易被评判 —— 真实的页头、真实的侧栏、真实的数据、真实的信息密度。孤立的一次性路由是个真空环境：每个变体单独看都挺好。只要有合理的现有页面可以承载变体，就默认用子形态 A。只有当原型确实无处安放时才退而求其次用子形态 B。

### 子形态 A —— 在现有页面上调整（优先）

路由已经存在。变体渲染在**同一路由**上，由 `?variant=` URL 查询参数控制。现有的数据获取、参数与鉴权全部保留 —— 只有渲染部分切换。这是默认选择；除非有明确理由，否则选它。

如果原型针对的东西还没有页面，但*天然应该长在某个页面里*（仪表盘的新版块、设置页的新卡片、现有流程的新步骤）—— 这仍然算子形态 A。把变体挂载到宿主页面内部。

### 子形态 B —— 新建页面（最后手段）

仅当要原型化的东西确实没有可容纳它的现有页面时使用 —— 例如全新的顶层界面，或无法合理嵌入任何位置的流程。

创建一个**一次性路由**，遵循项目已有的路由约定 —— 不要发明新的顶层结构。命名要让人一眼看出是原型（例如在路径或文件名里带上 `prototype` 一词）。同样用 `?variant=` 模式。

在确定用子形态 B 之前先自问：真的没有可以嵌入的现有页面吗？空路由会掩盖真实页面会暴露的设计问题。

两种子形态的悬浮底栏完全一致。

## 流程

### 1. 写明问题并确定数量 N

默认 **3 个变体**。超过 5 个就不再是差异明显，而是噪音 —— 以此为上限。

用一行话写下计划，放在原型所在位置或文件顶部注释里：

> 「设置页的三个变体，通过 `?variant=` 切换，挂在现有 `/settings` 路由上。」

无论用户是否在场质疑，这一步都要做。

### 2. 生成差异明显的变体

起草每个变体。每一套都要满足：

- 页面的用途，以及它能拿到的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，用什么就用什么）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同** —— 不同的布局、不同的信息层级、不同的主要操作方式，而不只是换个配色。三个微调过的卡片网格不是 UI 原型，是墙纸。如果两稿太像，就用明确的「不要用卡片网格」指引重做一稿。

### 3. 把它们接起来

在路由上创建一个单一的切换组件：

```tsx
// 伪代码 —— 按项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：所有现有数据获取都保留在切换器之上；每个变体只改变渲染的子树。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

一个固定定位的小条，位于屏幕底部居中，包含三个部分：

- **左箭头** —— 切到上一个变体（循环）。
- **变体标签** —— 显示当前变体键名，如果变体导出了名称，也一并显示。例如 `B — 侧栏布局`。
- **右箭头** —— 切到下一个变体（循环）。

行为：

- 点击箭头更新 URL 查询参数（用框架的路由 —— Next 上用 `router.replace`，React Router 上用 `navigate` 等），这样变体可分享且刷新后稳定。
- 键盘：`←` 和 `→` 方向键同样可循环切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 视觉上要与页面区分开（例如高对比的胶囊形、轻微阴影），让人明确知道它不是被评审的设计的一部分。
- 在生产构建中隐藏 —— 用 `process.env.NODE_ENV !== 'production'` 或等价检查做门控，防止误合并的原型把切换条带给用户。

把切换器放在一个共享组件里，两种子形态都能复用。放在项目存放共享 UI 的位置。

### 5. 交给用户

给出 URL（以及 `?variant=` 的键名）。用户有空时会自行翻看。最有价值的反馈通常是**「我想要 B 的页头加 C 的侧栏」** —— 那才是他们真正想要的设计。

### 6. 记录答案并清理

一旦某个变体胜出，写下选了哪个以及为什么（提交信息、ADR、issue，或 AFK 运行且用户尚未回复时放在原型旁边的 `NOTES.md`）。然后：

- **子形态 A** —— 删除落选变体和切换器；把胜者吸收进现有页面。
- **子形态 B** —— 把胜出的变体提升为正式路由，删除一次性路由和切换器。

不要让变体组件和切换器散落在仓库里。它们烂得很快，还会迷惑下一位读者。

## 反模式

- **只在配色或文案上有差异的变体。** 那是微调，不是原型。真正的变体在结构上就不一致。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就违背了初衷。每个变体都应该有推翻整个布局的自由。
- **把变体接到真实的写操作上。** 只读原型完全够用。如果某个变体需要变更数据，指向一个 stub —— 问题是「它应该长什么样」，不是「后端能不能用」。
- **把原型直接提升为生产代码。** 变体代码是在原型约束下写出来的（没测试、错误处理最少）。吸收时请认真重写。
