# 原型

原型是**用来回答一个问题的一次性代码**。问题决定形态。

## 选择分支

先弄清楚要回答的是哪个问题 —— 从用户的提示、周围的代码中判断，如果用户在场就直接问：

- **「这套逻辑 / 状态模型感觉对吗？」** → [LOGIC.md](LOGIC.md)。构建一个微型交互式终端应用，驱动状态机跑过那些在纸面上很难推演的场景。
- **「它应该长什么样？」** → [UI.md](UI.md)。在同一路由下生成多套差异明显的 UI 变体，通过 URL 查询参数和悬浮底栏切换。

两个分支产出的东西截然不同 —— 选错分支，整个原型就白做了。如果问题确实含糊且联系不上用户，默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型开头声明这一假设。

## 两个分支通用的规则

1. **从第一天起就是一次性的，并醒目标注。** 把原型代码放在它将来实际会被使用的位置附近（紧邻它所服务的模块或页面），让上下文一目了然 —— 但命名要让普通读者一眼看出这是原型，不是生产代码。对一次性 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **一条命令即可运行。** 用项目现有任务-runner 支持的任何方式 —— `pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能不假思索地把它跑起来。
3. **默认不做持久化。** 状态放在内存里。持久化恰恰是原型要**验证**的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，就用一个临时数据库或本地文件，并起一个醒目的「PROTOTYPE — 可随时删除」名字。
4. **跳过打磨。** 不写测试，除让原型**能跑起来**所需外不做错误处理，不做抽象。重点是快速学到东西，然后删掉。
5. **让状态可见。** 每次操作后（逻辑分支）或每次切换变体后（UI 分支），打印或渲染完整的相关状态，让用户看清变化。
6. **结束时删除或吸收。** 当原型回答了它的问题，要么删掉它，要么把验证过的决策吸收进真实代码 —— 不要让它在仓库里烂着。
7. **精确标注环境与状态。** 基于真实证据，把产物标注为本地原型、静态演示、测试部署或生产部署。一个能访问的 URL 本身不能证明生产就绪、认证、持久化、性能或合规。
8. **把事实与演示假设分开。** 将模拟数据、示例用户、权重、阈值、预测数据、客户评价和转化数据标注为未经校验的示例，除非用户提供了可核实的来源。绝不编造验证数量、成功日志或指标提升。
9. **高风险决策必须有人把关。** 用于招聘、医疗、法律、金融、投资或其他重大决策时，只构建决策辅助与审计流程。不得输出或自动化最终决策；必须由可问责的人工与适用的专业审查把关。
10. **外部副作用必须设门槛。** 在生产部署、真实账号创建、数据库写入、发送通知、支付或其他不可逆操作之前，说明目标、范围、所需权限、回滚与验证方案，并取得明确授权。

## 完成之后

原型唯一值得保留的是**答案**。把它连同它回答的问题一起，记录在持久的地方（提交信息、ADR、issue，或原型旁边的 `NOTES.md`）。记录实际的运行命令、观察到的证据、环境、遗留假设和未验证范围。如果用户在场，记录就是一段简短对话；如果不在，就留好占位，让他们（或下一次执行时的你）在删除原型前补上结论。
