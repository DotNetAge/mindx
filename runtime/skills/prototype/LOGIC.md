# 逻辑原型

一个微型交互式终端应用，让用户亲手驱动状态模型。当问题关于**业务逻辑、状态流转或数据形状**时使用 —— 这类东西在纸面上看起来合理，但只有跑过真实场景才能发现问题。

## 什么情况下适合这个形态

- 「我不确定这个状态机能不能处理先 X 后 Y 的边界情况。」
- 「这个数据模型真的能表达……这种情况吗？」
- 「我想在写 API 之前先摸清它应该长什么样。」
- 任何用户想**按键操作并观察状态变化**的场景。

如果问题是「它应该长什么样」 —— 分支错了。用 [UI.md](UI.md)。

## 流程

### 1. 写明问题

写代码之前，先写下要原型化的状态模型和要回答的问题。写一段话，放在原型的 README 里或文件顶部的注释中。回答错误问题的逻辑原型纯属浪费 —— 把问题写明确，之后才能核对，无论用户是正在围观还是稍后回来看。

### 2. 选择语言

宿主项目用什么就用什么。如果项目没有明显的运行时（例如纯文档仓库），就问。

工具链遵循项目现有约定 —— 不要为了一个原型引入新的包管理器或运行时。

### 3. 把逻辑隔离到可移植的模块中

把真正回答问题的那部分逻辑，放进一个小而纯粹的接口后面，将来可以整体抽出来放进真实代码库。包在外面的 TUI 是一次性的；逻辑模块不该是。

正确的形态取决于问题本身：

- **纯 reducer** —— `(state, action) => state`。适合动作是离散事件、状态是单一值的场景。
- **状态机** —— 显式的状态与转移。适合「当前哪些动作合法」本身就是问题一部分的场景。
- **作用于纯数据类型的一小组纯函数**。适合没有隐式的当前状态、只有变换的场景。
- **带清晰方法面的类或模块**，当逻辑确实持有持续演进的内部状态时。

选择最贴合问题的形态，*而不是*最容易接到 TUI 上的形态。保持纯净：不做 I/O，不写终端代码，不用 `console.log` 做流程控制。TUI 导入它并调用它；任何东西都不反向流动。

这正是原型能在其生命周期之外仍有价值的原因。当问题被回答后，经过验证的 reducer / 状态机 / 函数集可以整体搬进真实模块 —— TUI 外壳则被删除。

### 4. 构建最小的、能暴露状态的 TUI

把它做成**轻量 TUI** —— 每一次 tick，清屏（`console.clear()` / `print("\033[2J\033[H")` 或等价方式）并重新渲染整帧。用户看到的应该始终是一个稳定的画面，而不是不断增长的滚动缓冲。

每一帧包含两个部分，按此顺序：

1. **当前状态**，美化打印且 diff 友好（每行一个字段，或格式化的 JSON）。字段名或小节标题用**加粗**，次要上下文（时间戳、ID、派生值）用**暗淡**。原生 ANSI 转义码就够用 —— `\x1b[1m` 加粗、`\x1b[2m` 暗淡、`\x1b[0m` 复位。除非项目里已经有样式库，否则不必引入。
2. **键盘快捷键**，列在底部：`[a] 添加用户  [d] 删除用户  [t] 时钟步进  [q] 退出`。按键加粗、描述暗淡（或反过来）—— 哪种读起来清晰就用哪种。

行为：

1. **初始化状态** —— 单个内存中的对象/结构体。启动时渲染第一帧。
2. **每次读取一个按键（或一行）**，分发给修改状态的处理器。
3. **每次操作后重新渲染完整帧** —— 不要追加，要替换。
4. **循环直到退出。**

整帧应该能在一屏内放下。

### 5. 一条命令即可运行

在项目现有的任务-runner 里加一个脚本（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`）。用户应该运行 `pnpm run <prototype-name>` 或等价命令 —— 永远不需要记路径。

如果宿主项目没有任务-runner，就把命令放在原型 README 的顶部。

### 6. 交给用户

把运行命令交给用户。他们会自己驱动它；最有价值的时刻是他们说出「等等，这不应该发生」或「咦，我原以为 X 会不一样」 —— 这些是**想法**里的 bug，而这正是原型的全部意义。如果他们想加新动作，就加。原型是会演进的。

### 7. 记录答案

当原型完成了使命，问题的答案就是唯一值得保留的东西。如果用户在场，问它教会了他们什么。如果不在，就在原型旁边留一个 `NOTES.md`，让答案可以被填上（或者由你来填，如果你旁观了整个过程），然后再删除原型。

## 反模式

- **不要加测试。** 需要测试的原型就不再是原型了。
- **不要接真实数据库。** 用内存存储，除非问题本身就是关于持久化的。
- **不要泛化。** 不搞「万一以后要支持 X」。原型只回答一个问题。
- **不要把逻辑和 TUI 搅在一起。** 如果 reducer / 状态机引用了 `console.log`、提示输入或终端转义码，它就不再可移植。让 TUI 保持在纯模块之上的一层薄壳。
- **不要把 TUI 外壳带进生产。** 外壳是为终端手工驱动优化的。它背后的逻辑模块才是值得保留的部分。
