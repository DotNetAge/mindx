# USER.md 格式规格

> 本规格锁定 `~/.mindx/USER.md` 的章节与条目写法。任何人（任何模型）按本规格写出的画像，结构必须完全一致；差异只允许出现在内容里。

## 总则

1. 章节顺序固定，标题措辞固定，不得增删改名；无内容的章节保留标题，正文写一行「暂无记录」。
2. 条目句式固定：**结论——证据**。结论一行说清偏好本身；证据标注观察来源（哪次对话、哪个项目、用户原话或军规定案）。
3. 无证据不落笔。推测性条目必须在证据段开头标「（推测）」，并在被证实或证伪后更新。
4. 说人话：画像会被所有 Agent 直接消费，写用户视角的自然语言，禁止技术黑话与含混形容词（「比较喜欢」「还不错」之类不可核实的话不写）。
5. 全文控制在百行以内：高信噪比优先，宁缺毋滥。

## 章节规格

按序六节：

### 身份与称呼

怎么称呼、身份背景、所在行业与角色。是所有对话的基调。

### 沟通偏好

语言、回复风格、措辞禁忌。例如：结论先行、禁用表情符号、说人话不讲机器话、禁止某种句式。

### 审美偏好

UI 与设计的口味：配色、布局、动画、组件风格、反面案例。设计、选型类决策直接消费本节。

### 工作偏好

协作与交付习惯：代码风格、命名约定、决策方式（谁拍板、何时要选项）、对时间估计与文档的态度。

### 红线与禁忌

用户明确否决过、发过火、反复纠正的东西。**本节是全档案价值最高的区域**——一条红线能避免所有 Agent 重复踩坑。写法与其他节一致，但每条必须可追溯到具体事件。

### 背景与技术栈

经历、能力边界、常用技术栈与工具链。委托任务、选技术方案时消费本节。

## 示例（虚构人物，仅示范格式）

```markdown
# 用户画像

## 身份与称呼

- 偏好被称为「船长」，认为比「老板」更像一起航行的伙伴——首次通话时主动确认（2026-08）
- 连锁餐饮企业主，名下 12 家门店，关注数字化运营——自我介绍时提及（2026-08）

## 沟通偏好

- 结论先行，简短回答——全局军规定案（2026-10）
- 禁止使用表情符号——全局军规定案（2026-09）

## 审美偏好

- 界面文字必须说人话，不透露技术细节——军规定案后多次纠正 Agent 用词（2026-10）
- （推测）偏好冷色调——三次方案汇报均在冷色系方案上停留更久（2026-09）

## 工作偏好

- 需要用户决策时直接给 2-3 个选项，禁止长篇方案清单——明确纠正过两次（2026-09、2026-10）
- 禁止任何时间估计——多次删改文档中的工期表述（2026-09）

## 红线与禁忌

- 不要在未确认前执行不可逆操作——曾因自动清理目录表达不满（2026-09）
- 不要用「大概、可能」汇报已完成的工作——验收对不上时发过火（2026-08）

## 背景与技术栈

- 出版过两本行业专著，对长文创作有专业心得——闲聊中提及（2026-08）
- 常用工具链：微信生态、飞书、Excel——项目往来文件观察（2026-08 至今）
```

## 反例

- `用户人很好，沟通顺畅`——不可核实的空话，无消费价值。
- `用户喜欢简洁`——无来源、无措辞依据，两个月后没人知道「简洁」指什么。
- `用户可能喜欢深色主题`——推测条目未标「（推测）」，会被当作已证实事实消费。
- 自创章节（如「用户的一天」「情绪记录」）——结构漂移的起点，一律禁止。
