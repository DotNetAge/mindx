# 组建团队

把"接手一个没有团队的大项目"变成"一支编制合理、各司其责的智能体团队"。

## 何时使用

- 用户接手或打开一个大型项目，说"给这个项目配个团队"、"帮我组建一个团队负责这个项目"
- 项目已有会话与代码，但尚无团队实体负责它
- 复盘产出的成建制团队提议经用户裁决后，由本技能执行建制

**不使用**：只想创建单个 Agent（走 agent-creator）；项目已有完整团队且运转正常（告知用户并停止，编制修订由用户另起任务，不归本技能）。

## 主题澄清（动手前必做）

用户未指明目标项目或组建范围时，禁止自行猜测。先用 AskUser 提供 2-4 个假设选项让用户选择，用户不选再开放提问：

- **目标项目不明**（"给我这个项目配个团队"但未指明哪个项目）→ 列出候选：当前会话工作目录 / 最近活跃的项目（`mindx project list` 结果）/ 用户口述的其他项目。
- **范围不明** → 列出候选：全项目组建 / 只补缺口岗位（结合前提检查的存量编制）。
- **目标形态不明** → 列出候选：成建制团队 / 单个 Agent 即可（后者路由 agent-creator）。

每项给具体选项 + "其他（自由输入）"兜底。项目与范围明确后进入工作流。

## 前提检查

1. 确认会话工作目录即目标项目（考古与蓝图都落在这里）
2. `mindx team list --json` 与 `mindx agent list --all --json` —— 项目可能已有部分编制：
   - 已有完整团队 → 告知用户并停止
   - 已有零散 Agent → 只为缺口岗位做增量规划，存量 Agent 纳入编制评估而非重复创建

## 工作流

进入工作流前先 `TaskCreate` 建立任务清单（步骤 1-6 各一项，含每步产出），推进中用 `TaskUpdate` 标记完成状态，中断恢复时用 `TaskList`/`TaskGet` 读取进度，不凭回忆对齐工作点。

### 步骤 1：项目考古（派 SubAgent 执行）

考古会读大量文件，**必须派 SubAgent 执行**（检索型子任务只返结论），主上下文只聚合判断。考古维度：

- 技术栈与框架（语言、构建工具、依赖清单）
- 模块划分与目录结构（顶层模块、职责边界）
- git 热区（近 30 天改动集中的模块——活跃度即职责权重）
- 外部接口面（API、数据库、部署方式）
- 现有文档与约定（README、AGENTS.md、规范文件）

考古报告落盘为蓝图工件的「项目现状」节。禁止全量读源码——每个维度抽样即可，结论比细节重要。

### 步骤 2：领域拆解（MECE 检验）

把考古结论拆解为互斥且完备的领域清单：

- **互斥**：任一典型任务有且只有一个明确归属领域——拿一个真实任务对照两个相邻领域，若都说"归我"，重新划界
- **覆盖**：领域并集覆盖项目的主要职责面（以 git 热区与目录结构为准，不为冷代码设岗）

### 步骤 3：产出团队蓝图工件

蓝图落盘项目目录下的 `.agents/plans/team-blueprint.md`，是编制决策的唯一交接物（考古、拆解、确认依据全部在此可追溯）。结构：

```markdown
# 团队蓝图：<项目名>

## 项目现状（考古摘要）
[技术栈 / 模块 / 热区 / 接口面，各 1-3 句]

## 编制清单
| 岗位 | 职责概览（负责什么/产出什么/什么时候用） | 共享技能 | 独享技能 | 来源（复用/新建） |
| ---- | ---------------------------------------- | -------- | -------- | ----------------- |

## 与现成团队对比
[整队复用评估：本地 `mindx team list --json` 与市场 `mindx market list --kind team` 的检索词、命中项、契合度结论。检索词必须覆盖需求的全流程词（如「软件研发」「全流程交付」），禁止只搜单个岗位词。结论为「无一契合」时也要写明检索词与排除理由——缺本节不放行建制]

## 负责人选定
[谁任 leader 及理由——通常选职责横跨多领域或主导集成度的岗位。leader 岗硬性要求：1 门管理技能（任务拆解/派工/验收类；默认装配 goal-planner 目标规划，覆盖拆解、估算与选岗派工，等价技能可替换）+ 1 门领域手艺技能（能抽查验证成员产出——验收取证由它承担，goal-planner 不做执行），缺一即空心领导，禁止注册]

## 团队职责（Profile 要点）
[协作规则、验收口径、汇报链路——写法按 references/team-design.md 编制规范第 6-9 条执行]

## 工作区约定
| 产物 | 落点 | 责任岗位 |
| ---- | ---- | -------- |
[每类交接产物写明落点目录（docs/、data/、records/ 等）；团队工作目录（即本项目目录）根必建 AGENTS.md——目录地图、当前进度、更新规则，接手只读它就能续作，不靠考古历史会话]
```

岗位概览写法（概览三问）按 agent-creator 技能的 references/agent-writing.md 执行。共享技能是全团队一致性的方法论（如代码审查、测试生成、根因调试），独享技能是岗位专有做法（如特定框架开发）——只装配该岗位需要的，每个技能都消耗上下文。

### 步骤 4：老板确认（建制前必过）

把蓝图呈现给用户：岗位清单、每个岗位的一句话概览、来源标记（复用/新建）、负责人选定。**用户确认前不创建任何实体**；用户要求调整则修订蓝图重新确认。

### 步骤 5：复用检索与建制

**先整队检索，再逐岗位检索，能复用绝不新建**（蓝图「与现成团队对比」节缺失或结论未填时，先补齐再进本步）：

1. 团队级检索：`mindx team list --json`（本地）+ `mindx market list --kind team --filter "<关键词>"`——关键词覆盖需求的全流程词（如「软件研发」「全流程交付」），禁止只搜单个岗位词（岗位词只命中个体，命不中成建制团队）。命中定位契合的现成团队 → 与用户确认后整队复用（`mindx market install team <name>`），跳到步骤 6
2. 整队无命中，逐岗位 `mindx market list --kind agent --filter "<领域关键词>"`——命中即 `mindx market install agent <name>`
3. 无现成的，按 agent-creator 技能的单 Agent 工作流从零创建（考古结论此时就是它的领域上下文来源）
4. 建制前核对：leader 装配清单含 1 门管理技能（默认 goal-planner）+ 1 门领域手艺技能（蓝图「负责人选定」节的硬性要求），缺一不建队
5. 全部岗位就位后 `mindx team add <team> --leader <lead> --member ...`，蓝图「团队职责」与「工作区约定」节写入 Team Profile（`mindx team update <team> --profile`），并按约定在本项目根建好目录骨架与 AGENTS.md
6. `mindx team hire <team>`

### 步骤 6：交接

向用户汇报：编制清单（谁负责什么）、启动方式（选团队 = 以负责人身份发起会话）、蓝图文件位置。

## 注意事项

- **共享技能宁少勿多**——每个装配的技能都进入该 Agent 的每次会话上下文；判定标准是"没有它会做错"，不是"有了更好"
- **leader 的 SOUL 必须写「估算 + 阶梯派工 + 抽查验证自己动手」**——团队会话就是与 leader 对话：接到任务先出计划并估算（章法见 goal-planner 技能的「第三步 估算工作量并分配 Agent」与「第四步 选岗并判定执行方式」，共用能力），小验证自己动手（≤5 轮工具调用内出结论），摸底分批派工并写明预算；只收报告不抽查验证的 leader 是空心领导，只埋头包揽不派工的 leader 同样失职
- **确认后的编制修改要同步更新蓝图文件**——蓝图是审计痕迹

## 反模式

- **跳过考古直接建团队** —— 不了解项目就设岗，岗位与实际职责面必然错位
- **复用论证只下沉到 Agent 层与技能层** —— 整队检索（本地 + 市场 `--kind team`，全流程词）不跑或蓝图缺「与现成团队对比」节，成建制现成团队漏网，重复建制烧双份编制
- **一个岗位包整个项目** —— 与"能单不多"矛盾：真只需一个 Agent 时不要组建团队
- **蓝图未确认就建制** —— 批量创建实体必须先过确认门
- **全岗位配同一堆技能** —— 共享与独享不分，上下文被无关技能撑爆
- **建完就散** —— 不写 Team Profile、不落工作区约定（产物落点 + 根目录 AGENTS.md）、不做交接汇报，用户不知道团队怎么用，会话一清团队就断档
