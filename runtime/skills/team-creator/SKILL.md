# 组建团队

把"接手一个没有团队的大项目"变成"一支编制合理、各司其责的智能体团队"。

## 何时使用

- 用户接手或打开一个大型项目，说"给这个项目配个团队"、"帮我组建一个团队负责这个项目"
- 项目已有会话与代码，但尚无团队实体负责它
- 复盘产出的成建制团队提议经用户裁决后，由本技能执行建制

**不使用**：只想创建单个 Agent（走 agent-creator）；项目已有完整团队且运转正常（告知用户并停止，编制修订由用户另起任务，不归本技能）。

## 主题澄清（动手前必做）

用户未指明目标项目或组建范围时，禁止自行猜测。先用 AskUser 提供 2-4 个假设选项让用户选择，用户不选再开放提问：

- **目标项目不明**（"给我这个项目配个团队"但未指明哪个项目）→ 列出候选：当前会话工作目录 / 最近活跃的项目（`mindx project list` 结果）/ 用户口述的其他项目。
- **范围不明** → 列出候选：全项目组建 / 只补缺口岗位（结合前提检查的存量编制）。
- **目标形态不明** → 列出候选：成建制团队 / 单个 Agent 即可（后者路由 agent-creator）。

每项给具体选项 + "其他（自由输入）"兜底。项目与范围明确后进入工作流。

## 前提检查

1. 确认会话工作目录即目标项目（考古与编制决策记录都落在这里）
2. `mindx team list --json` 与 `mindx agent list --all --json` —— 项目可能已有部分编制：
   - 已有完整团队 → 告知用户并停止
   - 已有零散 Agent → 只为缺口岗位做增量规划，存量 Agent 纳入编制评估而非重复创建

## 工作流

进入工作流前先 `TaskCreate` 建立任务清单（步骤 1-6 各一项，含每步产出），推进中用 `TaskUpdate` 标记完成状态，中断恢复时用 `TaskList`/`TaskGet` 读取进度，不凭回忆对齐工作点。

### 步骤 1：复用检索（前置闸，命中即免考古）

先查有没有现成团队可以直接整队接手，禁止跳过本步直接考古设岗：

1. 整队检索：本地 `mindx team list --json` + 市场 `mindx market list --kind team --q "<关键词>"`。检索词必须覆盖需求的全流程词（如「软件研发」「全流程交付」「内容营销」），禁止只搜单个岗位词——岗位词只匹配得到单 Agent，必然漏掉成建制团队
2. 命中契合的现成团队 → 会话内呈现其编制与定位，向用户确认后整队复用（`mindx market install team <name>`），跳到步骤 5 建制——免考古免拆解，团队 Profile 与成员定义已由包自带，不重写不转录
3. 整队无命中 → 进入步骤 2；逐岗位的 Agent 复用检索放到步骤 4，此时岗位清单已定

### 步骤 2：项目考古（派 SubAgent 执行）

考古会读大量文件，**必须派 SubAgent 执行**（检索型子任务只返结论），主上下文只聚合判断。考古维度：

- 技术栈与框架（语言、构建工具、依赖清单）
- 模块划分与目录结构（顶层模块、职责边界）
- git 热区（近 30 天改动集中的模块——活跃度即职责权重）
- 外部接口面（API、数据库、部署方式）
- 现有文档与约定（README、AGENTS.md、规范文件）

考古结论会话内聚合，作为拆解与编制设计的依据，不落盘成持久工件。禁止全量读源码——每个维度抽样即可，结论比细节重要。

### 步骤 3：领域拆解（MECE 检验）

把考古结论拆解为互斥且完备的领域清单：

- **互斥**：任一典型任务有且只有一个明确归属领域——拿一个真实任务对照两个相邻领域，若都说"归我"，重新划界
- **覆盖**：领域并集覆盖项目的主要职责面（以 git 热区与目录结构为准，不为冷代码设岗）

### 步骤 4：编制设计与老板确认（建制前必过）

产出编制清单并在会话内呈现：岗位清单、每个岗位的一句话概览、来源标记（复用/新建）、负责人选定。**用户确认前不创建任何实体**；用户要求调整则修订编制重新确认。

| 岗位 | 职责概览（负责什么/产出什么/什么时候用） | 共享技能 | 独享技能 | 来源（复用/新建） |
| ---- | ---------------------------------------- | -------- | -------- | ----------------- |

- 岗位概览写法（概览三问）按 agent-creator 技能的 references/agent-writing.md 执行。共享技能是全团队一致性的方法论（如代码审查、测试生成、根因调试），独享技能是岗位专有做法（如特定框架开发）——只装配该岗位需要的，每个技能都消耗上下文
- 逐岗位复用检索：本地无对应 Agent 时先 `mindx market list --kind agent --q "<领域关键词>"`，命中即 `mindx market install agent <name>`；无现成的按 agent-creator 技能的单 Agent 工作流从零创建（考古结论此时就是它的领域上下文来源）
- 负责人选定：通常选职责横跨多领域或主导集成度的岗位。leader 岗硬性要求：1 门管理技能（任务拆解/派工/验收类，等价能力可替换）+ 1 门领域手艺技能（能抽查验证成员产出——验收取证由它承担，计划技能不做执行），缺一即空心领导，禁止注册
- 确认后的编制决策记录按 runtime/AGENTS.md 随手记规则落项目 `.agents/notes/`（决策类、轻量：岗位清单、来源、负责人理由）。禁止落 `.agents/plans/` 之类的持久蓝图文档——持久蓝图会被执行期 LLM 当作唯一事实源，盖过 TEAM.md 与成员 IDENTITY/SOUL 的定义，把职责与协作流程锁死在招聘时刻的快照上；职责唯一出处是成员 IDENTITY/SOUL，协作流程唯一出处是 TEAM.md Profile

### 步骤 5：建制

1. 建制前核对：leader 装配清单含 1 门管理技能 + 1 门领域手艺技能（见步骤 4 硬性要求），缺一不建队
2. 全部岗位就位后 `mindx team add <team> --leader <lead> --member ...`
3. Team Profile 写入团队职责与工作区约定（`mindx team update <team> --profile`）：团队职责只写协作流程与任务闸门，工作区约定给每类交接产物落点目录——写法按 references/team-design.md 编制规范第 6-11 条执行；并按约定在本项目根建好目录骨架与 AGENTS.md（目录地图、当前进度、更新规则，接手只读它就能续作）
4. `mindx team hire <team>`
5. 团队头像：从内置库挑一张未占用的图写入 TEAM.md 的 `icon`（成员头像已在各自 IDENTITY.md，团队只配自己那一张）：
   ```bash
   python3 ~/.mindx/assets/bin/pick-avatar.py --group team --target ~/.mindx/teams/<team>/TEAM.md
   ```
   库存耗尽（退出码 2）时停下补充库存，禁止手编 base64。
   派图只在**本机新建团队时**做一次：整队复用市场现成团队（步骤 1 第 2 条）时沿用包内 TEAM.md 自带 icon，不重派、不覆盖

### 步骤 6：交接

向用户汇报：编制清单（谁负责什么）、启动方式（选团队 = 以负责人身份发起会话）、编制决策记录位置。

## 注意事项

- **共享技能宁少勿多**——每个装配的技能都进入该 Agent 的每次会话上下文；判定标准是"没有它会做错"，不是"有了更好"
- **leader 的 SOUL 必须写「估算 + 阶梯派工 + 抽查验证自己动手」**——全文按 references/team-design.md 编制规范第 5 条执行；只收报告不抽查验证、只埋头包揽不派工的 leader 都是空心领导

## 反模式

- **跳过复用检索直接考古设岗** —— 整队检索（本地 + 市场 `--kind team`，全流程词）不跑或检索词只含岗位词，成建制现成团队漏网，重复建制烧双份编制
- **把编制设计落成持久蓝图文档** —— 持久蓝图会被执行期 LLM 当作唯一事实源，无视 TEAM.md 与成员 IDENTITY/SOUL 的既有定义；职责归成员 IDENTITY/SOUL，协作流程归 TEAM.md Profile，编制决策只落 `.agents/notes/` 轻量记录
- **编制未确认就建制** —— 批量创建实体必须先过确认门
- **一个岗位包整个项目** —— 与"能单不多"矛盾：真只需一个 Agent 时不要组建团队
- **全岗位配同一堆技能** —— 共享与独享不分，上下文被无关技能撑爆
- **建完就散** —— 不写 Team Profile、不落工作区约定（产物落点 + 根目录 AGENTS.md）、不做交接汇报，用户不知道团队怎么用，会话一清团队就断档
- **Profile 重述成员职能** —— 成员名单与角色描述由系统自动注入团队提示词（prompt_builder 成员名单区），正文再写一遍就是双份噪声与对号负担；Profile 正文只写协作流程、任务闸门与验收汇报口径
- **调度链写给不在场的人** —— Profile 只注入负责人 SYSTEM_PROMPT（发起方与成员均不可见）：「发起方只对接负责人、不越过负责人直管成员」对负责人是废话且诱导转发器自我定位，写了比没写更差；正文只写约束负责人自己的规则（主理、定档、验收、汇报），受众自检按 references/team-design.md 编制规范第 12 条执行
