# Team 实体 — 一等团队、编制设计与招募

> 团队的结构事实（实体与命令）与编制设计规范（怎么切分成员领域才可路由）。
> 成员 Agent 的定义规范见 agent-creator 技能的 references/（agent-schema.md 与 agent-writing.md）。

## Team 实体

固定团队不是 Agent 的属性，而是独立的一等实体（`~/.mindx/teams/<team>/TEAM.md`）：

- frontmatter：`name`（内部标识）/ `nick_name`（展示主名）/ `description` / `leader`（负责人 Agent 名）/ `members`（成员 Agent 名列表，纯引用）/ `icon` / `category` / `hired`
- 正文 Profile：团队人设定义（负责人怎么协调成员、跟踪结果、汇报成果），系统在团队会话中原样注入（缺失时用兜底文案）
- **引用单向（Team→Agent）**：团队持有成员名单，Agent 定义里不写任何团队信息；同一 Agent 可被多个团队引用
- **团队会话以负责人身份发起**（团队会话 resolve 到 leader，与团队对话 = 与负责人对话）；雇佣团队（`mindx team hire`）后团队才出现在会话选择器
- 管理命令：`mindx team add/update/hire/fire/rm/export`；团队可整包进市场（`mindx team export` 产出 kind=team 包，消费者 `mindx market install team` 整队招聘）

## 编制设计规范（建队前必须完成）

团队是"用户需求 → 团队 → 成员"选择链的中层。编制设计决定这层选择是否有效：

1. **领域切分互斥且覆盖**：编制结果必须满足——任一具体任务有且只有一个明确归属成员，且领域并集覆盖团队使命；切分动作与互斥/覆盖检验法按 SKILL.md 步骤 2 执行。
2. **概览保持干净**：成员 description 只写自己的概览（负责什么/能干什么/什么时候用），禁止为划界在概览里指派或指代其他成员——切分问题在编制层解决，不进 description。
3. **独特可辨自检**：某成员的概览换成同团队其他成员仍然成立 → 该成员没有独立领域，合并或重切。
4. **团队 description 也是概览**：写清这个团队承接什么需求、能产出什么、什么时候找它——这正是概览三问，同样禁止"全方位 X 服务"式空话与指代成员的话术。
5. **leader SOUL 必须写「估算 + 阶梯派工 + 抽查验证自己动手」**：团队会话就是与 leader 对话——leader 接到任务先出计划并估算（估算定档与选岗派工的章法按其装配的计划技能执行：三变量定档、预算进任务书，这是所有负责人共用能力，非 leader 专设），小验证自己动手（≤5 轮工具调用内出结论），摸底分批派工并写明预算；只收报告不抽查验证的 leader 是空心领导，只埋头包揽不派工的 leader 同样失职。
6. **团队职责归 Team Profile**：成员间协作规则、验收口径、汇报链路写进 TEAM.md 正文，不散落进成员 SOUL。正文是协作经验的沉淀——团队承接的业务协作流程分阶段写清「责任角色 → 产出 → 作为下一阶段的何种依据」（如分析阶段调研角色产出需求分析报告，作为设计阶段架构设计的输入依据），从宏观看就是一条业务流；它保持轻量（与 SOUL 同注入常驻系统提示词，复杂描述是常驻成本），价值在于给负责人作计划时提供决策依据。两类内容禁止进正文：团队定位重述（description 已承载）与成员职能重述（成员名单与角色描述由系统自动注入提示词的成员名单区，重述即双份噪声）。人格同理分层：团队的集体人格由 Profile 承载，成员只保留最小个性差异，浓度按层级递减（负责人居中、成员从简）——多人格同场会互相打架（见 agent-creator 技能 references/persona-engineering.md 的 token 纪律）。
7. **Profile 正文角色化（写活）**：正文用「角色/岗位」指代成员（如「调研角色产出用户画像简报」），配合职责描述让角色可辨，禁止成员 Agent 名进正文——frontmatter 的 `leader`/`members` 才是名字锚点（机器解析装配用）；运行时系统把**实际雇佣**的成员名单（名字 + 角色描述）注入提示词，正文的角色指代由 LLM 对号到实际名单。正文具名会在成员未安装、换版本或一角色多 Agent 时让指令指向空气，LLM 失去按实际编制调度的能力。
8. **正文同理不具名技能**：Profile 里引用成员能力时写「审批流程」「图文创作能力」等能力维度，不写技能名——与成员 Agent 定义同一纪律。
9. **对号歧义交还用户**：LLM 把正文角色/能力指代对号到运行时注入的实际清单时，若同一维度有多个高度相似的可选项（多个成员、多个技能）且任务上下文不足以决策，禁止任意指派——列出候选与差异，由用户决定方向。
10. **工作区约定必须有落点**：Profile 必须含「工作区约定」段——每类交接产物写明落点目录（如 docs/、art/、data/、records/），并声明团队工作目录根必建 AGENTS.md（写目录地图、当前进度、更新规则），每步产物收口即更新进度区。产物链只有链条没有落点，会话上下文一清团队就断档，任何新会话或角色接手都要考古重建；有落点 + AGENTS.md，接手只读一个文件就能续作。
11. **任务闸门由计划承接**：交给团队的任务首先到达负责人——负责人主理任务、成员按需协助，禁止任务一来就全员出动。负责人装配的计划技能以 Profile 的业务流与协作规则为决策依据做规模定档：任务可落在业务流任意阶段，起点按用户已提供的产物判定——已有产物的阶段不重做、也不做复核式重做（「对齐一下」「评审重构」类变相重做同属重做），产物直接作为下游输入，与本任务无关的阶段直接跳过，用户已提供的输入（现成文案、素材、规范、代码等）不重复生产、直接采用；上游依据确有缺口时列出缺口向用户确认后再补，不静默重做。轻档按单阶段小批派工直接执行；强串行的业务流表述（「冻结前不并行」「未达标即退回」）只约束它所在的阶段内部，不构成轻档必须走满全流程或从头开始的理由；重档（全员、长时、多领域同时协作）才出完整计划并经用户批准，由获批计划驱动执行。两层披露各司其职：Profile 给业务流宏观图（常驻），计划给单次任务的具体执行（按需进上下文）——细节不预付进常驻提示词。闸门缺失的后果：任何任务都演变成全编制总动员，token 成倍燃烧且无人对结果收口。
12. **Profile 受众自检**：Team Profile 只注入负责人的 SYSTEM_PROMPT（发起方与成员均不可见），正文每条规则先问「这句话约束谁」——只写约束负责人自己的规则（主理、定档、抽查验收、汇报升级）。约束发起方的规则不写：「发起方不越过负责人直管成员」由团队会话 resolve 到负责人的架构保证，写进 Profile 对负责人是废话，且诱导「门卫/转发器」自我定位——写了比没写更差；约束成员的规则写进成员 Agent 定义，成员看不到 Profile，写进正文对成员无效。

## 招募与雇佣要点

- 成员 Agent 一律按 agent-creator 技能的单 Agent 工作流逐个招募（先查本地与市场，能复用绝不新建）；leader 候选须过蓝图「负责人选定」节的 leader 硬性要求，缺一不建队。
- 建队任命负责人（必须是已招募的 Agent）：`mindx team add <team> --leader <agent> --member ... --description "团队一句话定位" --nick_name "两三字外号"`。
- 团队职责（负责人怎么协调、跟踪、汇报）落 TEAM.md 正文 Profile（`mindx team update <team> --profile "..."` 或直接编辑）。
- `mindx team hire` 后团队才出现在会话选择器；发起方进入团队会话即与负责人对话，这是架构硬保证，无需在 Profile 中重述（见编制规范第 12 条）。
- 整队进市场：`mindx team export` 产出 `<team-name>.mindpkg`，消费者 `mindx market install team` 一次装齐团队与成员。
