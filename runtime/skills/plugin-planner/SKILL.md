# 插件规划师

本技能做的是一件简单的事：**需求分析**。从工作细节中反推——当前的工作里，有哪些动态的内容与状态需要让用户了解？用最漂亮的方式，把那些重复的、繁杂的数据呈现出来。这是本技能最重要的使命，下列全部机制都是为它服务的执行手段。

## 核心判据（先记住再动手）

**动态性是根本判据**——值得呈现的是工作中动态的内容与状态：会推进的进度、会流转的状态、会变化的数据。静态的、一次性的信息不值得为它建界面；重复出现、繁杂到人读不过来的数据，才最需要最漂亮的呈现。

**技能被触发，插件被打开。** 技能是给 Agent 的操作指令，插件是给人的交互界面——需求服务人的查看与操作才考虑插件。

**两个承载层，定位不同**：

- **仪表板是轻度方案**——一个 `.dash` 文件即可运行，按文件分析取数，适合美化呈现与汇报。"方便用户了解情况"首选它：用最简单的美呈现最关键的信息，一份会动的汇报胜过一屏表单
- **插件是富交互与富处理方案**——可承载更多规则与数据处理（数据库、Node 运行时皆可），与生态深度绑定。但插件的操作者首先是 Agent：数据修改绝大多数由 Agent 经 RPC 完成，界面以知情呈现为主；只有 Agent 无法处理的业务行为（验收确认、业务裁决、授权）才为用户保留输入协作点。插件处处引导人机协作：界面呈现 Agent 的工作进展与结果，在协作点引导用户介入，让用户随时清楚"Agent 做了什么、哪里需要我"——这是与传统 App 的根本区别，本生态的插件是为此而生的新形式应用

**红线：禁止"要用户输入一群数据才能用"的插件**——用户不做批量录入。数据从生态来（Agent 产出的记录、daemon 数据、项目文件），不从用户手里来。

## 何时使用

- 用户明确要求"做个插件 / 这个功能要有个界面入口"
- 工作中撞见产出需要界面呈现、本地无合用插件，经用户同意引入插件工作后
- 复盘产出插件立项提议
- 工作总结收尾时的例行行为分析（主动开展，不等用户问）

**不使用**：需求缺的是 Agent 能力不是呈现（走 skill-creator 或 agent-creator）；已有插件或仪表板可覆盖（直接推荐用户打开）。

## 工作流

进入工作流前先 `TaskCreate` 建立任务清单（上下文研判 → 行为分析与预判 → 分层方案 → 方向裁决 → 交接各一项，含每步产出），推进中用 `TaskUpdate` 标记完成状态，中断恢复时用 `TaskList`/`TaskGet` 读取进度，不凭回忆对齐工作点。

### 第一步 上下文自动研判（静默执行，零打扰）

并行读取，不向用户提问。工作痕迹都是需求来源，只是置信度与信息价值不同，按类型读取并区别使用：

- `USER.md`（用户画像）→ 行业、角色——场景标配的推断基准
- 当前 Team leader 的 IDENTITY/SOUL → 项目方向
- `.agents/memory/`（复盘提取后的稳定记录，高置信）与 `.agents/notes/`（原始素材，低置信，需佐证）→ 显性需求陈述
- 报告类产出（日报、复盘 report）→ 周期性总结中的反复模式——"本周又在 X 上耗了大量时间"是需求信号
- `.agents/dashboards/` 与已装插件（`mw plugin list --json`）→ 已固化的可视化需求与已有能力，防撞车
- 工作日志（logs）与 TODO.md → 真实行为序列与未决事项——实际做了什么比说了什么更接近真实需求
- `.agents/plans/plugin-charter.md`（历史立项卡）→ 历史裁决：被判"暂不做"的方向不重复提议，除非出现新证据
- 市场货架（`mindx market list --kind plugin --q <关键词>`）→ 社区有没有现成方案（只读检索，静默执行）

### 第二步 行为分析与功能预判（双源）

- **源 A 痕迹取证**：同类呈现需求**跨痕迹独立出现**才立项——不同会话、不同类型的痕迹互为佐证（显性陈述 + 报告反复模式 + 日志行为印证，是置信度递增的取证链）；单一痕迹中的孤证不立项，仅记 notes 待再现
- **源 B 场景标配**：从行业与项目方向推导标配工具，属常识推断**无需用户告知、无需记录证据**——项目开发标配进度跟踪与缺陷管理，内容创作标配稿件管理。标配预判必须落到具体功能："项目管理"不是功能，"带状态流转的缺陷清单 + 按严重度分布的看板"才是
- 每个预判如实标注来源（痕迹取证 / 场景标配），用户裁决时知道依据
- 需求缺的是 Agent 能力不是呈现 → 如实告知并路由 skill-creator / agent-creator，终止
- 已有插件或仪表板可覆盖 → 推荐用户打开，终止
- **市场有现成方案先复用，不闭门造车**——市场检索命中功能对应的插件（描述与需求匹配）→ 用质量信号择优：列表的 D/L（下载量）与 Rating（评分均值+条数）列，或 `--sort downloads` 按下载量排序；下载量大、评分高的货架方案优先推荐安装试用（`mindx market install`）。信号并列或都为零时，描述匹配度定优先级。货架方案不合用或无货才立项自研。换位想：自己是用户，货架上有好货时也会直接拿，不会先想着自己写一个

### 第三步 分层实施方案（对照 references/templates/）

每个预判产出一份方案，按最短路径分层：

- **L1 仪表板方案（最低交付物）**：仅需查看与监控 → 路由 dashboard 技能生成 `.dash`（场景路由见其 references/scene-*.md：项目跟踪、缺陷、需求池、看板、OKR、人力、架构均有现成场景），零开发，落盘即生效
- **L2 插件方案**：需要富处理能力（数据加工、规则引擎、跨源整合）或富交互呈现 → 依据预判模板产出实施方案：插件名、功能清单、席位布局（对照 mx-plugin-dev 的 references/seats.md）、骨架场景、数据来源，并写明三方分工——**Agent 操作面**（哪些数据加工与状态流转由 Agent 经 RPC 完成）、**用户知情面**（界面呈现什么、如何打开即读）、**协作点**（仅限 Agent 无法处理的业务行为，能没有就没有）
- 多方案按用户价值排序，标明各自成本（L1 即刻可用，L2 需开发）
- **行业界面映射**：匹配方案时先查 `references/industry-ui-map.md`（行业 → 高频界面类型 → 承载建议 → 人机协作点），用高频界面语汇校准功能清单，避免发明生僻形态
- **外搜兜底（活口）**：预判命中陌生行业、映射覆盖不了时，上网搜罗该行业当下主流应用的界面类型与人机协作形态（WebSearch），把结论**蒸馏回映射文件**并标注来源与日期——外搜是兜底不是主路径，搜到即沉淀，下次不再搜同一行业

### 第四步 单次方向裁决（建制前必过）

AskUser 一次呈现全部方案，用户对每个方向裁决：采纳 / 调整 / 暂不做。**裁决前不创建任何实体、不写一行代码**；用户要求调整则修订方案重新裁决。裁决结论落 `.agents/plans/plugin-charter.md`（每方案一节：预判来源、分层结论、裁决结果）。

### 第五步 交接

- 采纳的 L1 方案 → 路由 dashboard 技能生成
- 采纳的 L2 方案 → 路由 mx-plugin-dev 施工，方案文件的功能清单与席位布局节直接作为其规格输入，四轮问卷按已定项裁剪
- 本技能不写一行插件代码（单写者原则：规划管"建什么"，开发管"怎么建"）

## 预判模板（references/templates/）

方案产出靠三层结构接力，各层粒度不同：

- **行业语汇层** `references/industry-ui-map.md`——行业 → 高频界面 → 协作点，校准功能清单，不发明生僻形态
- **场景模板层** `references/templates/`——高频场景的完整方案，命中即直接套用：`project-tracking.md`（项目跟踪场景）、`bug-management.md`（缺陷管理场景）
- **组装骨架层** `references/templates/generic-scaffold.md`——未命中场景用 ui-map 语汇 + 最接近模板的结构组装方案，每格必须填实

**棘轮沉淀**：同一场景族的组装方案第二次出现时，固化为正式模板。模板按场景族命名（如 lead-tracking、order-flow），不按行业建模板——行业差异由 ui-map 注入，避免行业×场景的模板爆炸。模板库按真实需求生长，不预写空壳。

## 注意事项

- **研判静默、裁决单次**——上下文读取与预判不问用户，全部方案一次呈现一次裁决，禁止把预判拆成多轮问卷
- **插件面向反复需求**——L2 立项仍需"记录反复出现"或"场景标配"依据，单次奇想记 notes 待再现
- **形态误判宁可折返**——进入预判后发现是能力缺口的，如实告知并路由对应流程，不硬凑成插件

## 反模式

- **逐项问用户要需求**——预判是 Agent 的工作，裁决才是用户的；把 Agent 该做的分析摊给用户是失职
- **要用户填数据才能用**——数据从生态来，不从用户手里来；批量录入界面是红线反模式
- **把领域名当功能**——"项目管理"不是功能，功能必须落到具体交互与数据
- **仪表板能承载的硬上插件**——先 L1 后 L2，插件是升级不是默认
- **跳过裁决直接施工**——方案未裁决不创建任何实体
- **与既有插件/仪表板撞车**——研判第一步就查已装清单

## 重要说明

- **本技能不直接创建插件与仪表板**——施工路由 mx-plugin-dev，仪表板路由 dashboard，本技能负责预判、方案与裁决门。
- **方案文件是唯一交接物**——全部预判依据（双源、分层、裁决）在 `.agents/plans/plugin-charter.md` 可追溯。
