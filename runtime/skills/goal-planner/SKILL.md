# 目标规划

把用户的模糊目标变成可批准执行的完整计划。计划的终点是用户批准；执行方式只是计划里的字段，执行由获批计划载明的执行方承担。账本是 S2 计划的状态事实源，计划正文在计划文件里。

不是所有目标都值得走满五步：先做第零步规模预判，S0/S1 走轻档，S2 才走完整价值链。

价值链五步：**分析需求消解歧义 → 工作分解 → 估算定档 → 选岗与方式 → 提交计划待批准**。

## 何时使用

- 用户下达目标、方向性要求，或说「落实 / 安排 / 推进」
- 需要回答「这事要多少工作量、该派给谁」
- 要求出计划、出方案、要求把几件事排一下

**不使用**：执行获批计划；纯粹的会话内互助（不涉目标，连清单都用不上）；做完之后的经验沉淀（不属本技能，交复盘）。

## 第零步 规模预判（进流程第一件事，决定本次走多重）

先按原话判规模档，档位决定后面走几步。规模档（S）管「流程走多重」，与第三步的任务估算档（0/1/2 档，管「谁来干、给多少轮」）是两套刻度，别混：

| 档 | 判据 | 产出 | 落盘 | 账本 |
| --- | --- | --- | --- | --- |
| S0 清单直答 | 任务 ≤3、无前置依赖、不需要先读材料才知道怎么干 | 直接给任务清单，附一句「这是清单，不是正式计划；要落盘或派人告诉我」 | 不落盘 | 不入账 |
| S1 轻量计划 | 任务 4-8，或存在依赖，由本 Agent 自己干或只派 1 个岗 | 一张表：任务 / 验收 / 依赖 / 预算轮数 / 执行方 | 写 `<项目>/.agents/plans/G-<编号>.md` 简版 | 不入账 |
| S2 完整计划 | 任务 >8 / 要派 ≥2 个执行方（去重计）/ 总预算 >40 轮 / 需用户批准才动手 / 有实质歧义 | 五步全跑，产出完整计划文件与任务书 | 完整计划文件 | 入账 |

- 判据用原话就能判；多条同时命中取最重档
- **交付与批准**：S0 的清单就是交付物，给出即结束；S1 给出表后等用户一句确认再动手；S2 才走第五步正式批准门与账本状态流转
- **强制升档**：S0/S1 期间被问到「要多久、派谁、落到谁头上」，或发现要惊动多个岗、发现真依赖，立即升档并告知用户
- **不许为省事降档**：把任务拆得比实际粗、把没消解的歧义当成已消解，都算造假；拿不准升一档

## 第一步 分析需求，消解歧义（原话 → 意图卡）

从用户原话提炼意图卡四项：收益方与场景 / 成功判据（具体可检查）/ 范围边界（明确不做的事）/ 含糊点。S0 跳过本节直接出清单；S1 只填目标与成功判据两项；S2 四项齐填。

- 原话逐字录入，永远不改写；意图与分解允许修正
- **何时必须澄清**：成功判据不可检查、范围有冲突、资源边界缺失——三者任一命中即问，都齐备不问。此门对 S2 强制；S0/S1 卡住时在回答里一句话带问，不另开 AskUser 流程
- **怎么问**：把含糊点写成一份问清单，在一条消息里并发问完（AskUser 单次只带一问，多问就并发多次），每问附 2-4 个假设选项，禁止拆成多轮问卷；方法论细则（话术分类、判据可检查化转换、停问条件）见 [requirements-clarification.md](references/requirements-clarification.md)，意图卡模板见 [templates.md](references/templates.md)

## 第二步 工作分解（意图卡 → 领域任务清单 + 依赖）

把意图卡拆解为领域任务清单；逐任务回答「怎么干」时暴露的含糊点回第一步补卡，禁止带歧义继续分解；同时理清任务间依赖关系（谁先谁后、谁阻塞谁）。

- **领域名不是任务**——"项目管理"不是任务，"带状态流转的缺陷清单"才是
- 每任务四件套：目标（一句话）/ 验收标准（干成什么样算成）/ 上下文位置（绝对路径）/ 产出与去向（写到哪、给谁看）
- **计划质量三判据**：逐任务有可检查验收、依赖顺序显式标注、用户原话中的约束一条不漏
- 计划文档与任务书成文模板见 [templates.md](references/templates.md)

## 第三步 估算工作量并定档（Token 式，共用章法）

对每个任务估算定档。估算用 **LLM 工作单位**（探测点数、工具调用轮数、上下文体积），禁止按人天/人数换算：

- **三变量**：理解置信度（C1 有权威正本——设计定稿、批准大纲、既定规范 / C2 有歧义待澄清 / C3 模糊需探测）、探测点数量（逐条列名计数，禁拍总数）、成本预算（轮数为主、体积为辅）
- **定档即分配**：按置信度 × 探测点数查表，无表内命中一律取最末行

| 置信度 | 探测点 | 档位 | 预算 |
| --- | --- | --- | --- |
| C1 / C2 | ≤3 | 0 档：自己做 | 6-12 轮 |
| C3 | ≤3 | 0 档：自己做，按清单先探测 | 8-15 轮；探完仍无路径升 1 档报批 |
| C1 / C2 | 4-8 | 1 档：一个岗 | 12-25 轮 |
| C3 | 4-8 | 1 档：一个岗 | 15-30 轮 |
| 任一 | >8 或涉 ≥3 个岗 | 2 档：每批 ≤2 岗 | 分批累加，单批按 1 档口径；总量 >40 轮回第二步再拆 |

- **预算口径**：账本与任务书的主单位是轮数；体积（≈k tokens）只写进任务书作参考。禁止报精确点值
- **档位只管规模，岗由第四步点名**：本表给的是工作量档与轮数，派给哪个执行方一律在第四步按匹配规则确定
- **轻档粗估**：S1 照算预算轮数，但按上表区间取中位粗估、不逐任务列探测点清单；只有 S2 的 0 档任务才强制逐条列名
- **渐进升级**：允许升档，禁止开局全上；全员会战默认禁止，须分批摸底证明确需 + 用户明确批准
- 探测点计数规范、轮数基准表、每轮上下文体积估算方法见 [estimation-method.md](references/estimation-method.md)

## 第四步 选岗并判定执行方式（写进计划的字段，不是执行）

先按第三步档位定谁干，再点名到岗。执行方取自当前上下文（用户点名 > 上下文已载入的分工 > 运行环境提供的清单，后层不得覆盖前层），本技能不枚举专家、不指定查询命令。派单必须点名到具体执行方，写不出名字就不许进计划。

- 0 档 → **自己做**；要跨轮跟踪时用 TaskCreate 建进度清单，清单不等于工作本身
- 1-2 档 → **SubAgent**：按 [dispatch-matching.md](references/dispatch-matching.md) 比对候选的职责描述与能力标签，执行方栏写「执行方 + 命中依据 + 依据来源」，禁止写「相关专家」「对口同事」这类占位
- 长时等待（定时触发、跨天等待、用户不在场）→ **Cron**（工具名 `Cron`，字段填 cron 表达式或 scheduled_at）

派前三问，任一不过就降档自己做：

- **有对口方吗**：按匹配规则比对后零命中即无对口，三出口——自己干 / 先建岗（另起流程）/ 如实报缺口交用户裁决
- **净收益为正吗**：单任务预算 <8 轮不派——子代理装配 10-30k 基础上下文的钱填不平
- **值得断线吗**：派单额外付出派发 1 轮 + 收割 1 轮，只有换来并行（≥2 个无依赖任务同跑）或主会话上下文保护才划算
- **S1 派岗仍要自包含**：轻档不写独立任务书，但派出去的 task 必须写清目标、验收、上下文绝对路径三项——子代理看不到本会话

判据：能当场收结论的不排程；cron 表达式是等待方式，不是排期——计划里不排开工时刻、不画甘特图。

## 第五步 提交计划全文待批准

按 [templates.md](references/templates.md) 产出用户可读的完整计划，落盘到 `<项目>/.agents/plans/G-<编号>.md`（意图卡、计划正文、各任务书同一文件；账本只存状态与指针），再把计划全文呈现给用户批准。任务 ≥3 或有并行组时附 mermaid 依赖图，单任务小计划不画图。**用户批准前不得发生任何执行动作**；用户要求调整则修订重新提交。批准后计划交由其载明的执行方（本 Agent 或所指派的执行方）执行，执行进展由执行方回写账本。

## 账本

位置：`<项目>/.agents/plans/goal-ledger.md`。计划的登记、回顾、核对全部以它为准——不凭记忆，不散落在对话里。

```markdown
## G-20261013-01 <目标标题>
- 状态：待批准
- 原话：<用户原话逐字>
- 收益方与场景：<谁受益，什么场景>
- 成功判据：<可检查>
- 不做：<明确排除>
- 澄清：<问 → 答，一条一行；没问过则省略>
- 计划文件：.agents/plans/G-20261013-01.md
- 分解：
  - [ ] T1 <领域任务> → <执行方>（执行：自己做 / SubAgent / cron 表达式）预算：<N 轮>验收：<标准>
  - 依赖：T2 ← T1
- 批准：<用户批准原话 + 日期>，仅已批准条目有
- 进展：
  - 2026-10-13 <执行方回写，一行一条，倒序追加，不改写历史>
```

- 编号 G-YYYYMMDD-序号，全仓唯一；状态三种：待批准 / 已批准 / 已驳回（含取消）
- **可变与不可变分开**：状态行、任务勾选是可变状态字段，随时改；「原话」永不改写，「进展」只追加——两者别混
- **建账时机**：S2 计划的意图卡成形后立即入账（状态待批准）；后续修订只改收益方、判据、分解。S0/S1 不入账——账本只装需要批准的目标。忘记就如实说，不补写编造
- **「已批准」只能由用户确认后写入**：同时把用户批准原话与日期记进「批准」行，没有这行即视为未批准；驳回与取消须注明原因
- 与 TODO.md 分工：TODO.md 是项目杂项待办，账本只管用户目标的计划登记与批准状态
- 与复盘分工：复盘提出的新目标经用户认可后回到本技能入账
- **解析与核对用脚本**：计划汇总、任务清单、无预算任务检查跑 `scripts/ledger.py`（确定性操作不裸算，用法见 `--help`）
- 账本行只留执行方；命中依据与依据来源写在计划文件的任务书里，账本是索引不是全文

## 注意事项与反模式

- **意图未澄清就分解**——臆测的目标安排是空转
- **带歧义继续分解**——分解中发现歧义必须回第一步补卡，禁止硬编任务
- **依赖不标注**——任务间依赖关系不显式标注，执行方无所适从
- **排时间表**——计划只有依赖顺序与等待方式
- **跳过量化直接派工（S2）**——S2 里没有探测点计数与预算的任务书不得进计划；S1 按区间粗估即可，不适用本条
- **按人天/人数估工作量**——把活当人做是瞎猜
- **开局全员会战**——最高成本最高风险的派工，禁止
- **未批准就执行**——用户没批准计划就动手（含自己先查一轮、先写草稿、建清单当干活）
- **计划夹带执行动作**——计划步预写执行过程是步骤越界
- **小活走全流程**——两三步能说清的事也写意图卡、出任务书、落盘建账，流程成本高于任务本身
- **轻档硬扛重活**——已经要派多个岗、已被追问派谁，还按 S0/S1 不升档，等于回避量化
- **派给「相关专家」**——写不出具体执行方与命中依据就占位，等于把选岗推给执行方现场猜
- **小活派大岗**——预算不到 8 轮还派子代理，装配成本比活本身贵
