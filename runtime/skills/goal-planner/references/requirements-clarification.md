# 需求澄清方法论

把「用户说的一段话」变成「一张可执行的意图卡」。

## 一、用户话术三分类与澄清策略

| 类型 | 特征 | 例 | 策略 |
| --- | --- | --- | --- |
| 方向型 | 只有目标域，无交付物 | "把项目质量搞上去" | 必须澄清：成功判据与范围全缺，先问再动 |
| 任务型 | 有明确交付物 | "给这个项目配个团队" | 逐项核对意图卡四项，缺哪项问哪项 |
| 纠偏型 | 对进行中的工作改要求 | "先别动存储层，优先出迁移方案" | 更新意图卡的范围边界与优先级，其余继承 |

## 二、意图卡四项的填法

1. **收益方与场景**——谁因此受益、在什么场景受益。填不出来说明没听懂目标，回炉澄清。
2. **成功判据**——具体到可检查。转换方法：把状态形容词换成可数指标。
   - 差："变好"、"质量提升"、"用户体验改善"
   - 好："上线后每周至少 X 次"、"全量用例通过率 ≥95%"、"峰值响应 ≤500ms"
   - 用户没给指标时，从用户原话里找隐含参照（"像 XX 那样"= 以 XX 为判据），找不到才进澄清清单
3. **范围边界**——明确"不做的事"。用排除问法自查："这个目标隐含不做哪些事？"
4. **含糊点**——逐条列出理解不一致会导致返工的点，每条写成一句可回答的问题。

## 三、澄清提问规范

- **何时必须问**（三者任一命中）：成功判据不可检查 / 范围边界有冲突 / 资源与时间边界缺失。三者齐备不问。
- **怎么问**：AskUser 单次调用只承载一个问题，因此把全部含糊点写成问清单，在**同一条消息里并发多次 AskUser**，用一轮对话问完；每个问题附 2-4 个贴近上下文的假设选项 + "其他（自由输入）"兜底。禁止一次只问一个再等一轮，把一个清单拆成多轮对话。
- **何时停**：判据可检查、范围无冲突即停；追问"还有别的想法吗"是噪声。
- **不臆测**：含糊点宁可问，不猜。

## 四、失败模式

- 现象：用户说"差不多就这样，去干吧"。原因：把澄清当走过场被用户回推。
  动作：把意图卡四项完整呈现 30 秒确认一遍（不是问问题，是亮理解），用户点头再动。
- 现象：澄清后任务仍然发散。原因：范围边界没写"不做"。
  动作：回意图卡补"不做"清单，从用户原话与优先级排序反推。
- 现象：多轮问卷惹用户烦。原因：拆轮提问。
  动作：全部含糊点合并成一条消息里的并发 AskUser，一轮问清。
