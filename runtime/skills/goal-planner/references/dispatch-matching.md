# 选岗与派单判定

决定「派给谁」和「值不值得派」。两件事都必须落到可复查的依据，不许凭「这活像 XX 专家」的感觉。

本文件不枚举任何执行方、不指定任何查询命令——有哪些人可用由当前会话的上下文决定，不归计划技能管。

## 一、候选执行方从哪来

按优先级取，**后层不得覆盖前层**：

1. **用户点名**——本会话里用户指定的执行方一律照用，用户说了算
2. **上下文已载入的分工**——团队编制、项目约定的负责人、已装配同伴的职责描述、项目说明里写明的岗位
3. **运行环境提供的清单**——环境若有具名执行方查询机制，用它补齐前两层没覆盖的候选；按该环境的方式取，本技能不指定命令
4. **前三层都空**——走第三节的无对口三出口

**为什么要守优先级**：环境清单只是「补齐」，不是「重定义候选池」。清单里没有用户点名的人，不等于那个人不存在；让清单覆盖上下文已知的分工，会把执行派给错的人。

- 领域只作检索入口，用来缩小候选范围，不作规模闸门——同一领域内也会有多岗协作，按领域数判规模会失真
- 规模看「要惊动几个执行方」：数去重后的人数/岗数，不数领域分类数

## 二、任务 → 执行方的匹配

三步，每步都留可复查的痕迹：

1. **提信号**：从任务描述里取动作动词（拆解 / 实现 / 审阅 / 验收 / 迁移 / 写文案 / 配图 / 调研…）+ 对象名词（状态机 / 迁移脚本 / 官网文案 / 插图…），各 1-3 个
2. **比对**：拿候选执行方在上下文里的职责描述、能力标签、触发语，逐项比对上述信号；命中 ≥1 即候选。三层来源的候选一视同仁，只有优先级不同
3. **排序取一**：多候选按命中项数量排序；同分优先取高优先级来源（用户点名 > 上下文分工 > 环境清单），再看职责描述是否覆盖动作

**落笔要求**：执行方栏写「执行方 + 命中依据 + 依据来源」，例如：

```
- 执行方：<执行方>（命中：能力标签「数据库迁移」+ 职责含「迁移脚本回滚」；来源：用户点名）
```

写不出具体执行方就是无对口，禁止写「相关专家」「对口同事」「对应负责人」这类占位——占位进计划等于把选岗推给执行方现场猜。

## 三、无对口的三个出口

没找到能承接的执行方时，按序选一个，并把结论写进计划：

1. **自己干**：降一档，本 Agent 直接做（多数情况下就够了）
2. **先建岗**：能力确实缺且要长期用 → 按运行时的建岗流程新建，属另一条流程，不在本计划内执行
3. **如实报缺口**：一次性需求不值得建岗 → 在计划里写明「无对口执行方，由本 Agent 代做，风险：XX」，交用户裁决

## 四、派单值不值得

派单有三笔固定开销，都来自执行机制本身，不是估计：

| 开销 | 依据 |
| --- | --- |
| 派发 1 轮 + 收割 1 轮 | 子代理异步执行，派发只回执，结果要单独收割 |
| 子代理装配 10-30k 基础上下文 | 每个子代理自带系统提示与角色定义，见 estimation-method 第三节 |
| 任务书 1 轮 | 派单前必须写清目标、验收、上下文位置、预算 |

所以派单换来的**不是省轮数**，是两样东西：**并行**和**主会话上下文保护**。判定顺序：

- **填不平就不派**：单任务预算 <8 轮一律自己做——装配 10-30k 约等于一个 8 轮任务的新增上下文量级（每轮 1-3k），省下的不够付装配钱
- **要并行才优先派**：≥2 个互不依赖的任务同时跑，派单的额外 2 轮被并行收益覆盖
- **要护主上下文才派**：任务需大量读文件或跑长命令（主会话体积会被撑大），派出去让子代理吞掉

## 五、失败模式

- 现象：任务书写「派给相关专家」。原因：没比对上下文，凭印象填空。
  动作：按第二节拿候选的职责描述与能力标签比对，落笔写清依据与来源；比对不到写无对口。
- 现象：技能里跑了个清单命令，结果团队里本来有更合适的人没被选中。原因：让环境清单覆盖了上下文已知的分工。
  动作：回第一节优先级链，用户点名与上下文分工优先于清单。
- 现象：5 轮的小活派了个子代理，回来还要整合。原因：只看了「有没有对口的人」，没算装配成本。
  动作：先过第四节「填不平就不派」，<8 轮自己做。
- 现象：派出去 3 个人，结果互相等对方的产出。原因：依赖没在计划里标。
  动作：回第二步补依赖图，无依赖的才并行派。
