# Token 式工作量估算方法论

估算工作量只用 **LLM 工作单位**：探测点数、工具调用轮数、上下文体积。禁止把工作当人做换算人数、人天、工时。

## 一、三变量

### 1. 理解置信度（C 级）

| 级 | 判据（信号清单） |
| --- | --- |
| C1 | 目标有权威正本（spec/PRD/批准大纲/既定规范，领域不限）；口径有文档可查；执行者读完材料即可动手 |
| C2 | 方向明确但有歧义点待澄清；口径分散在多处需对齐；有参考样例但不完全对应 |
| C3 | 只有目标没有路径；需要探测探明现状；关键可行性未验证（技术可行性、事实可考性、风格可行性均属此级） |

### 2. 探测点数量（N）

一个探测点 = 一次「查证动作」：开读一个文件 / 实测一个接口 / 核对一处口径 / 跑一次构建测试 / 问一个只有特定人能答的问题。

计数规范：
- **逐条列名**，写成清单（"读 daemon.log 定位 182 次调用的分布"、"实测 /ws 断线重连"、"核对 token_usages 记账口径"），禁止只写总数
- 同类且相邻的查证（同目录批量读文件）算 1 个探测点，不按文件数翻倍

### 3. 成本预算（B）

B（轮数）≈ Σ 各探测点轮数 + 汇总写作 1-2 轮（见轮数基准表）。
B（上下文体积）≈ 每轮体积 × 轮数（见体积估算节）。

## 二、轮数基准表

探测点类型按动词定义，不按领域定义——任何领域的探测点都应能归入五类之一：

| 探测点类型 | 定义（领域无关） | 典型轮数 |
| --- | --- | --- |
| 读取与核对 | 打开并核对既有材料（代码文件/设计文档/行业报告/原始数据） | 1-2 |
| 定向检索 | 在既有信息源中定位特定内容（代码检索/文献检索/市场与竞品数据检索） | 2-3 |
| 实测/试做 | 亲手做一个最小验证动作（跑接口/试写样章/试发问卷/试做访谈/试算数据） | 2-4 |
| 口径核对 | 对齐多个对象间的一致性（模块间口径/术语风格/多家数据源口径） | 2-3 |
| 汇总成稿 | 把结论写成正式产出（结论写作/章节成稿/调研报告） | 1-2 |

探测点归不进五类时：按最相邻类型取先验 + 第一个任务实测校准——列名计数照常，禁止因领域陌生退回拍总数。

表值是**分解后子任务**的先验（完整任务求解的实测中位标尺见第六节实证依据）；拆分纪律：单任务预算超 ~40 轮即与业界完整任务同量级，说明拆分不足，回第二步再拆。

**档位预算的算法**：B = Σ各探测点轮数 + 汇总写作 1-2 轮 + 返工余量 1 轮。按此式算出的区间与 SKILL.md 第三步定档表一一对应（表内数字即本式的区间端点，改一处必须同步另一处）：

| 探测点数 | 中位（每点 2 轮） | 最坏（每点 4 轮） |
| --- | --- | --- |
| 3 | 3×2+2+1 = 9 | 3×4+2+1 = 15 |
| 8 | 8×2+2+1 = 19 | 8×4+2+1 = 35 |

定档表取中位到最坏的可用区间：0 档 6-12 轮（C3 小任务 8-15）、1 档 12-25 轮（C3 中任务 15-30）、2 档单批按 1 档口径累加。**禁止写出低于中位的上限**——那会让闸门每轮误报。

## 三、每轮上下文体积估算

每轮消耗 ≈ 基础会话 + 当轮新增（历史不可变，只新增可省）：

- 基础会话：系统提示 + Agent 定义（IDENTITY+SOUL）+ 装配技能全文 ≈ 10-30k tokens（技能多的 Agent 取高值）
- 当轮新增：文件读取 1-3k /篇、命令输出 0.5-2k /次、代码生成 1-5k /次
- 任务总消耗 ≈ Σ(基础会话 + 各轮新增)；多轮任务的基础会话被 KV 缓存化解（纸面大头不等于账单大头），**真金白银主要花在每轮新增与输出**——压预算先压轮数、再压单轮体积
- **派单是双份基础会话**：主会话一份 + 每个子代理各一份 10-30k，派 N 个岗就是 N+1 份。所以派单的账面成本高于「自己做」同等工作量，只有换来并行或主会话上下文保护才划算（判定见 [dispatch-matching.md](dispatch-matching.md) 第四节）

## 四、预算落盘与闸门

- 预算写进任务书：「预算：≤N 轮 / 约 Xk tokens」+ 探测点清单；账本的任务行只记轮数（脚本按轮数解析），体积只进任务书。无预算的任务书不得下发
- 同一任务天然波动可达 30×（见第六节）——预算按中位估、余量按波动留，禁止报精确点值
- 执行中超预算：先收已有结论再决策下一步，禁止顺手多跑几轮（多跑不提升成功率，实证同第六节）
- 收尾核对：实际消耗（token_usages 记账）同时对照轮数与 tokens 两栏，任一栏偏差大说明估算方法要修——把偏差记进进展行，连续偏差 ≥2 次重校基准表

## 五、失败模式

- 现象：估算只写"大概 10 轮"。原因：没列探测点。
  动作：退回列名清单，轮数从清单推。
- 现象：预算总被超。原因：漏算汇总轮与返工轮。
  动作：基准表 +1 轮返工余量；连续偏差 ≥2 次重校基准表。
- 现象：按"这活要 2 个人 3 天"报工作量。原因：人类思维惯性。
  动作：重算——列探测点、数轮数，换算成人天只会误导用户决策。

## 六、实证依据（论文摘要级引用，数字取整，链接未逐条复核——沿用作档位依据前先抽验一条）

- **智能体任务的成本结构**：500 个 SWE-bench 任务 × 每任务 4 次独立运行实测——单任务平均约 4M tokens、约 $1.9；智能体任务比单轮推理/对话贵约 1000×，**输入侧而非输出侧驱动成本**（https://arxiv.org/abs/2604.22750）→ 支撑「压预算先压轮数再压单轮体积」与基础会话常驻体积的估算结构
- **同任务波动与多跑无益**：同一任务多次运行总 tokens 可差 30×，且更多 tokens 不转化为更高准确率——难题反而输入越多准确率越低（https://arxiv.org/abs/2604.22750）→ 支撑预算留余量不报点值、「超预算先收结论再决策」
- **轮次中位数标尺**：5 个领先 Agent 完整求解一个 SWE-bench 实例的中位轮次 41-58 轮，复杂任务超 175 轮；无轮控时生成补丁均值 $5.85（https://arxiv.org/html/2510.16786）→ 支撑拆分纪律与档位轮数只适用于子任务
- **成本模型三输入**：估算须实测——平均输入 tokens/请求（系统提示+历史+消息+检索上下文）、平均输出 tokens/请求（从 ≥100 条真实请求测量，禁止拍脑袋）、请求量（https://codelint.dev/blog/llm-cost-calculator-complete-guide）→ 支撑 B = 轮数 × 每轮体积的结构与「实测优先于先验」。注：此条为个人博客级来源，仅作结构参考，不当权威数字用
- **闸门的经济性**：智能体会话成本 $0.003-$0.32+ 区间，贵在失控的循环而非任务本身（https://repost.aws/articles/ARUnVD5kbTTQG0GbpZh1cueQ）→ 支撑预算闸门与渐进升级纪律
- **缓存化解纸面大头**：主流供应商缓存读取价 ≈ 输入价 2.5%（https://octomind.run/blog/llm-api-pricing-comparison）；与本地计费实测互证（19M 纸面 tokens 96% 缓存命中仅 $0.11）→ 估算盯「新增与输出」，不盯纸面总量
