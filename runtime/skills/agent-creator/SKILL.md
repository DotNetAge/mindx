## 何时用

- 当用户说"我需要一个 XXX 专家"、"我需要一个懂 XXX 的人"、"为 XXX 创建一个智能体"
- 当处理某项专业领域中的工作，但没有现有智能体合适
- 复盘产出的招募提议（deep-review E 路，用户已裁决）由本技能执行招募——提议三条件校验在复盘侧完成，本技能照常走"先复用后创建"与概览验证

已有合适智能体（Agent）时**不要使用**。

## 先判定：招募 Agent 还是团队

本技能覆盖两类产出：单个 Agent 与成建制团队。动手前先按目标形态判定走哪条路：

| 信号                                                                                   | 判定                                           |
| -------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 目标落在单一领域，一个角色可独立交付（"我需要一个代码审查员"）                         | 招募单个 Agent                                 |
| 目标拆解后子任务分属 ≥2 个互斥领域，且需要交接、集成或并行推进（如"把这个产品做出来"） | 组建团队                                       |
| 同类多领域工作会成建制反复出现（"以后这类项目都这么干"）                               | 组建团队（一次编制，重复驱动）                 |
| 单一领域但量大且重复                                                                   | 单个 Agent + Cron 定时驱动即可，不需要团队编制 |
| 用户明确要求"一个团队 / 部门"                                                          | 组建团队                                       |

原则：**能单不多**——团队等于多个 Agent 加编制与协调开销，只在协作必要或复用明确时成立。判定为团队后先读 [team-design.md](references/team-design.md) 的编制设计规范再动手；判定为单个 Agent 则按下方工作流推进。

## 指导原则：先提供假设选项

采用AskUser工具向用户收集信息。收集信息时，不要直接问开放式问题。应该这样做：

1. **解读用户意图**，生成 2-4 个具体的假设选项
2. **呈现选项**，让用户选择或完善
3. 所有选项都不合适时，再提出开放式问题

**示例**：如果用户说"我需要一个项目经理"，回应：

> 我可以创建一个项目管理智能体。哪种类型最合适？
>
> - **软件项目经理** — 管理开发冲刺、任务跟踪、敏捷工作流和团队协调
> - **建筑项目经理** — 监督建筑项目、时间表、资源分配和合规性
> - **营销活动经理** — 规划和执行营销活动、跟踪 KPI、管理内容日历
> - **其他** — 描述你的具体需求
>
> 或者你有其他想法？

以下所有数据收集都采用这种方法。这样可以减少来回沟通，帮助用户更快明确需求。

## 前提条件：收集所需信息

继续之前，先确认是否已收集所有必要信息。如果有不清楚或缺失的项目，用上述假设选项方法与用户澄清。

- **(a) 名称**：小写连字符，基于名词，反映角色（`python-programmer`、`code-reviewer`）
- **(b) 角色与描述**：role 为中文头衔；description 为 1-2 句中文**概览**——只写负责什么、能干什么、什么时候用，禁止路由指派与技术细节（详见 [agent-writing.md](references/agent-writing.md)）。可选昵称（nick_name，2-3 字展示主名）创建时经 `--nick_name` 一并设置
- **(c) 业务分类**：中文 category，如"产品研发"、"办公提效"
- **(d) 角色职责（SOUL）**：负责什么、怎么工作、不做什么——三段式（职责→方式→边界）+ 三要素规则 + 价值观排序 + 两层边界（编写规范见 [agent-writing.md](references/agent-writing.md)）
- **(e) 所需技能**：`mindx skill list --json` 查看可用技能后预选；技能是 LLM 操作指令，保持精简
- **(f) 排除的工具**：`exclude_tools` 按角色裁剪内置工具（决策树见工作流步骤 4）
- **(g) MCP 白名单**：需要外部服务时列 `allows_tools`（`mcp:<server>`）；空 = 不注入

> 用户描述模糊时，不要盲目猜测，提出具体的角色类别让他们选择。

## 智能体定义速览

智能体以目录格式存储（`agents/<name>/`）：`IDENTITY.md`（frontmatter 强类型元数据 + 正文惯例留空）+ `SOUL.md`（角色职责正文，原样注入提示词）。完整字段表见 [agent-schema.md](references/agent-schema.md)；编写规范与示例见 [agent-writing.md](references/agent-writing.md)。

## 工作流

### 步骤 1：本地与市场双重检索（先复用，后创建）

```bash
mindx agent list --all --json
mindx market list --kind agent --filter "<领域关键词>"
mindx market list --kind team --filter "<领域关键词>"
```

注意：`agent list` 默认只显示已雇佣的智能体，查重时**必须加 `--all`**。

按以下顺序决策，**能复用绝不新建**：

1. **本地已有**相同名称或领域重叠的智能体 → 通知用户并停止，让用户决定是否创建不同角色
2. **市场已有**匹配的 Agent 包 → 呈现匹配项让用户选择：安装雇佣（`mindx market install agent <name>` + `mindx agent hire`，跳到步骤 8，流程结束）；接近但不完全契合 → 询问安装后定制还是从零创建
3. **市场已有**匹配的团队包（成建制协作需求优先）→ 整队招聘 `mindx market install team <name>`，流程结束
4. 两边都没有 → 继续从零创建

### 步骤 2：审查编写规范

编写之前，阅读 [agent-schema.md](references/agent-schema.md)（字段与结构事实）与 [agent-writing.md](references/agent-writing.md)（description 与 SOUL 编写方法论）。市场清单输出自带同类 Agent 的 role/description/skills 组合，可参照目标 `category` 下的既有条目把握命名与描述风格。

### 步骤 3：配置技能（本地 → 市场 → Web 检索，三级找齐）

```bash
mindx skill list --json
```

- 只选择**实现智能体所需行为**的领域相关技能，最多 2-3 个（每个技能都消耗上下文）
- **本地缺所需技能时**，按 `skill-search` 技能查找与安装（先本地后市场，市场命中直接安装、热重载生效）
- **本地与市场都没有时**，先 WebSearch 检索该领域的现成方案，三条出路按序尝试：
  1. **找到现成 CLI 或公开技能规范** → 规划匹配的技能（同类能力归并为一个，守住 2-3 上限），路由 `skill-creator` 走创建流程生成并落位 `.agents/skills/`，完成后回本步骤装配——本技能不直接编写 SKILL.md（单写者原则）
  2. **找到合适的 MCP 服务** → 不造技能，列入 `allows_tools`（见步骤 4）
  3. **检索后确实没有** → 告知用户该能力暂缺，宁缺毋滥，禁止硬凑不相关技能

### 步骤 4：确定工具裁剪方案

根据角色确定 `exclude_tools` 与 `allows_tools`（字段细节见 [agent-schema.md](references/agent-schema.md)）：

- **管理者角色**（协调他人）：保留 SubAgent、CollectResults；需要运行期组队时在 `include_tools` 列出 Team* 工具
- **工作者角色**：排除 SubAgent、CollectResults（不委派）；常见追加 Sleep、PowerShell
- **工程师角色**：保留 Bash 用于构建和测试
- 需要外部服务时在 `allows_tools` 列出 MCP 服务；不写则不注入

### 步骤 5：创建智能体

```bash
mindx agent add <agent-name> \
    --role "中文角色头衔" \
    --description "1-2 句中文职责描述" \
    --nick_name "两三字外号" \
    --skills "skill1,skill2"
```

命令会生成目录（`IDENTITY.md` + 空 `SOUL.md`），新智能体**默认未雇佣**。

### 步骤 6：补全定义文件

- **IDENTITY.md**：补充 `category`、`exclude_tools`、`allows_tools` 等字段；正文惯例留空
- **SOUL.md**：按 [agent-writing.md](references/agent-writing.md) 编写角色职责（三段式、三要素、价值观排序、两层边界、按需退化行为与自检清单）

### 步骤 7：概览选择验证（行为面验收）

注册面验证（hire + list）只能证明"存在"，不能证明"会被选对"。雇佣前做一次概览选择测试：

1. 写 3-5 个典型任务表述（模拟用户真实说法）+ 1-2 个**不该派给它**的相邻任务
2. 派一个 SubAgent 模拟选择者：同时阅读 `mindx agent list --json` 中多条 Agent 的概览，为每个任务挑一个 Agent——禁止自己写自己验
3. 典型任务没选中它 → 概览的"负责什么/能干什么"不清晰，回改自己的概览；不该接的任务选中了它 → 概览"什么时候用"含混，回改自己的概览。修补只落在自己的概览内，禁止写指派他人的文本
4. 若两个相邻 Agent 的概览并排仍难区分 → 这是编制层切分问题：改双方概览的领域限定词与产出物使其可辨，或合并角色

### 步骤 8：雇佣并验证

```bash
mindx agent hire <agent-name>
mindx agent list --json
```

- `hire` 后智能体才可用于会话、`/agent` 切换与定时任务
- 验证已出现在雇佣列表中，并用 `mindx agent get <name>` 复查最终配置

后续调整可用 `mindx agent update --agent-name <name>` 修改 role/description/skills/exclude-tools 等字段，角色职责直接编辑 `SOUL.md`。

## 团队招募

经过"先判定"确认目标需要成建制协作后，为其组建团队。团队是**独立的一等实体**（`~/.mindx/teams/<team>/TEAM.md`）：任命负责人（leader）、引用成员、持有独立的团队 Profile；团队会话以负责人身份发起，由负责人协调成员。

**建队前先过编制设计规范**（[team-design.md](references/team-design.md)）：成员领域切分互斥且覆盖、概览保持干净不写指派（切分问题在编制层解决）、团队 description 就是概览三问、leader 的 SOUL 必须写协调职责。

1. **拆解领域**：与用户确认团队要覆盖的领域清单，每个领域对应一位成员——按编制规范检验互斥与覆盖后再动手
2. **逐领域招募**：每位成员按「工作流」步骤 1-8 招募——先查本地与市场，能复用绝不新建
3. **建队与雇佣**：`mindx team add <team> --leader <lead-agent> --member ...`，团队职责写 Team Profile，`mindx team hire` 后出现在会话选择器
4. **驱动与验收**：跨 Agent 的工作安排通过 Cron 定时驱动负责人主导——调度链保持"发起方 → 负责人 → 成员"，发起方不越过负责人直管成员

整队进市场（`mindx team export` / `mindx market install team`）等细节见 [team-design.md](references/team-design.md)。

## 注意事项与反模式

- **能复用绝不新建** — 跳过本地与市场双重检索就动手是造轮子；查重必须 `agent list --all`（默认视图只显示已雇佣）。
- **新建默认未雇佣** — `agent add` 与 `market install agent` 落地均为 `hired: false`，忘记 `mindx agent hire` 就永远不出现在会话列表。
- **技能贪多与硬凑** — 5 个技能可能消耗 80% 上下文窗口，最多 2-3 个；找遍本地、市场与 Web 检索都没有合适方案才告知暂缺，禁止塞不相关技能。冲突指令的技能会让 LLM 不可预测地切换。
- **概览写成路由或含混不清** — description 里塞"归谁/不归谁"的指派是指代噪声，LLM 并列对比时只会被干扰；概览只写负责什么、能干什么、什么时候用。
- **跳过概览选择验证** — 只做注册面验证（hire 后出现在列表），选错人要到任务被错派时才暴露。
- **规则写成空泛口号** — 缺触发场景与理据的职责（"保证质量""输出专业"）不产生行为约束；SOUL 写成能力清单同理。
- **通用智能体** — "我是一个有用的助手"毫无意义，每个智能体应有特定领域、视角和约束。
- **技能够用却创建智能体** — 需要可重用指令就创建技能，需要硬边界角色才创建智能体。

## 重要说明

- **所有字段都供 LLM 使用，除非另有说明。** 写得清晰精确，模糊描述会导致错误路由。
- **技能是操作指令**，告诉 LLM 表现什么行为，不是给用户的功能开关。
- **提开放式问题前先提供选项。** 这样交互更快，也能帮助用户厘清需求。
