# 招募智能体

为需求配上一个能干这活的单个智能体：先复用，复用不了再创建。

## 何时使用

- 当用户说"我需要一个 XXX 专家"、"我需要一个懂 XXX 的人"、"为 XXX 创建一个智能体"
- 当处理某项专业领域中的工作，但没有现有智能体合适
- 复盘产出的单个 Agent 招募提议由本技能执行招募——提议三条件校验在复盘侧完成，本技能照常走"先复用后创建"与概览验证

已有合适智能体时**不要使用**；目标需要成建制团队时走 team-creator。

## 先判定：单个 Agent 还是团队

| 信号                                                                                   | 判定                                           |
| -------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 目标落在单一领域，一个角色可独立交付（"我需要一个代码审查员"）                         | 单个 Agent，按下方工作流推进                   |
| 目标拆解后子任务分属 ≥2 个互斥领域，且需要交接、集成或并行推进（如"把这个产品做出来"） | 组建团队 → 走 team-creator                     |
| 同类多领域工作会成建制反复出现（"以后这类项目都这么干"）                               | 组建团队 → 走 team-creator（一次编制，重复驱动） |
| 单一领域但量大且重复                                                                   | 单个 Agent + Cron 定时驱动即可，不需要团队编制 |
| 用户明确要求"一个团队 / 部门"                                                          | 组建团队 → 走 team-creator                     |

原则：**能单不多**——团队等于多个 Agent 加编制与协调开销，只在协作必要或复用明确时成立。

## 指导原则：先提供假设选项

用 AskUser 收集信息时禁止直接抛开放式问题：先解读用户意图生成 2-4 个具体假设选项供用户选择，全部不合适再开放提问。

> "我需要一个项目经理"的回应示例：
>
> - **软件项目经理** — 管理开发冲刺、任务跟踪、敏捷工作流与团队协调
> - **建筑项目经理** — 监督施工进度、资源分配与合规
> - **营销活动经理** — 策划执行营销活动、跟踪 KPI 与内容日历
> - **其他** — 描述你的具体需求

## 前提条件：收集所需信息

继续之前确认以下信息齐备，缺项用假设选项法澄清：

- **(a) 名称**：小写连字符，基于名词，反映角色（`python-programmer`、`code-reviewer`）
- **(b) 角色与描述**：role 为中文头衔；description 为 1-2 句中文概览（负责什么/能干什么/什么时候用，写法见 [agent-writing.md](references/agent-writing.md)）。可选昵称（nick_name，2-3 字展示主名）创建时经 `--nick_name` 一并设置
- **(c) 业务分类**：中文 category，如"产品研发"、"办公提效"
- **(d) 角色职责（SOUL）**：负责什么、怎么工作、不做什么——三段式（职责→方式→边界）+ 三要素规则 + 价值观排序 + 两层边界（编写规范见 [agent-writing.md](references/agent-writing.md)）；面向用户的角色再做人格工程（见 [persona-engineering.md](references/persona-engineering.md)）
- **(e) 技能与工具预选**：覆盖职责的技能、按角色裁剪的 `exclude_tools`、需要时的 `allows_tools` MCP 白名单——装配细则在工作流步骤 3-4

## 工作流

进入工作流前先 `TaskCreate` 建立任务清单（步骤 1-8 各一项，含每步产出），推进中用 `TaskUpdate` 标记完成状态，中断恢复时用 `TaskList`/`TaskGet` 读取进度，不凭回忆对齐工作点。

### 步骤 1：本地与市场双重检索（先复用，后创建）

```bash
mindx agent list --all --json
mindx market list --kind agent --filter "<领域关键词>"
```

注意：`agent list` 默认只显示已雇佣的智能体，查重时**必须加 `--all`**。

按以下顺序决策，**能复用绝不新建**：

1. **本地已有**相同名称或领域重叠的智能体 → 通知用户并停止，让用户决定是否创建不同角色
2. **市场已有**匹配的 Agent 包 → 呈现匹配项让用户选择：安装雇佣（`mindx market install agent <name>` + `mindx agent hire`，跳到步骤 8，流程结束）；接近但不完全契合 → 询问安装后定制还是从零创建
3. 两边都没有 → 继续从零创建

### 步骤 2：审查编写规范

编写之前，阅读 [agent-schema.md](references/agent-schema.md)（字段与结构事实）与 [agent-writing.md](references/agent-writing.md)（description 与 SOUL 编写方法论）；目标是秘书、负责人、面向用户的专家或市场上架的 Agent 时，加读 [persona-engineering.md](references/persona-engineering.md)（人格工程），内部工具型跳过。市场清单输出自带同类 Agent 的 role/description/skills 组合，可参照目标 `category` 下的既有条目把握命名与描述风格。

### 步骤 3：配置技能（先过职责-能力对齐门，再三级找齐）

**职责-能力对齐门（选技能前必过）**：技能配比先对齐职责再谈预算。从步骤 (d) 的职责草稿列出该角色的核心职责动作（拆解、编码、审阅、验收、汇报…），逐个回答「哪个技能覆盖它」：

| 核心职责动作 | 覆盖技能 |
| ------------ | -------- |

- 有动作无技能覆盖 → 按下文三级检索补齐；检索后确实没有 → 回改职责草稿收窄该动作，或如实告知用户能力缺口由用户裁决，禁止带着缺口过门
- 管理者角色（协调他人）的「目标拆解、派工规划」动作默认由计划规划类技能（目标拆解、估算定档、选岗派工）覆盖——编制管理者/负责人时先核对该装配，缺即带缺口过门；等价能力可替换

过门后按本地 → 市场 → Web 检索三级找齐：

```bash
mindx skill list --json
```

- 只选择**实现智能体所需行为**的领域相关技能，最多 2-3 个（每个技能都消耗上下文）
- **本地缺所需技能时**，按 `skill-search` 技能查找与安装（先本地后市场，市场命中直接安装、热重载生效）
- **本地与市场都没有时**，先 WebSearch 检索该领域的现成方案，三条出路按序尝试：
  1. **找到现成 CLI 或公开技能规范** → 规划匹配的技能（同类能力归并为一个，守住 2-3 上限），路由 `skill-creator` 走创建流程生成并落位 `.agents/skills/`，完成后回本步骤装配——本技能不直接编写 SKILL.md（单写者原则）
  2. **找到合适的 MCP 服务** → 不造技能，列入 `allows_tools`（见步骤 4）
  3. **检索后确实没有** → 告知用户该能力暂缺，宁缺毋滥，禁止硬凑不相关技能

### 步骤 4：确定工具裁剪方案

根据角色确定 `exclude_tools` 与 `allows_tools`（字段细节见 [agent-schema.md](references/agent-schema.md)）：

- **管理者角色**（协调他人）：保留 SubAgent、CollectResults；需要运行期组队时在 `include_tools` 列出 Team* 工具
- **工作者角色**：排除 SubAgent、CollectResults（不委派）；常见追加 Sleep、PowerShell
- **工程师角色**：保留 Bash 用于构建和测试
- 需要外部服务时在 `allows_tools` 列出 MCP 服务；不写则不注入

### 步骤 5：创建智能体

```bash
mindx agent add <agent-name> \
    --role "中文角色头衔" \
    --description "1-2 句中文职责描述" \
    --nick_name "两三字外号" \
    --skills "skill1,skill2"
```

命令会生成目录（`IDENTITY.md` + 空 `SOUL.md`），新智能体**默认未雇佣**。

### 步骤 6：补全定义文件

- **IDENTITY.md**：补充 `category`、`exclude_tools`、`allows_tools` 等字段；正文惯例留空
- **SOUL.md**：按 [agent-writing.md](references/agent-writing.md) 编写角色职责（三段式、三要素、价值观排序、两层边界、按需退化行为与自检清单）；面向用户的角色按 [persona-engineering.md](references/persona-engineering.md) 长入人格要素并过人格质量门

### 步骤 7：概览选择验证（行为面验收）

注册面验证（hire + list）只能证明"存在"，不能证明"会被选对"。雇佣前做一次概览选择测试：

1. 写 3-5 个典型任务表述（模拟用户真实说法）+ 1-2 个**不该派给它**的相邻任务
2. 派一个 SubAgent 模拟选择者：同时阅读 `mindx agent list --json` 中多条 Agent 的概览，为每个任务挑一个 Agent——禁止自己写自己验
3. 典型任务没选中它 → 概览的"负责什么/能干什么"不清晰，回改自己的概览；不该接的任务选中了它 → 概览"什么时候用"含混，回改自己的概览。修补只落在自己的概览内，禁止写指派他人的文本
4. 若两个相邻 Agent 的概览并排仍难区分 → 这是编制层切分问题：改双方概览的领域限定词与产出物使其可辨，或合并角色

### 步骤 8：雇佣并验证

```bash
mindx agent hire <agent-name>
mindx agent list --json
```

- `hire` 后智能体才可用于会话、`/agent` 切换与定时任务
- 验证已出现在雇佣列表中，并用 `mindx agent get <name>` 复查最终配置

后续调整可用 `mindx agent update --agent-name <name>` 修改 role/description/skills/exclude-tools 等字段，角色职责直接编辑 `SOUL.md`。

## 注意事项与反模式

- **能复用绝不新建** — 跳过本地与市场双重检索就动手是造轮子；查重必须 `agent list --all`（默认视图只显示已雇佣）。
- **新建默认未雇佣** — `agent add` 与 `market install agent` 落地均为 `hired: false`，忘记 `mindx agent hire` 就永远不出现在会话列表。
- **技能配比只谈上限不谈对齐、贪多硬凑** — 最多 2-3 个是预算约束，先过职责-能力对齐门再谈预算；找遍三级检索都没有才告知暂缺，禁止塞不相关技能。
- **纯派发型管理者** — 职责只有「拆解→派发→收报告」而无任何自己动手动作（估算定档、抽查验证成员产出、亲自验收关键交付）的编制是空心 Agent；管理岗必须保留可核验的自己动手环节，缺手艺支撑禁止注册。
- **概览写成路由或含混不清** — description 只写负责什么、能干什么、什么时候用；指派话术是并列对比的噪声。
- **跳过概览选择验证** — 只做注册面验证（hire 后出现在列表），选错人要到任务被错派时才暴露。
- **规则写成空泛口号** — 缺触发场景与理据的职责（"保证质量""输出专业"）不产生行为约束；SOUL 写成能力清单同理。
- **通用智能体** — "我是一个有用的助手"毫无意义，每个智能体应有特定领域、视角和约束。
- **技能够用却创建智能体** — 需要可重用指令就创建技能，需要硬边界角色才创建智能体。
