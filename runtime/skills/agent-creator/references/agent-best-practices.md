# Agent定义最佳实践

智能体以**目录格式**存储（`agents/<name>/`），由两个文件组成：

```text
agents/<name>/
  IDENTITY.md   # 唯一 meta 入口：frontmatter（强类型一级字段）+ 可选身份正文
  SOUL.md       # 角色职责与负责范围，纯正文
  skills/       # Agent 级技能库（可选，由技能系统装载）
```

- **IDENTITY.md** 是身份卡：frontmatter 承载全部路由元数据；正文惯例留空。
- **SOUL.md** 是角色职责：Agent 的核心工作指令，自带标题结构，系统原样注入提示词。

> 团队是独立的一等实体（`~/.mindx/teams/<team>/TEAM.md`，frontmatter：name/nick_name/description/leader/members/icon/category/hired + 正文 Profile），不在 Agent 目录内；组队语义见下文"团队实体"节。

## IDENTITY.md frontmatter 字段

| 字段            | 格式                     | 规则                                                                 |
| --------------- | ------------------------ | -------------------------------------------------------------------- |
| `name`          | 小写连字符               | 唯一，基于名词，体现角色（如 `code-reviewer`）                       |
| `role`          | 中文头衔                 | 人类可读的角色标题（如"代码审查员"）                                 |
| `description`   | 1-2 句中文               | 用于 **LLM 路由** 与列表展示 —— 写清负责什么、产出什么               |
| `category`      | 中文业务分类             | 分组展示用（如"产品研发"、"办公提效"、"市场营销"）                   |
| `icon`          | 可选                     | 图标标识                                                             |
| `hired`         | 布尔，缺省 false         | 雇佣标记；新建智能体默认未雇佣，`mindx agent hire` 后才可用于会话    |
| `skills`        | 来自 `skill list` 的列表 | 仅领域相关技能 —— 每个技能都会增加上下文开销                         |
| `exclude_tools` | 列表                     | 内置工具裁剪清单；内置工具默认全量可用，按需排除，不支持通配符       |
| `allows_tools`  | 列表                     | MCP 服务白名单，条目格式 `mcp:<server>`；空清单 = 不注入任何 MCP 工具 |
| `include_tools` | 列表                     | 唤回默认不在场的内置工具（如 `TeamCreate` 等运行期组队工具）         |
| `introduction`  | 可选                     | 人设正文备用入口；IDENTITY.md 正文非空时覆盖此字段                   |
| `meta`          | 映射                     | 自由扩展杂项                                                         |

已废弃的旧字段（新定义中**不得出现**）：`allowed-tools`（允许列表）、`requires.bins` / `requires.env`、`meta.name_zh` / `meta.role_zh` / `meta.description_zh`、旧 `domains`（已迁移为 `category`）。技能（SKILL.md）的 frontmatter 与 Agent 定义对齐：同样不得出现 `allowed-tools`、`requires.*`、`meta.*_zh`。

## `description` — LLM 路由描述

为 **LLM 路由** 而写：由另一个 LLM 阅读后决定是否将任务委派给该 Agent。不是营销文案。

### 路由五要素（每条 description 必须全部覆盖）

| # | 要素 | 要求 | 反例（路由失效） | 正例 |
|---|------|------|----------------|------|
| 1 | 领域词精确 | 用领域限定词，禁用过宽通用词（"开发""管理""分析"单独出现等于没有领域） | "负责开发工作" | "负责 React 前端页面与组件开发" |
| 2 | 产出物明确 | 写清交付什么 | "帮助处理代码问题" | "输出按严重度分组、含文件行号的问题清单" |
| 3 | 边界排除 | 隐含或显式写明不做什么 | 无边界，什么都接 | "不做架构决策，不产出完整实现代码" |
| 4 | 相邻区分 | 与职责最接近的既有 Agent 有可辨识差异 | 与 `code-reviewer` 描述高度重叠 | "审查设计文档与 ADR；代码级审查归 code-reviewer" |
| 5 | 典型触发表述 | 描述本身含有用户实际会说出的话式表达 | 纯抽象名词堆砌 | "审查这段 diff 的安全漏洞"式任务语 |

### 排他性检验（路由有效性的最终判据）

写完 description 与 SOUL 后自问：**把这份职责描述套到同领域的另一个 Agent 身上，是否同样成立？**

- 成立 → 该描述是行业共性，不是这个 Agent 的领域——重写，直到它只描述"这一个岗位"
- 判据：删掉 Agent 名字，仅凭 description，能否在含相邻 Agent 的列表中无歧义地选中它

示例（来自 `code-reviewer`）：

```
负责代码质量、安全与可维护性审查的审查员，按置信度门控输出可执行的问题清单。
```

示例（来自 `frontend-engineer`）：

```
专注高质量页面开发、组件封装、交互实现、状态管理、兼容性适配、性能优化与代码重构。
核心底线：输出代码可直接上线、结构清晰、可复用、易维护、零屎山，拒绝敷衍凑数、堆砌冗余代码。
```

## IDENTITY.md 正文

**惯例留空。** 正文为空时，系统由 frontmatter 的 `name` / `role` / `description` 自动生成标准角色定义（"我叫 X 是一名 Y, Z"）。

正文非空时，将**整体覆盖**自动生成的角色定义，作为整个 Agent 的人设（标题由文件自身处理）。仅在前述字段无法表达人设时才使用正文，并在正文中自带标题结构。

## SOUL.md — 角色职责（核心工作指令）

SOUL.md 用**三段式**表述角色职责，顺序固定：

- **职责**（要干什么）：负责什么、产出什么
- **方式**（怎么干）：怎么思考决策、按什么步骤干、何时调用哪个技能、何时提问——可展开为多节
- **边界**（不干什么）：只做什么、不做什么

标题由 SOUL.md 自身处理，系统原样注入提示词，不注入额外标题。

### 编写规则

- 按三段式组织：**职责 → 方式 → 边界**，"方式"段可按角色展开为多节，不套用统一模板章节名。
- 每条规则具体、可执行，用祈使句；禁止空泛的能力描述。
- **规则条目按三要素写**：触发场景（何时生效）+ 具体行为（做什么/不做什么）+ 理据（为什么）。缺触发场景的规则不知道何时用，缺理据的规则是空泛口号。
  - 反例："保证输出质量"
  - 正例："输出结论前逐条核对引用条款与有效期——过期引用是职业事故"
- 显式引用所配技能："规划流程按 implementation-planning 技能执行"、"按 silent-failure-detection 技能逐条排查"。
- **职责**与**边界**两段缺一不可：职责写清负责什么、产出什么；边界写清只做什么、不做什么。
- 优先使用绝对性用语：`每个`、`所有`、`总是`、`从不`、`禁止`、`不得`。
- 定义是一份**约束清单**，不是能力炫耀。
- **反膨胀门槛**：每段规则 ≤8 条，工作流 ≤5 步；超出即说明领域切分过宽或把"能力吹嘘"写成了"约束"。
- **价值观排序**：角色的价值取向存在冲突可能时，在"方式"段开头写死排序（`A > B > C`，每项 ≤4 字）——价值观排序不清是行为摇摆与"崩人设"的根因。示例："合规 > 交付速度 > 通用性"。

### 诚实边界（与职责边界是两层）

"边界"段写两类约束，缺一不可：

- **职责边界**：只做哪些任务，不做哪些任务（对路由负责）
- **诚实边界**：能力局限的声明——知识截止时间、无法保证的事项、必须交由用户确认的决策（对幻觉负责）。示例："依赖库版本以官方文档当日为准，训练记忆中的 API 签名必须先核实再使用"。

### 退化行为（面向用户的角色必写，内部工具型可省）

| 压力场景 | 预期行为 |
|---------|---------|
| 用户反复质疑同一结论 | [复述论证并换角度，禁止逐字重复或顺从改口] |
| 被要求做违反边界的事 | [重申边界并给出替代路径] |
| 信息严重不足 | [声明不确定并标注置信度，禁止编造] |
| 用户表达不满/强烈情绪 | [先承认情绪再回到问题本身，禁止机械复读] |

### 质量自检清单（有明确交付物的角色必写）

把"输出要专业"这类不可验证要求转为可判定项，交付前逐条自查：

- 反例："代码质量高"
- 正例："所有函数有 docstring [是/否]""无调试残留 [是/否]""每条结论有出处 [是/否]"

### 示例一（`architect`，决策密集型）

```markdown
# 角色职责

## 职责

- 负责系统与服务的架构设计与关键技术决策，产出设计文档、ADR 与实施蓝图。

## 决策方式

- 先约束后方案：明确业务约束与质量属性优先级（性能、一致性、交付速度）后，再谈技术选型。
- 权衡显式化：每个关键决策写清备选项、取舍理由与被放弃项，沉淀为 ADR。
- 演进式设计：为当前需求设计最小充分结构，为可预见的变化留扩展缝，不为想象中的需求造抽象。
- 一致性优先：新设计必须与代码库既有模式对齐；偏离既有约定需显式说明理由。

## 规划方式

- 大型功能先产出实施蓝图：涉及文件、接口契约、数据流、构建顺序与里程碑，规划流程按 implementation-planning 技能执行。
- 每个阶段给出可验证的完成标准与风险预案。

## 交互规则

1. 前置校验：需求模糊、场景缺失、体量未知、技术边界不明确时，精准提问补齐信息，禁止主观臆断。
2. 风险前置：主动同步风险、短板、落地难点、兼容代价、后期迭代隐患，禁止只报优势。

## 边界

- 只做设计与决策建议，实现细节交由对应语言岗位；不产出未经确认的完整代码方案。
```

### 示例二（`code-reviewer`，流程密集型）

```markdown
# 角色职责

## 职责

- 负责代码质量、安全与可维护性审查，按严重度分组输出可执行的问题清单；无问题时明确说明，不凑数。

## 审查流程

1. 先看变更意图（需求/diff 范围），再逐文件审查；上下文不足时主动补读相关代码，不凭猜测下结论。
2. 按维度检查：正确性 > 安全 > 可维护性 > 性能 > 风格；每条问题给出文件与行号定位。
3. 置信度门控：只报告置信度 ≥ 80% 的问题；可以且应该返回"零发现"，严重度膨胀比遗漏更损害信任。

## 严重度分级

- critical：可被利用的漏洞、数据损坏、必然崩溃
- high：逻辑错误、竞态、资源泄漏

## 输出

按严重度分组列出：位置、问题、影响、建议修法；无问题时明确说明已检查的维度，不凑数。
```

## `skills` — 技能分配

技能是 **LLM 的操作指令**，不是功能开关。每个技能会激活特定的工具、行为或领域知识。

- 选择能**实现 Agent 所需行为**的技能
- 不要贪多 —— 每个技能都会增加上下文开销
- 查询 `mindx skill list --json` 查看可用选项
- 示例：代码审查员需要 `security-review`、`silent-failure-detection`、`coding-standards`

---

## `exclude_tools` / `allows_tools` — 工具控制

内置工具默认全量可用，控制手段只有两个：

- **`exclude_tools`（内置工具裁剪）**：按角色排除确实有害的工具。工作者排除 `SubAgent`、`CollectResults`（不委派）；常见追加 `Sleep`、`PowerShell`。不支持通配符，只能指定具体工具名。`Team*` 运行期组队工具默认不在场，无需排除。
- **`include_tools`（唤回默认不在场的工具）**：`Team*` 运行期组队工具（`TeamCreate`/`TeamDelete`/`TeamList`/`TeamGetTasks`）默认剥离，需要运行期组队时在此列出唤回。
- **`allows_tools`（MCP 服务白名单）**：条目格式 `mcp:<server>`（server 粒度），决定注入哪些 MCP server 的工具；空清单 = 不注入任何 MCP 工具。内置工具不在此列。

工作者智能体保留 `SubAgent` 后可能开始委派工作而不是自己做 —— 只给明确需要协调他人的角色保留委派工具。

## Team 实体 — 一等团队与负责人

固定团队不是 Agent 的属性，而是独立的一等实体（`~/.mindx/teams/<team>/TEAM.md`）：

- frontmatter：`name`（内部标识）/ `nick_name`（展示主名）/ `description` / `leader`（负责人 Agent 名）/ `members`（成员 Agent 名列表，纯引用）/ `icon` / `category` / `hired`
- 正文 Profile：团队人设定义（负责人怎么协调成员、跟踪结果、汇报成果），系统在团队会话中原样注入（缺失时用兜底文案）
- **引用单向（Team→Agent）**：团队持有成员名单，Agent 定义里不写任何团队信息；同一 Agent 可被多个团队引用
- **团队会话以负责人身份发起**（团队会话 resolve 到 leader，与团队对话 = 与负责人对话）；雇佣团队（`mindx team hire`）后团队才出现在会话选择器
- 管理命令：`mindx team add/update/hire/fire/rm/export`；团队可整包进市场（`mindx team export` 产出 kind=team 包，消费者 `mindx market install team` 整队招聘）

### 团队编制设计规范（建队前必须完成）

团队是"用户需求 → 团队 → 成员"路由链的中层。编制设计决定这层路由是否有效：

1. **领域切分互斥且覆盖**：成员职责两两互斥（任一具体任务有且只有一个明确归属成员）且并集覆盖团队使命。检验法：把一个典型任务同时描述给两个相邻成员的 description，若两者都说"归我"，切分无效，重新划界。
2. **每成员 description 写相邻区分**：与团队内职责最接近的成员互相写明分界（"X 归我；Y 归某某成员"）。
3. **排他性检验**：某成员的职责描述换成同团队其他成员仍然成立 → 该成员没有独立领域，合并或重切。
4. **团队 description 写"何时找这个团队"**：面向"用户需求 → 团队"层路由，写清团队承接的需求类型与不承接的类型，禁用"提供全方位 X 服务"式万能描述。
5. **leader SOUL 必须写协调职责**：团队会话就是与 leader 对话——leader 的 SOUL 除个人专业职责外，必须写明任务拆解、派发成员、跟踪结果、汇报成果的方式；缺协调职责的 leader 会在团队会话里自己埋头干活。
6. **团队职责归 Team Profile**：成员间协作规则、验收口径、汇报链路写进 TEAM.md 正文，不散落进成员 SOUL。

## 风格规则

- 使用直接、简短、祈使句式的语言。
- 优先使用绝对性用语：`每个`、`所有`、`总是`、`从不`、`禁止`、`不得`。
- SOUL 每条规则都要具体可执行，含明确边界。
- `role` / `description` 直接用中文，不设独立中文字段；智能体间命名保持一致。

---

## 反模式

- 名称重复 —— 先用 `mindx agent list --all --json` 查重（默认视图只显示已雇佣的）
- 市场已有却重复创建 —— 先用 `mindx market list --kind agent` 检索，能复用就安装雇佣
- 职责范围过广 —— 会破坏专家委派机制
- 路由描述无排他性 —— description 套到同领域任何 Agent 身上都成立，等于没有领域
- 与相邻 Agent 描述重叠 —— 两个 Agent 都说"归我"时 LLM 路由不可预测，必须写明分界
- 技能贪多 —— 每个技能都会增加上下文开销
- 规则写成空泛口号 —— 缺触发场景与理据的规则（"保证质量""输出专业"）不产生行为约束
- 缺价值观排序 —— 价值取向有冲突可能的角色不写死排序，行为就会摇摆
- SOUL 缺少职责或边界段 —— 会导致误路由与越界
- 名称与角色不匹配 —— `python-programmer` 的描述却写成"全栈开发"，会干扰路由
- `description` 写成营销文案 —— 它是给 LLM 路由用的
- 创建后忘记 `mindx agent hire` —— 智能体永远不出现在会话可用列表中
- 使用已废弃的旧字段（`allowed-tools`、`requires.*`、`meta.*_zh`）
- SOUL 写成能力清单 —— SOUL 是角色职责与约束，不是"我会什么"的罗列
- 规则条数失控 —— 单段规则 >8 条或工作流 >5 步，说明领域切分过宽，重新划界

## 创建检查清单

运行 `mindx agent add` 之前：

- [ ] 已与用户确认名称、角色、业务分类、工作范围
- [ ] 已运行 `mindx agent list --all --json` —— 确认无重复或重叠的 Agent
- [ ] 已运行 `mindx market list --kind agent --filter "<关键词>"` —— 确认市场无现成可复用的 Agent 包
- [ ] 已运行 `mindx skill list --json` —— 已识别相关技能；本地缺失的技能已按 `find-skills` 技能查找并安装
- [ ] `name` 为小写连字符格式，唯一，基于名词
- [ ] `role` 为简洁中文头衔；`description` 为 1-2 句中文路由描述，含边界
- [ ] `category` 已确定为中文业务分类
- [ ] `skills` 列表精简 —— 仅包含领域相关技能
- [ ] `exclude_tools` 按角色裁剪；需要 MCP 服务时已列 `allows_tools`

创建之后：

- [ ] 已编写 SOUL.md（职责、方式、边界三段式，显式引用技能）
- [ ] description 过排他性检验：套到同领域其他 Agent 身上不成立
- [ ] 与职责最接近的既有 Agent 已写明相邻区分
- [ ] 规则条目含触发场景 + 具体行为 + 理据；单段规则 ≤8 条，工作流 ≤5 步
- [ ] 价值取向有冲突可能的角色已写价值观排序；面向用户的角色已写退化行为
