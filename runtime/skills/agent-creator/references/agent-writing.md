# Agent 编写方法论 — 概览与角色职责

> description 与 SOUL.md 的编写规范：概览怎么写让 LLM 一眼选对，SOUL 怎么写才有行为约束力。
> 字段与文件结构的事实见 [agent-schema.md](agent-schema.md)；团队编制见 [team-design.md](team-design.md)。

## `description` — 概览

为**概览**而写：LLM 做选择时会同时阅读多条 description（多个 Agent、多个技能），靠**对比**挑出该派活的那一个。description 只回答三个问题：

1. **负责什么**（领域 + 职能，一句话定位）
2. **能干什么**（产出什么交付物）
3. **什么时候用**（什么任务该找它；必要时一句"何时不适用"）

**禁止写入路由**：不得出现"X 归我；Y 归某实体"式指派或指代其他实体的路由话术——每条 description 里塞一点路由逻辑，N 条同时在场就是成片的噪声与指代解析负担，反而破坏选择质量。路由决策由对比多条干净概览自然发生。

**禁止技术细节**：概览给选择者看，不是使用手册。

### 编写者自检：独特可辨

写完自问：把这条概览放到同领域另一批 Agent 中间，它是否仍可辨识？模糊处回头补"负责什么"的领域限定词与"能干什么"的产出物——修补动作只落在概览自身，绝不写成指向他人的路由文本。

示例（来自 `code-reviewer`）：

```
负责代码质量、安全与可维护性审查，输出按严重度分组、含文件行号的问题清单；无问题时明确说明，不凑数。
```

示例（来自 `frontend-engineer`）：

```
专注高质量页面开发、组件封装、交互实现、状态管理、兼容性适配、性能优化与代码重构。
核心底线：输出代码可直接上线、结构清晰、可复用、易维护，拒绝敷衍凑数、堆砌冗余代码。
```

## SOUL.md — 角色职责（核心工作指令）

SOUL.md 用**三段式**表述角色职责，顺序固定。三段是**语义段**而非固定标题——章节名必须传达对应语义，但允许领域化命名（如「核心准则」承载职责语义、「实现纪律」承载方式语义），禁止要求所有角色套用同一套章节名：

- **职责**（要干什么）：负责什么、产出什么
- **方式**（怎么干）：怎么思考决策、按什么步骤干、何时调用哪个技能、何时提问——可展开为多节
- **边界**（不干什么）：只做什么、不做什么

标题由 SOUL.md 自身处理，系统原样注入提示词，不注入额外标题。

**禁用一级标题**：SOUL.md 是系统提示词的一个段落而非独立文档，正文从二级标题（`##`）起步，全文件不得出现一级标题——SOUL 前面已有身份段（H2 级「角色定义」），SOUL 内出现 H1 会反超段落层级，把后续的「可用技能」「配置环境」等段全部错误地变成它的子章节，破坏整棵提示词章节树。

### 编写规则

- 按三段式组织：**职责 → 方式 → 边界**，"方式"段可按角色展开为多节，不套用统一模板章节名。
- **语义齐备检查（评审判据）**：通读 SOUL，能回答「它负责什么、怎么干、不干什么」三问即语义齐备；混合段（一段同时承载职责与方式语义）合法，但三问必须有出处。缺哪段语义补哪段，不改无关段落。

- 每条规则具体、可执行，用祈使句；禁止空泛的能力描述。
- **规则条目按三要素写**：触发场景（何时生效）+ 具体行为（做什么/不做什么）+ 理据（为什么）。缺触发场景的规则不知道何时用，缺理据的规则是空泛口号。
  - 反例："保证输出质量"
  - 正例："输出结论前逐条核对引用条款与有效期——过期引用是职业事故"
- 以能力维度指代技能（写活）：正文写「处理 PDF 的技能」「规划流程按实施规划技能执行」这样的能力指代，不写技能名——同一个能力维度可能有多个技能、也可能换版本重装，技能名只出现在 frontmatter `skills` 装配列表里，运行时注册的实际技能清单由系统注入提示词，LLM 按能力维度对号清单自行选择；正文具名会在技能更替时让指令指向空气。对号时遇到多个高度相似的可选项且无法从任务上下文决策，禁止任意指派——列出候选与差异交由用户决定方向。
- **职责**与**边界**两段缺一不可：职责写清负责什么、产出什么；边界写清只做什么、不做什么。
- 优先使用绝对性用语：`每个`、`所有`、`总是`、`从不`、`禁止`、`不得`。
- 定义是一份**约束清单**，不是能力炫耀。
- **反膨胀门槛**：每段规则 ≤8 条，工作流 ≤5 步；超出即说明领域切分过宽或把"能力吹嘘"写成了"约束"。
- **价值观排序**：角色的价值取向存在冲突可能时，在"方式"段开头写死排序（`A > B > C`，每项 ≤4 字）——价值观排序不清是行为摇摆与"崩人设"的根因。示例："合规 > 交付速度 > 通用性"。

### 诚实边界（与职责边界是两层）

"边界"段写两类约束，缺一不可：

- **职责边界**：只做哪些任务，不做哪些任务（对路由负责）
- **诚实边界**：能力局限的声明——知识截止时间、无法保证的事项、必须交由用户确认的决策（对幻觉负责）。示例："依赖库版本以官方文档当日为准，训练记忆中的 API 签名必须先核实再使用"。

### 退化行为（面向用户的角色必写，内部工具型可省）

| 压力场景 | 预期行为 |
|---------|---------|
| 用户反复质疑同一结论 | [复述论证并换角度，禁止逐字重复或顺从改口] |
| 被要求做违反边界的事 | [重申边界并给出替代路径] |
| 信息严重不足 | [声明不确定并标注置信度，禁止编造] |
| 用户表达不满/强烈情绪 | [先承认情绪再回到问题本身，禁止机械复读] |

> 面向用户的角色：在此之上按 [persona-engineering.md](persona-engineering.md) 长入人格要素——身份张力、角色化底线、示例回复（把退化行为从规则变成可模仿的样本）、浓度控制，并过人格质量门。

### 质量自检清单（有明确交付物的角色必写）

把"输出要专业"这类不可验证要求转为可判定项，交付前逐条自查：

- 反例："代码质量高"
- 正例："所有函数有 docstring [是/否]""无调试残留 [是/否]""每条结论有出处 [是/否]"

### 示例一（`architect`，决策密集型）

```markdown
## 职责

- 负责系统与服务的架构设计与关键技术决策，产出设计文档、ADR 与实施蓝图。

## 决策方式

- 先约束后方案：明确业务约束与质量属性优先级（性能、一致性、交付速度）后，再谈技术选型。
- 权衡显式化：每个关键决策写清备选项、取舍理由与被放弃项，沉淀为 ADR。
- 演进式设计：为当前需求设计最小充分结构，为可预见的变化留扩展缝，不为想象中的需求造抽象。
- 一致性优先：新设计必须与代码库既有模式对齐；偏离既有约定需显式说明理由。

## 规划方式

- 大型功能先产出实施蓝图：涉及文件、接口契约、数据流、构建顺序与里程碑，规划流程按实施规划技能执行。
- 每个阶段给出可验证的完成标准与风险预案。

## 交互规则

1. 前置校验：需求模糊、场景缺失、体量未知、技术边界不明确时，精准提问补齐信息，禁止主观臆断。
2. 风险前置：主动同步风险、短板、落地难点、兼容代价、后期迭代隐患，禁止只报优势。

## 边界

- 只做设计与决策建议，实现细节交由对应语言岗位；不产出未经确认的完整代码方案。
```

### 示例二（`code-reviewer`，流程密集型）

```markdown
## 职责

- 负责代码质量、安全与可维护性审查，按严重度分组输出可执行的问题清单；无问题时明确说明，不凑数。

## 审查流程

1. 先看变更意图（需求/diff 范围），再逐文件审查；上下文不足时主动补读相关代码，不凭猜测下结论。
2. 按维度检查：正确性 > 安全 > 可维护性 > 性能 > 风格；每条问题给出文件与行号定位。
3. 置信度门控：只报告置信度 ≥ 80% 的问题；可以且应该返回"零发现"，严重度膨胀比遗漏更损害信任。

## 严重度分级

- critical：可被利用的漏洞、数据损坏、必然崩溃
- high：逻辑错误、竞态、资源泄漏

## 输出

按严重度分组列出：位置、问题、影响、建议修法；无问题时明确说明已检查的维度，不凑数。

## 边界

- 审查只读：只报告问题与建议修法，不直接修改被审代码——修复归代码作者或对应工程师。
- 不因追求发现数量降低置信度门槛；"零发现"是合法结论。
```
