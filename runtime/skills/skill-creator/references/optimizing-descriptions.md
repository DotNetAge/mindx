# 优化 skill 描述

> 如何改进 skill 的描述，让它在相关提示上稳定触发。

skill 只有被激活才有用。`SKILL.md` 前置元数据中的 `description` 字段是智能体决定是否为给定任务加载 skill 的主要机制。描述不足意味着该触发时不会触发；描述过宽意味着不该触发时也会触发。

本指南介绍如何系统化地测试和改进 skill 描述，以提高触发准确性。

## 技能触发机制

智能体使用[渐进式披露](spec.md#渐进式披露)来管理上下文。启动时，它们只加载每个可用 skill 的 `name` 和 `description`——刚好足以判断 skill 何时可能相关。当用户任务与描述匹配时，智能体把完整的 `SKILL.md` 读入上下文并遵循其指令。

这意味着描述承担了触发的全部责任。如果描述没有传达 skill 何时有用，智能体就不会知道去调用它。

一个重要的细微差别：智能体通常只针对超出其单独处理能力的知识或能力需求来查阅 skill。像"读取这个 PDF"这样简单的一步式请求，即使描述完全匹配也可能不会触发 PDF skill，因为智能体用基础工具就能处理。涉及专业知识——不熟悉的 API、领域特定工作流或不常见格式——的任务，才是好描述能起作用的地方。

## 编写有效的描述

测试之前，先了解好描述长什么样。几个原则：

* **使用祈使句式。** 把描述写成对智能体的指令："当……时使用此技能"，而不是"此技能可以……"。智能体在决定是否行动，所以要告诉它何时行动。

* **聚焦用户意图，而非实现。** 描述用户想达成什么，而不是 skill 的内部机制。智能体匹配的是用户的要求。

* **宁可激进一些。** 明确列出 skill 适用的场景，包括用户没有直接说出领域的情况："即使他们没有明确提到'CSV'或'分析'。"

* **保持简洁。** 几句话到一小段通常正合适——足够覆盖 skill 的范围，又不会在众多 skill 之间撑大智能体的上下文。[规范](spec.md#描述字段)强制执行 1024 字符的硬上限。

## 设计触发评估查询

要测试触发，你需要一组评估查询——标注了应该或不应该触发你的 skill 的真实用户提示。

```
[
  { "query": "我有一份 ~/data/q4_results.xlsx 电子表格，C 列是收入、D 列是支出——你能加一列利润率，并标出所有低于 10% 的吗？", "should_trigger": true },
  { "query": "把这个 json 文件转成 yaml 最快的方法是什么", "should_trigger": false }
]
```

目标约 20 个查询：8-10 个应该触发，8-10 个不应该触发。

### 应该触发的查询

这些测试描述是否覆盖了 skill 的范围。从几个维度变化：

* **措辞**：有的正式、有的随意、有的带拼写错误或缩写。

* **明确性**：有的直接说出 skill 的领域（"分析这个 CSV"），有的只描述需求而不点明（"我老板想从这份数据文件里出一张图"）。

* **详细程度**：混合简短提示与信息密集的提示——一句"分析我的销售 CSV 并画张图"，与一条带文件路径、列名和背景故事的较长的消息。

* **复杂度**：变化步骤数和决策点。把单步任务与多步工作流混在一起，测试当 skill 应对的任务埋藏在更大的链条中时，智能体能否辨别其相关性。

最有价值的应该触发查询是那些 skill 会有帮助、但单看查询难以看出关联的情况。这些正是措辞起作用的地方——如果查询已经精确要求了 skill 所做的事，任何合理的描述都会触发。

### 不应该触发的查询

最有价值的负例是**近似匹配**——与你的 skill 共享关键词或概念、但实际需要不同东西的查询。这些测试描述是否精确，而不只是宽泛。

对于 CSV 分析 skill，弱的负例是：

* `"写一个斐波那契函数"` — 明显无关，测不出什么。

* `"今天天气怎么样？"` — 没有关键词重叠，太简单。

强的负例：

* `"我需要更新 Excel 预算电子表格里的公式"` — 共享"电子表格"和"数据"概念，但需要的是 Excel 编辑，不是 CSV 分析。

* `"你能写一个读取 csv 并逐行上传到我们 postgres 数据库的 python 脚本吗"` — 涉及 CSV，但任务是数据库 ETL，不是分析。

### 追求真实的技巧

真实用户提示包含通用测试查询所缺少的上下文。包含：

* 文件路径（`~/Downloads/report_final_v2.xlsx`）

* 个人背景（"我经理让我……"）

* 具体细节（列名、公司名、数据值）

* 随意的语言、缩写和偶尔的拼写错误

## 测试描述是否触发

基本方法：在安装了 skill 的智能体上运行每个查询，观察智能体是否调用它。确保 skill 已注册并且你的智能体可发现——具体方式因客户端而异（例如 skill 目录、配置文件或 CLI 标志）。

大多数智能体客户端提供某种可观测性——执行日志、工具调用历史或详细输出——可以让你看到一次运行中查阅了哪些 skill。细节查看你的客户端文档。如果智能体加载了你的 skill 的 `SKILL.md`，说明它被触发了；如果智能体没有查阅就继续执行，说明没触发。

一个查询"通过"的条件是：

* `should_trigger` 为 `true` 且 skill 被调用，或

* `should_trigger` 为 `false` 且 skill 未被调用。

### 多次运行

模型行为是非确定性的——同一个查询这次运行可能触发 skill，下次就不触发。每个查询运行多次（3 次是合理的起点），计算**触发率**：skill 被调用的运行次数占比。

应该触发的查询在触发率高于阈值（0.5 是合理的默认值）时通过。不应该触发的查询在触发率低于该阈值时通过。

20 个查询各运行 3 次就是 60 次调用。你需要把它脚本化。下面是通用结构——把 `check_triggered` 中的 `claude` 调用和检测逻辑替换成你的智能体客户端提供的任何东西：

```
#!/bin/bash
QUERIES_FILE="${1:?Usage: $0 <queries.json>}"
SKILL_NAME="my-skill"
RUNS=3

# 此示例使用 Claude Code 的 JSON 输出检查 Skill 工具调用。
# 将此函数替换为你的智能体客户端的检测逻辑。
# skill 被调用时返回 0（成功），否则返回 1。
check_triggered() {
  local query="$1"
  claude -p "$query" --output-format json 2>/dev/null \
    | jq -e --arg skill "$SKILL_NAME" \
      'any(.messages[].content[]; .type == "tool_use" and .name == "Skill" and .input.skill == $skill)' \
      > /dev/null 2>&1
}

count=$(jq length "$QUERIES_FILE")
for i in $(seq 0 $((count - 1))); do
  query=$(jq -r ".[$i].query" "$QUERIES_FILE")
  should_trigger=$(jq -r ".[$i].should_trigger" "$QUERIES_FILE")
  triggers=0

  for run in $(seq 1 $RUNS); do
    check_triggered "$query" && triggers=$((triggers + 1))
  done

  jq -n \
    --arg query "$query" \
    --argjson should_trigger "$should_trigger" \
    --argjson triggers "$triggers" \
    --argjson runs "$RUNS" \
    '{query: $query, should_trigger: $should_trigger, triggers: $triggers, runs: $runs, trigger_rate: ($triggers / $runs)}'
done | jq -s '.'
```

## 用训练/验证集拆分避免过拟合

如果针对所有查询优化描述，就有过拟合的风险——写出的描述对这些特定措辞有效，却无法应对新措辞。

解决办法是拆分查询集：

* **训练集（约 60%）**：用于发现失败并指导改进的查询。

* **验证集（约 40%）**：留出来、只用于检查改进是否泛化的查询。

确保两个集合都包含成比例的应该触发和不应该触发查询——别不小心把正例都放进一个集合。随机打乱，并在各轮迭代中保持拆分固定，这样才是同类相比。

如果你使用类似[上面](#多次运行)的脚本，可以把查询拆成两个文件——`train_queries.json` 和 `validation_queries.json`——分别对每个文件运行脚本。

## 优化循环

1. **评估**当前描述在*训练集和验证集*上的表现。训练结果指导你的修改；验证结果告诉你这些修改是否在泛化。

2. **找出** *训练集*中的失败：哪些应该触发的查询没触发？哪些不应该触发的查询触发了？

* 只用训练集的失败来指导修改——无论你自己改描述还是提示 LLM，都要把验证集的结果排除在过程之外。

3. **修订描述。** 聚焦泛化：

* 如果应该触发的查询失败，描述可能太窄。扩大范围，或补充关于 skill 何时有用的上下文。

* 如果不应该触发的查询误触发，描述可能太宽。增加关于 skill *不*做什么的具体性，或澄清该 skill 与相邻能力之间的边界。

* 避免从失败的查询中添加特定关键词——那是过拟合。应找出这些查询所代表的通用类别或概念，并针对它处理。

* 如果多轮迭代后仍卡住，尝试结构上不同的描述写法，而不是渐进式微调。不同的框架或句式可能突破精修无法突破的瓶颈。

* 检查描述是否仍在 1024 字符限制内——优化过程中描述往往会长大。

4. **重复**步骤 1-3，直到所有*训练集*查询通过或不再看到有意义的改进。

5. **选择最佳迭代**，依据其验证通过率——*验证集*中通过的查询占比。注意：最佳描述不一定是你最后产出的那个；更早的迭代可能比后来过拟合训练集的迭代有更高的验证通过率。

五次迭代通常够了。如果性能没有提升，问题可能出在查询上（太简单、太难或标注不当），而不是描述。

## 应用结果

选定最佳描述后：

1. 更新 `SKILL.md` 前置元数据中的 `description` 字段。

2. 验证描述在[1024 字符限制](spec.md#描述字段)内。

3. 验证描述按预期触发。手动试几个提示做快速 sanity check。更严格的做法：写 5-10 个全新查询（混合应该触发和不应该触发）通过评估脚本运行——因为这些查询从未参与优化过程，它们能诚实地检验描述是否泛化。

前后对比：

```
# 之前
description: 处理 CSV 文件。

# 之后
description: >
  分析 CSV 和表格数据文件——计算汇总统计、
  添加派生列、生成图表并清洗杂乱数据。当用户持有
  CSV、TSV 或 Excel 文件并希望探索、转换或可视化
  数据时使用此技能，即使他们没有明确提到"CSV"
  或"分析"。
```

改进后的描述更具体地说明了 skill 做什么（汇总统计、派生列、图表、清洗），也更宽泛地说明了何时适用（CSV、TSV、Excel；即使没有明确关键词）。
