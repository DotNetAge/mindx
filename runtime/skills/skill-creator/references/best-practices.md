# 创建技能的最佳实践

> 如何编写范围清晰、与任务相称的 skill。

## 从真实专业知识出发

技能创建中的一个常见误区是：让 LLM 生成 skill 却不提供领域特定上下文——只依赖 LLM 的通用训练知识。结果往往是一堆模糊、笼统的流程（"妥善处理错误"、"遵循身份验证最佳实践"），而不是那些真正让技能有价值的特定 API 模式、边界情况和项目约定。

有效的 skill 植根于真实专业知识。关键在于把领域特定上下文喂进创建过程。

### 从实际操作中提取

在与智能体的对话中完成一个真实任务，过程中提供上下文、纠正和偏好。然后把可复用的模式提取成 skill。注意以下几点：

* **有效的步骤** — 通向成功的动作序列
* **你做的纠正** — 你纠正智能体方法的地方（例如"用库 X 而不是 Y"、"检查边界情况 Z"）
* **输入/输出格式** — 数据进出时的样子
* **你提供的上下文** — 智能体本来不知道的项目特定事实、约定或约束

### 从现有项目产物中综合

当你有一批现有知识时，可以把它喂给 LLM，让它综合出一个 skill。从你团队实际的事故报告和操作手册中综合出的数据管道 skill，会优于从一篇泛泛的"数据工程最佳实践"文章中综合出的 skill，因为它捕捉了*你的* schema、失败模式和恢复流程。关键是项目特定材料，而不是通用参考资料。

好的源材料包括：

* 内部文档、操作手册和风格指南
* API 规范、schema 和配置文件
* 代码审查评论和问题跟踪器（捕捉反复出现的问题和审查者期望）
* 版本控制历史，尤其是补丁和修复（通过实际发生的变化揭示模式）
* 真实世界的失败案例及其解决方案

## 用真实执行来打磨

skill 的初稿通常需要打磨。在真实任务上运行 skill，然后把结果——所有结果，不只是失败的——反馈到创建过程中。问自己：什么触发了误报？漏掉了什么？什么可以删掉？

即使只做一轮"执行-修订"，也能明显提升质量，而复杂领域往往需要多轮。

<Tip>
  阅读智能体的执行轨迹，而不只是最终输出。如果智能体把时间浪费在低效步骤上，常见原因包括：指令太模糊（智能体试了好几种方法才找到可行的）、指令不适用于当前任务（智能体还是照做了）、或者给了太多选项却没有明确默认值。
</Tip>

## 明智地使用上下文

skill 一旦激活，其完整的 `SKILL.md` 正文就会连同对话历史、系统上下文和其他已激活的 skill 一起加载进智能体的上下文窗口。你 skill 中的每个 token 都在与窗口中其他一切争夺智能体的注意力。

### 补充智能体缺少的，省略它已知的

聚焦于没有你的 skill 智能体*不会知道*的内容：项目特定约定、领域特定流程、非显而易见的边界情况，以及要用的特定工具或 API。你不需要解释什么是 PDF、HTTP 如何工作、或数据库迁移是什么。

````markdown
<!-- 太啰嗦——智能体已经知道 PDF 是什么 -->
## 提取 PDF 文本

PDF（便携式文档格式）文件是一种常见文件格式，包含文本、图片
和其他内容。要从 PDF 中提取文本，你需要使用一个库。
推荐 pdfplumber，因为它能很好地处理大多数情况。

<!-- 更好——直接说智能体自己不知道的部分 -->
## 提取 PDF 文本

文本提取使用 pdfplumber。扫描文档回退到
pdf2image 加 pytesseract。

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
````

对每块内容问自己："没有这条指令，智能体会在这里出错吗？"如果不会，就删掉。如果不确定，就测试。如果智能体不用 skill 也能把整个任务做好，那这个 skill 可能没有增加价值。

### 设计内聚的单元

决定一个 skill 该覆盖什么，就像决定一个函数该做什么：你要让它封装一个与其他 skill 组合良好的内聚工作单元。范围过窄的 skill 会迫使单个任务加载多个 skill，带来开销和指令冲突的风险。范围过宽的 skill 则难以精确触发。一个用于查询数据库并格式化结果的 skill 可能是一个内聚单元，而一个还覆盖数据库管理的 skill 很可能想做的事太多了。

### 追求适度的细节

过于全面的 skill 弊大于利——智能体难以提取相关内容，还可能被不适用于当前任务的指令带偏，走上无产出的路径。简洁、分步骤的指引加上一个可用示例，往往胜过面面俱到的文档。当你发现自己在覆盖每个边界情况时，考虑一下其中大多数是否更适合交给智能体自行判断。

### 用渐进式披露组织大型 skill

[规范](./spec.md)建议把 `SKILL.md` 控制在 500 行、5000 token 以内——只保留智能体每次运行都需要的核心指令。当 skill 确实需要更多内容时，把详细参考材料移到 `references/` 或类似目录的单独文件中。

关键是告诉智能体*何时*加载每个文件。"如果 API 返回非 200 状态码，读取 `references/api-errors.md`"比笼统的"详见 references/"更有用。这让智能体按需加载上下文而不是一开始就全加载，这正是[渐进式披露](./spec.md#progressive-disclosure)的设计意图。

## 校准控制程度

并非 skill 的每个部分都需要同样的规定性程度。让指令的具体程度与任务的脆弱性相匹配。

### 具体程度匹配脆弱性

**给智能体自由**：当多种方法都有效、任务容忍变化时。对于灵活的指令，解释*为什么*可能比刚性指令更有效——理解指令背后意图的智能体能做出更好的上下文相关决策。一个代码审查 skill 可以描述该检查什么，而不必规定精确步骤：

```markdown
## 代码审查流程

1. 检查所有数据库查询是否存在 SQL 注入（使用参数化查询）
2. 验证每个端点的身份验证检查
3. 查找并发代码路径中的竞态条件
4. 确认错误信息不会泄露内部细节
```

**保持规定性**：当操作脆弱、一致性重要、或必须遵循特定顺序时：

````markdown
## 数据库迁移

严格按此顺序运行：

```bash
python scripts/migrate.py --verify --backup
```

不要修改命令或添加额外参数。
````

大多数 skill 两者兼有。逐部分独立校准。

### 提供默认方案，而不是选项菜单

当多种工具或方法都可行时，选定一个默认方案，简要提及替代方案，而不是把它们作为对等选项摆出来。

````markdown
<!-- 选项太多 -->
你可以用 pypdf、pdfplumber、PyMuPDF 或 pdf2image……

<!-- 明确的默认方案 + 逃生通道 -->
文本提取用 pdfplumber：

```python
import pdfplumber
```

需要 OCR 的扫描 PDF 改用 pdf2image 加 pytesseract。
````

### 重过程，轻声明

skill 应该教智能体*如何应对*一类问题，而不是*为某个具体实例产出什么*。对比：

```markdown
<!-- 具体答案——只对这个确切任务有用 -->
将 `orders` 表按 `customer_id` 关联到 `customers`，过滤出
`region = 'EMEA'` 的行，并对 `amount` 列求和。

<!-- 可复用的方法——适用于任何分析查询 -->
1. 从 `references/schema.yaml` 读取 schema 找到相关表
2. 按 `_id` 外键约定关联表
3. 把用户请求中的过滤条件作为 WHERE 子句
4. 按需聚合数值列并格式化为 markdown 表格
```

这并不意味着 skill 不能包含具体细节——输出格式模板（参见[输出格式模板](#输出格式模板)）、"绝不输出 PII"这类约束、以及特定工具指令都很有价值。要点是：即使个别细节是具体的，*方法*应当可以泛化。

## 高效指令的模式

以下是一些组织 skill 内容的可复用技巧。不是每个 skill 都需要全部——用适合你任务的那些。

### 注意事项（Gotchas）小节

许多 skill 中价值最高的内容是注意事项列表——那些违背合理假设的环境特定事实。这些不是泛泛建议（"妥善处理错误"），而是对智能体在没人告诉它的情况下必然会犯的错误的具体纠正：

```markdown
## 注意事项

- `users` 表使用软删除。查询必须包含
  `WHERE deleted_at IS NULL`，否则结果会包含已停用的账户。
- 用户 ID 在数据库中是 `user_id`，在认证服务中是 `uid`，
  在计费 API 中是 `accountId`。三者指向同一个值。
- 只要 Web 服务器在运行，`/health` 端点就返回 200，
  即使数据库连接已断开。用 `/ready` 检查完整的
  服务健康状态。
```

把注意事项放在 `SKILL.md` 中，这样智能体在遇到相关情况前就能读到。如果你告诉智能体何时加载，单独的参考文件也可以，但对非显而易见的问题，智能体可能认不出触发时机。

<Tip>
  当智能体犯了需要你纠正的错误时，把纠正加入注意事项小节。这是迭代改进 skill 最直接的方式之一（参见[用真实执行来打磨](#用真实执行来打磨)）。
</Tip>

### 输出格式模板

当你需要智能体以特定格式产出时，提供一个模板。这比用散文描述格式更可靠，因为智能体对具体结构的模式匹配能力远强于理解大段文字。短模板可以直接内联放在 `SKILL.md` 中；较长的模板，或只在某些情况下需要的模板，存放在 `assets/` 中并从 `SKILL.md` 引用，这样只在需要时加载。

````markdown theme={null}
## 报告结构

使用此模板，根据具体分析按需调整各部分：

```markdown
# [分析标题]

## 摘要
[关键发现的一段概述]

## 关键发现
- 发现 1 及支撑数据
- 发现 2 及支撑数据

## 建议
1. 具体的可执行建议
2. 具体的可执行建议
```
````

### 多步骤工作流清单

明确的清单帮助智能体跟踪进度、避免跳步，尤其是步骤之间有依赖或验证关卡时。

```markdown theme={null}
## 表单处理工作流

进度：
- [ ] 步骤 1：分析表单（运行 `scripts/analyze_form.py`）
- [ ] 步骤 2：创建字段映射（编辑 `fields.json`）
- [ ] 步骤 3：验证映射（运行 `scripts/validate_fields.py`）
- [ ] 步骤 4：填写表单（运行 `scripts/fill_form.py`）
- [ ] 步骤 5：验证输出（运行 `scripts/verify_output.py`）
```

### 验证循环

指示智能体在继续前验证自己的工作。模式是：做工作 → 运行验证器（脚本、参考清单或自查）→ 修复问题 → 重复直到验证通过。

```markdown theme={null}
## 编辑工作流

1. 进行编辑
2. 运行验证：`python scripts/validate.py output/`
3. 如果验证失败：
   - 查看错误信息
   - 修复问题
   - 再次运行验证
4. 只有验证通过才能继续
```

参考文档也可以充当"验证器"——指示智能体在定稿前对照参考检查其工作。

### 计划-验证-执行

对于批量或破坏性操作，让智能体先用结构化格式创建中间计划，对照事实来源验证它，然后才执行。

```markdown
## PDF 表单填写

1. 提取表单字段：`python scripts/analyze_form.py input.pdf` → `form_fields.json`
   （列出每个字段名、类型以及是否必填）
2. 创建 `field_values.json`，将每个字段名映射到其目标值
3. 验证：`python scripts/validate_fields.py form_fields.json field_values.json`
   （检查每个字段名是否存在于表单中、类型是否兼容、
   必填字段是否缺失）
4. 如果验证失败，修订 `field_values.json` 并重新验证
5. 填写表单：`python scripts/fill_form.py input.pdf field_values.json output.pdf`
```

关键成分是第 3 步：一个对照事实来源（`form_fields.json`）检查计划（`field_values.json`）的验证脚本。像 `Field 'signature_date' not found — available fields: customer_name, order_total, signature_date_signed` 这样的错误能给智能体足够的信息自我纠正。

### 打包可复用脚本

如果你注意到智能体每次运行都在独立地重新发明相同的逻辑——画图表、解析特定格式、验证输出——那就是信号：应该一次性写一个经过测试的脚本，打包进 `scripts/`。

更多关于设计和打包脚本的内容，参见[在 skill 中使用脚本](using-scripts.md)。
