# 创建技能的最佳实践

> 如何编写范围清晰、与任务相称的 skill。

## 技能三层结构（每个 skill 的完整形态）

一个完整技能由三层构成，缺一层都是不完整技能。写技能前先想清楚三层各自装什么：

| 层 | 定位 | 职责 | 回答的问题 |
| --- | --- | --- | --- |
| `SKILL.md` | **工作指导** | 决策路由：何时用、怎么判断、按什么顺序推进、走到哪一步读哪个文件（渐进式披露） | "接下来该做什么" |
| `references/` | **作业指导书** | 具体怎么做：全量收集领域权威资料（官方规范/API/模板/最佳实践，全文收纳+中文翻译+frontmatter 出处/更新日期+行号索引） | "这一步具体怎么做" |
| `scripts/` | **算力简化** | 三类操作优先脚本化：①高频重复 ②长时费算力的复杂操作 ③含技术含量的专业操作（一个程序能确定性解决复杂专业问题） | "哪些重活不用 LLM 干" |

**三层各自的纪律：**

- **SKILL.md 只写决策，不写操作细节**：正文是工作指导——什么时候用、先做什么后做什么、遇到分支怎么判断、读哪个参考文件。操作细节（参数表、规范条文、API 签名）一律下沉 references，正文不重复。正文膨胀到 >150 行（validate size warning）往往就是操作细节没下沉的信号。
- **references 是全量域索引**：把该领域"智能体不知道、但不该临时去查"的权威资料全部收纳（官方规范、API 手册、标准、模板、检查单、术语表、权威数据）。全量收集后，LLM 运行的决策路径被锁定在最短路径上——本地即查，不引导外搜，不凭记忆猜。每份文件必须带 frontmatter（source 出处 + updated 更新日期，更新检查依据），≥300 行文件带行号索引（LLM 按行定位，不用全文扫描）。
- **scripts 承接重活（三类）**：①高频重复——智能体每次运行都在重复同一段逻辑；②长时费算力的复杂操作——解析、转换、验证、批处理，脚本比 LLM 现场推理省 token、省时间、结果可复现；③**含技术含量的专业操作**——一个程序能确定性解决非常复杂的专业问题（格式解析、算法计算、协议转换、领域专用计算），即使频率不高也应优先写 script，而不是让 LLM 每次现场推理（LLM 推理这类问题既慢又易错，脚本一次写对、永久复用）。判断标准：有程序能确定性解决的操作，优先脚本，不留给 LLM 现场发挥。

**决策路径最短化的检验**：写完一个 skill，模拟 LLM 跑一遍主流程——每一步"接下来做什么"都应由 SKILL.md 给出明确路由（含"读哪个 references 文件"），"具体怎么做"都应在本地 references 里可查，重复计算/专业计算都应有脚本承接。若某一步 LLM 需要外搜或凭记忆猜，就是三层没装完的信号。

## 从真实专业知识出发

技能创建中的一个常见误区是：让 LLM 生成 skill 却不提供领域特定上下文 —— 只依赖 LLM 的通用训练知识。结果往往是一堆模糊、笼统的流程（"妥善处理错误"、"遵循身份验证最佳实践"），而不是那些真正让技能有价值的特定 API 模式、边界情况和项目约定。

有效的 skill 植根于真实专业知识。关键在于把领域特定上下文喂进创建过程。

### 从实际操作中提取

在与智能体的对话中完成一个真实任务，过程中提供上下文、纠正和偏好。然后把可复用的模式提取成 skill。注意以下几点：



* **有效的步骤** — 通向成功的动作序列

* **你做的纠正** — 你纠正智能体方法的地方（例如 "用库 X 而不是 Y"、"检查边界情况 Z"）

* **输入 / 输出格式** — 数据进出时的样子

* **你提供的上下文** — 智能体本来不知道的项目特定事实、约定或约束

### 从现有项目产物中综合

当你有一批现有知识时，可以把它喂给 LLM，让它综合出一个 skill。从你团队实际的事故报告和操作手册中综合出的数据管道 skill，会优于从一篇泛泛的 "数据工程最佳实践" 文章中综合出的 skill，因为它捕捉了*你的* schema、失败模式和恢复流程。关键是项目特定材料，而不是通用参考资料。

好的源材料包括：



* 内部文档、操作手册和风格指南

* API 规范、schema 和配置文件

* 代码审查评论和问题跟踪器（捕捉反复出现的问题和审查者期望）

* 版本控制历史，尤其是补丁和修复（通过实际发生的变化揭示模式）

* 真实世界的失败案例及其解决方案

## 用真实执行来打磨

skill 的初稿通常需要打磨。在真实任务上运行 skill，然后把结果 —— 所有结果，不只是失败的 —— 反馈到创建过程中。问自己：什么触发了误报？漏掉了什么？什么可以删掉？

即使只做一轮 "执行 - 修订"，也能明显提升质量，而复杂领域往往需要多轮。

## 明智地使用上下文

skill 一旦激活，其完整的 `SKILL.md` 正文就会连同对话历史、系统上下文和其他已激活的 skill 一起加载进智能体的上下文窗口。你 skill 中的每个 token 都在与窗口中其他一切争夺智能体的注意力。

### 补充智能体缺少的，省略它已知的

聚焦于没有你的 skill 智能体*不会知道*的内容：项目特定约定、领域特定流程、非显而易见的边界情况，以及要用的特定工具或 API。你不需要解释什么是 PDF、HTTP 如何工作、或数据库迁移是什么。

对每块内容问自己："没有这条指令，智能体会在这里出错吗？" 如果不会，就删掉。如果不确定，就测试。如果智能体不用 skill 也能把整个任务做好，那这个 skill 可能没有增加价值。

### 设计内聚的单元

决定一个 skill 该覆盖什么，就像决定一个函数该做什么：你要让它封装一个与其他 skill 组合良好的内聚工作单元。范围过窄的 skill 会迫使单个任务加载多个 skill，带来开销和指令冲突的风险。范围过宽的 skill 则难以精确触发。一个用于查询数据库并格式化结果的 skill 可能是一个内聚单元，而一个还覆盖数据库管理的 skill 很可能想做的事太多了。

### 追求适度的细节

过于全面的 skill 弊大于利 —— 智能体难以提取相关内容，还可能被不适用于当前任务的指令带偏，走上无产出的路径。简洁、分步骤的指引加上一个可用示例，往往胜过面面俱到的文档。当你发现自己在覆盖每个边界情况时，考虑一下其中大多数是否更适合交给智能体自行判断。

### 用渐进式披露组织大型 skill

[规范](./spec.md)建议把 `SKILL.md` 控制在 500 行、5000 token 以内 —— 只保留智能体每次运行都需要的核心指令。当 skill 确实需要更多内容时，把详细参考材料移到 `references/` 或类似目录的单独文件中。

关键是告诉智能体*何时*加载每个文件。" 如果 API 返回非 200 状态码，读取 `references/api-errors.md`"比笼统的" 详见 references/" 更有用。这让智能体按需加载上下文而不是一开始就全加载，这正是[渐进式披露](./spec.md#progressive-disclosure)的设计意图。

## 校准控制程度

并非 skill 的每个部分都需要同样的规定性程度。让指令的具体程度与任务的脆弱性相匹配。

### 具体程度匹配脆弱性

**给智能体自由**：当多种方法都有效、任务容忍变化时。对于灵活的指令，解释*为什么*可能比刚性指令更有效 —— 理解指令背后意图的智能体能做出更好的上下文相关决策。一个代码审查 skill 可以描述该检查什么，而不必规定精确步骤：



```
## 代码审查流程

1. 检查所有数据库查询是否存在 SQL 注入（使用参数化查询）
2. 验证每个端点的身份验证检查
3. 查找并发代码路径中的竞态条件
4. 确认错误信息不会泄露内部细节
```

**保持规定性**：当操作脆弱、一致性重要、或必须遵循特定顺序时：



````
## 数据库迁移

严格按此顺序运行：

```bash
python scripts/migrate.py --verify --backup
```

不要修改命令或添加额外参数。
````

大多数 skill 两者兼有。逐部分独立校准。

### 重过程，轻声明

skill 应该教智能体*如何应对*一类问题，而不是*为某个具体实例产出什么*。对比：



```
<!-- 具体答案——只对这个确切任务有用 -->
将 `orders` 表按 `customer_id` 关联到 `customers`，过滤出
`region = 'EMEA'` 的行，并对 `amount` 列求和。

<!-- 可复用的方法——适用于任何分析查询 -->
1. 从 `references/schema.yaml` 读取 schema 找到相关表
2. 按 `_id` 外键约定关联表
3. 把用户请求中的过滤条件作为 WHERE 子句
4. 按需聚合数值列并格式化为 markdown 表格
```

这并不意味着 skill 不能包含具体细节 —— 输出格式模板（参见[输出格式模板](#输出格式模板)）、"绝不输出 PII" 这类约束、以及特定工具指令都很有价值。要点是：即使个别细节是具体的，*方法*应当可以泛化。

## 高效指令的模式

以下是一些组织 skill 内容的可复用技巧。不是每个 skill 都需要全部 —— 用适合你任务的那些。

### 注意事项（Gotchas）小节

许多 skill 中价值最高的内容是注意事项列表 —— 那些违背合理假设的环境特定事实。这些不是泛泛建议（"妥善处理错误"），而是对智能体在没人告诉它的情况下必然会犯的错误的具体纠正：



```
## 注意事项

- `users` 表使用软删除。查询必须包含
  `WHERE deleted_at IS NULL`，否则结果会包含已停用的账户。
- 用户 ID 在数据库中是 `user_id`，在认证服务中是 `uid`，
  在计费 API 中是 `accountId`。三者指向同一个值。
- 只要 Web 服务器在运行，`/health` 端点就返回 200，
  即使数据库连接已断开。用 `/ready` 检查完整的
  服务健康状态。
```

把注意事项放在 `SKILL.md` 中，这样智能体在遇到相关情况前就能读到。如果你告诉智能体何时加载，单独的参考文件也可以，但对非显而易见的问题，智能体可能认不出触发时机。

### 输出格式模板

当你需要智能体以特定格式产出时，提供一个模板。这比用散文描述格式更可靠，因为智能体对具体结构的模式匹配能力远强于理解大段文字。短模板可以直接内联放在 `SKILL.md` 中；较长的模板，或只在某些情况下需要的模板，存放在 `assets/` 中并从 `SKILL.md` 引用，这样只在需要时加载。



````
## 报告结构

使用此模板，根据具体分析按需调整各部分：

```markdown
# [分析标题]

## 摘要
[关键发现的一段概述]

## 关键发现
- 发现 1 及支撑数据
- 发现 2 及支撑数据

## 建议
1. 具体的可执行建议
2. 具体的可执行建议
```
````

### 多步骤工作流清单

明确的清单帮助智能体跟踪进度、避免跳步，尤其是步骤之间有依赖或验证关卡时。



```
## 表单处理工作流

进度：
- [ ] 步骤 1：分析表单（运行 `scripts/analyze_form.py`）
- [ ] 步骤 2：创建字段映射（编辑 `fields.json`）
- [ ] 步骤 3：验证映射（运行 `scripts/validate_fields.py`）
- [ ] 步骤 4：填写表单（运行 `scripts/fill_form.py`）
- [ ] 步骤 5：验证输出（运行 `scripts/verify_output.py`）
```

工作流重的技能（≥3 步、有依赖或验收关卡）应改用系统 Task 工具建清单，而不是让智能体在正文里手工维护 `- [ ]`：



```
## 调研工作流

进入工作流前先 `TaskCreate` 建立任务清单（每步一项，含每步产出），
推进中用 `TaskUpdate` 标记完成状态，中断恢复时用 `TaskList`/`TaskGet`
读取进度，不凭回忆对齐工作点。
```

Task 工具清单是智能体的外部状态，跨轮次、跨中断保持，比正文清单更可靠。

### 主题不明先澄清

技能触发后若用户未指明关键输入（调研对象、研究方向、目标、范围、约束），禁止智能体自行猜测主题。要求技能先提供澄清指令：



```
## 主题澄清（动手前必做）

用户未指明调研对象时，禁止自行猜测主题。先用 AskUser 提供 2-4 个
假设选项让用户选择，用户不选再开放提问。按缺失项逐项澄清：
- 对象不明 → 列出贴近用户上下文的候选（品牌/产品/公司/事件/话题…）
- 范围或时间不明 → 列出候选 + 标注默认值
- 用途不明 → 列出候选（风控/监控/调研/汇报…）
每项给具体选项 + "其他（自由输入）"兜底。
```

澄清让智能体快速进入工作流而不反复猜测，尤其适合调研、分析、生成类技能。选项应贴近用户上下文（从当前对话推断），不是泛泛的示例清单。

### 文档配图（SVG 插图）

内容创作类技能（写文章、报告、方案、调研、长文档）产出文档时，若内容涉及流程、机制、架构、对比、分布、时间线、关系、分类等可结构化表达（图形比文字更清楚），应主动配 HTML/SVG 插图，而不是让文档变成纯文字墙：



```
## 文档配图（推荐）

产出文档、报告、文章或方案时，若内容涉及流程、机制、架构、对比、
分布、时间线、关系、分类等可结构化表达（图形比文字更清楚），按
visualization 技能（design 分类）的 HTML/SVG renderer 输出协议主动配图；
纯文字已足够清楚时不配。图与正文共用同一份已核对数据，禁止编造数值与事实。
```

配图只加在 "图比文字更清楚" 的结构处，不强制每篇都配；短内容、纯叙述、改写类技能不必加此节。

### 参考资料自包含（references 收纳）

专业技能的参考资料与专业规范**必须预置进 `references/`**，禁止让智能体运行时自行搜索资料。这是长期实践经验：技能若不自带资料，LLM 运行时要么凭记忆猜（写错），要么现场去 Web 搜——既浪费运行次数与时间，搜回来的资料还可能与本技能的方法论不匹配，产出反而被污染。



```
## 参考文档索引（按需加载）

| 文档 | 何时加载 |
| ---- | -------- |
| `references/spec.md` | 需要协议规范细节时 |
| `references/templates.md` | 需要输出模板时 |
```

```

要点：

- **资料全部收纳**：专业规范、API 手册、标准、模板、检查单、术语表、权威数据，能预置的全部放 `references/`（正文只写"何时加载哪个文件"）。凡"智能体不知道、但不该临时去查"的内容都属于这一类。
- **本地优先，外搜兜底**：技能正文默认指向 `{base_dir}/references/` 内的本地文件，不出现"去搜索官方文档""上网查一下"这类开头即检索的指令；但外搜是"活口"不是禁令——仅当本地参考资料不足或过时（资料缺失、版本失效、规范更新）时才允许外搜，并明确标注补到了什么。禁止用"禁止外搜"堵死这条退路：本地资料永远可能过时。
- **引来源，不引搜索**：确实需要外部链接时，给出**具体 URL 与用途**（如 `https://docs.unity3d.com/...` 命令行参数），不写"自己查一下"。
- **核验后收纳**：引用任何外部规范/CLI 用法前必须核验真实性（官方文档/实测），核验结论连同来源 URL 一并写进 references，禁止凭印象写。
- **按需加载**：references 收纳不等于正文膨胀——正文仍只给索引与加载时机（渐进式披露），智能体需要时才读对应文件。

#### references 元信息头（frontmatter 强制）

每份 references 文件**开头必须有 YAML frontmatter 承载更新日期**——这是新鲜度检查的唯一依据，缺了就无法判断资料是否过时；`source` 只在资料有外部出处时填写，自产文档不写：

```yaml
---
updated: YYYY-MM-DD
source: <官方文档 URL，有外部出处才填>
scope: <版本/平台/工具限定，可选>
---
```

- **updated**：该资料最近一次对照官方源核验/更新的日期（YYYY-MM-DD），不是官方文档的发布日期
- **source**：核验所依据的官方文档 URL（被核验过的具体入口，非搜索页）；已收纳全文的给官方原文页或官方下载页/CDN 直链。**有外部出处的必填**（出处缺失就无法按 URL 核验陈旧）；自产文档（规范、模板、经验总结）没有出处，不写
- **scope**：明确该资料对哪些版本/环境成立（如 "Unity 2021-2023 LTS"、"Godot 4.x"）；版本不在范围内 = 本地资料过时 → 触发外搜兜底

frontmatter 后直接进入正文，不再保留 markdown 引用行式元信息头。写 references 时先落 frontmatter 再写正文。

#### 大参考目录（≥300 行强制）

**正文 ≥300 行的 references 文件，必须在 frontmatter 之后、正文第一个标题之前插入「## 目录」段**：树状缩进的无序列表，每条目为 `标题 [L始行-L末行]`——LLM 检索大文件时按行号区间定位到章节附近读取，比全文扫描高效得多：

```markdown
## 目录

- 校准控制程度 [L148-L224]
  - 具体程度匹配脆弱性 [L152-L184]
  - 提供默认方案，而不是选项菜单 [L185-L204]
```

- **条目格式**：`- 标题 [L始行-L末行]`；L末行 = 下一个级别不高于自身的标题的前一行（末条目到文件末行），即章节的实际覆盖范围；h2-h4 进目录，h1 是文档标题不进
- **树状缩进**：子级缩进两空格，层级与正文标题层级一致
- **行号**：相对文件开头的实际行号（含 frontmatter 与目录段自身），供 Read 按 offset 定位；正文增删后行号会漂移，更新正文时重跑脚本重建
- **重建式幂等**：用 `scripts/gen_reference_toc.py` 自动生成/重建——已存在目录段（含旧式表格版）则先剥离再按当前正文重算，正文修改后重跑即可
- **<300 行不强制**：短文件直接 Read 全量即可，目录反而占空间

#### references 新鲜度检查（技能进化时必做）

审查已有技能时，逐份 references 核对（写入步骤 C 清单）：

1. **看日期（软信号，只触发复核不触发动作）**：frontmatter `updated` 超期 → 列入待复核候选。超期只是"该去验证了"的信号，**不是"内容已陈旧"的判定**——硬加日期会产生误报（内容可能多年不过时，也可能短期内反复变更）。超期阈值按领域定（版本敏感类约 90 天、方法论类 180 天+），只用于**复核优先级排序**，不是预警/更新的开关
2. **查可达**：frontmatter `source` URL 抽查可达性（curl HEAD 或 fetch），失效 = 待复核候选；无 `source` 的自产文档跳过此步
3. **对变更（陈旧判定只在此步）**：版本敏感内容对照官方变更记录/版本发布，确认引用的参数、包名、规范是否真的已失效——**只有这一步确认陈旧，才进入预警/更新**
4. **更新或移除**：确认陈旧后重新核验并刷新 `updated`，或移除；无法核实的写"以官方文档为准"；**未确认陈旧的内容不更新，只刷新核验日期或保持不动**
5. **留痕**：核验过程与结论写入技能 notes/ 进化履历（一次一条，含旧日期→新日期）

新鲜度检查与引文断裂检查（refcheck）是两件事：refcheck 查"引用是否存在"，新鲜度查"引用是否仍正确"——后者才是技能腐烂的解药。

### 验证循环

指示智能体在继续前验证自己的工作。模式是：做工作 → 运行验证器（脚本、参考清单或自查）→ 修复问题 → 重复直到验证通过。



```
## 编辑工作流

1. 进行编辑
2. 运行验证：`python scripts/validate.py output/`
3. 如果验证失败：
   - 查看错误信息
   - 修复问题
   - 再次运行验证
4. 只有验证通过才能继续
```

参考文档也可以充当 "验证器"—— 指示智能体在定稿前对照参考检查其工作。

### 计划 - 验证 - 执行

对于批量或破坏性操作，让智能体先用结构化格式创建中间计划，对照事实来源验证它，然后才执行。



```
## PDF 表单填写

1. 提取表单字段：`python scripts/analyze_form.py input.pdf` → `form_fields.json`
   （列出每个字段名、类型以及是否必填）
2. 创建 `field_values.json`，将每个字段名映射到其目标值
3. 验证：`python scripts/validate_fields.py form_fields.json field_values.json`
   （检查每个字段名是否存在于表单中、类型是否兼容、
   必填字段是否缺失）
4. 如果验证失败，修订 `field_values.json` 并重新验证
5. 填写表单：`python scripts/fill_form.py input.pdf field_values.json output.pdf`
```

关键成分是第 3 步：一个对照事实来源（`form_fields.json`）检查计划（`field_values.json`）的验证脚本。像 `Field 'signature_date' not found — available fields: customer_name, order_total, signature_date_signed` 这样的错误能给智能体足够的信息自我纠正。

### 打包可复用脚本

如果你注意到智能体每次运行都在独立地重新发明相同的逻辑 —— 画图表、解析特定格式、验证输出 —— 那就是信号：应该一次性写一个经过测试的脚本，打包进 `scripts/`。

更多关于设计和打包脚本的内容，参见[在 skill 中使用脚本](using-scripts.md)。
