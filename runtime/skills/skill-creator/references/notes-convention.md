# 进化记录编写规范

技能目录内的 `notes/` 是该技能的进化履历。每次对已有技能进化（回观修正、审查修复、评估迭代）后必须追加一条记录。记录有两类读者：

1. **下一次执行进化的智能体**——写之前想清楚：他读到什么才能不重蹈覆辙。
2. **复盘智能体（retrospect）**——履历会被复盘只读扫描，作为群体踩坑旁证进入经验聚类；"问题"字段的缺口类型（六分类）就是聚类标签，写规范一些，别让下游猜。履历本身留在技能目录内（技能自包含），复盘不修改、不搬移。

## 记录模板

文件命名：`agent_name-分类-标题.md`。一条记录一节，追加式。"问题"字段的缺口类型取六分类（与项目 notes 的缺口词汇表同源，复盘聚类直接按标签分组）：

````markdown
## YYYY-MM-DD <一句话症状>（<agent_name>）

- 问题：<缺口类型>——<根因描述>。缺口类型六选一：
  触发遗漏（该触发没触发）/ 规则缺失（场景未覆盖或规则模糊）/
  指令冲突（规则互相矛盾）/ 流程漏洞（某环节不可行）/
  输出格式（产出不符合预期）/ 版本兼容（外部依赖变更）
- 否决：<试过但被否决的方案及原因；没有则省略本条>
- 修正：<改了 SKILL.md 哪部分，version X → Y>
- 验证：<复现命令或验证用例>
````

## 字段语义

| 字段 | 回答的消费者问题                                 |
| ---- | ------------------------------------------------ |
| 问题 | 出了什么错、根因属于哪类——下次同类症状直接定位   |
| 否决 | 哪些方案试过且不行——失败记录比成功记录更省 token |
| 修正 | 改了哪里、版本怎么变——防止把已有修正改回去       |
| 验证 | 怎么确认有效——直接复用验证路径，不必重新设计     |

用户在进化过程中给出的约束原话（如"不要加 CLI"）写入修正或否决条目——这类偏好不适合进 SKILL.md，只能活在履历里。

## 反模式

- 任务流水账（"今天做了 A 又做了 B"）——履历不是日志
- 无法验证的断言（"效果变好了"）——必须附证据
- 改写或删除旧记录——履历只追加
