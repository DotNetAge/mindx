# 评估技能输出质量

通过评估驱动迭代验证技能是否可靠地产出好结果——跨不同措辞、跨边界情况、并且优于不用技能的基线。写完技能跑一次"看起来能用"不等于可靠。

## 设计测试用例

测试用例三要素：

- **Prompt**：真实用户会输入的消息
- **Expected output**：成功长什么样的人类可读描述
- **Input files**（可选）：技能需要操作的输入文件

存放在技能目录的 `evals/evals.json`：

```json
{
  "skill_name": "csv-analyzer",
  "evals": [
    {
      "id": 1,
      "prompt": "data/sales_2025.csv 是月度销售数据，找出营收最高的 3 个月并生成柱状图",
      "expected_output": "一张柱状图，展示营收最高的 3 个月，坐标轴和数值有标注",
      "files": ["evals/files/sales_2025.csv"]
    }
  ]
}
```

写测试 prompt 的要点：

- **2-3 个用例起步**，看过第一轮结果再扩展，别提前过度投入
- **措辞多样**：随意的（"帮我清理下这个 csv"）和精确的（"解析 data/input.csv，删除 B 列为空的行，结果写到 data/output.csv"）都要有
- **覆盖边界**：至少一个用例测畸形输入、异常请求或技能指令可能含糊的情形
- **真实上下文**：真实用户会提文件路径、列名、个人场景。"处理这个数据"模糊到测不出任何东西

第一轮之前**不要写断言**——看过输出才知道"好"长什么样。

## 运行评估

核心模式：每个用例跑两次——**用技能**一次，**不用技能**（或旧版本）一次，得到对照基线。

### 工作区结构

评估结果放在技能目录旁边的 workspace，每轮完整迭代一个 `iteration-N/` 目录：

```
csv-analyzer/
├── SKILL.md
└── evals/
    └── evals.json
csv-analyzer-workspace/
└── iteration-1/
    ├── eval-top-months-chart/
    │   ├── with_skill/
    │   │   ├── outputs/       # 运行产出
    │   │   ├── timing.json    # token 与耗时
    │   │   └── grading.json   # 断言判定
    │   └── without_skill/
    │       ├── outputs/
    │       ├── timing.json
    │       └── grading.json
    └── benchmark.json         # 汇总统计
```

手工编写的只有 `evals/evals.json`；`grading.json`、`timing.json`、`benchmark.json` 在评估过程中产出。

### 发起运行

每次运行必须用**干净上下文**——不带前次运行或技能开发过程的残留状态，保证智能体只遵循 SKILL.md。通过子代理发起运行可天然隔离；无法用子代理时，每次运行单独开会话。

每次运行提供四样东西：技能路径（基线运行不给）、测试 prompt、输入文件、输出目录：

```text
执行这个任务：
- 技能路径：/path/to/csv-analyzer
- 任务：data/sales_2025.csv 是月度销售数据，找出营收最高的 3 个月并生成柱状图
- 输入文件：evals/files/sales_2025.csv
- 输出保存到：csv-analyzer-workspace/iteration-1/eval-top-months-chart/with_skill/outputs/
```

基线运行用相同 prompt 但不给技能路径，输出存到 `without_skill/`。

**优化已有技能时用旧版本做基线**：改动前先快照（`cp -r <skill-path> <workspace>/skill-snapshot/`），基线运行指向快照，输出存到 `old_skill/`。

### 记录耗时

每次运行结束后**立即**记录 token 和耗时（事后无处可查）：

```json
{ "total_tokens": 84852, "duration_ms": 23332 }
```

## 编写断言

断言是对输出应包含什么或应达成什么的可验证陈述。看完第一轮输出再加。

好断言：

- `"输出文件是合法 JSON"` — 可编程验证
- `"柱状图有坐标轴标签"` — 具体可观察
- `"报告包含至少 3 条建议"` — 可数

弱断言：

- `"输出质量好"` — 太模糊，无法判定
- `"输出必须恰好包含短语 Total Revenue: $X"` — 太脆，措辞不同就误判

不是所有质量都能写成断言——写作风格、视觉设计、"感觉对不对"这类留给人工审查。断言只留给能客观检查的东西。

## 评分

对每条断言对照实际输出判定 PASS/FAIL，并记录**具体证据**——证据要引用或指向输出本身，不能只是观点。机械检查（JSON 是否合法、行数、文件是否存在且尺寸正确）用验证脚本，比 LLM 判断更可靠且跨迭代可复用；主观判断交给 LLM。

```json
{
  "assertion_results": [
    { "text": "输出包含柱状图图片文件", "passed": true, "evidence": "outputs/ 下找到 chart.png（45KB）" },
    { "text": "两个坐标轴都有标签", "passed": false, "evidence": "Y 轴有标签 'Revenue ($)'，X 轴没有" }
  ],
  "summary": { "passed": 1, "failed": 1, "total": 2, "pass_rate": 0.5 }
}
```

### 评分原则

- **PASS 必须有具体证据，不许模糊通过。** 断言说"包含摘要"，输出只有一个"摘要"标题加一句空话 = FAIL——标签在，实质不在
- **评分时同时审查断言本身**：太容易（不管技能好坏都过）、太难（输出很好也总挂）、不可验证（无法从输出判断）的断言要在下一轮修正
- **比较两个版本时用盲评**：两份输出给 LLM 裁判且不透露来源，裁判按自己的 rubric 给组织、格式、可用性、完成度打整体分。这补足断言评分的盲区——两份输出可能都过全部断言但整体质量差距明显

## 汇总

每轮迭代的运行都评完分后，计算汇总统计存入 `benchmark.json`：

```json
{
  "run_summary": {
    "with_skill":    { "pass_rate": { "mean": 0.83, "stddev": 0.06 }, "tokens": { "mean": 3800, "stddev": 400 } },
    "without_skill": { "pass_rate": { "mean": 0.33, "stddev": 0.10 }, "tokens": { "mean": 2100, "stddev": 300 } },
    "delta":         { "pass_rate": 0.50, "tokens": 1700 }
  }
}
```

`delta` 说明技能**花的**（时间、token）和**买的**（通过率提升）。多花 13 秒换 50 个百分点通过率，值得；token 翻倍换 2 个百分点，可能不值。

用例少、单次运行的早期迭代只看原始通过数和 delta；stddev 要在扩展测试集、每用例多次运行后才有意义。

## 分析模式

汇总统计会掩盖重要模式。算完 benchmark 后：

- **两种配置都恒过的断言**：删掉或替换——模型不用技能也能处理，无区分度，只会虚增 with-skill 通过率
- **两种配置都恒挂的断言**：先排查是断言写错（要求模型做不到的事）、用例太难、还是检查错了对象，修复后再进下一轮
- **用技能才过的断言**：技能价值的真正来源。弄清是哪条指令或哪个脚本起了作用
- **同一 eval 时过时不过（高 stddev）**：要么 eval 对模型随机性敏感，要么技能指令含糊到每次理解都不同。补示例、收紧表述来降低歧义
- **时间/token 离群点**：某个 eval 比其他慢 3 倍，读它的执行记录找瓶颈

## 人工审查

断言只检查你想得到的。人工审查能发现没预料到的问题——技术上正确但没抓住重点的输出、难以写成通过/失败检查的毛病。逐个用例审查实际输出，记录**可执行的**反馈到 workspace 的 `feedback.json`：

```json
{
  "eval-top-months-chart": "图表缺坐标轴标签，且月份按字母序而不是时间序排列",
  "eval-clean-missing-emails": ""
}
```

"月份按字母序而非时间序"可执行；"看起来不好"不可执行。空反馈表示该用例通过审查。迭代时优先改有具体抱怨的用例。

## 迭代

评分和审查后，你手上有三个信号源：

- **失败断言** — 指向具体缺口：缺失的步骤、不清楚的指令、没覆盖的情形
- **人工反馈** — 指向方向性问题：方法错了、结构差、技术上正确但没用
- **执行记录** — 揭示为什么出错：指令被忽略可能是太含糊；无效步骤太多可能该删

把三者连同当前 SKILL.md 交给 LLM 提改进，并给出这些约束：

- **从反馈泛化** — 技能会用于大量不同的 prompt，修复要解决根本问题，不是给个别测试用例打补丁
- **保持精简** — 少而好的指令胜过穷举规则。执行记录显示的无用工作直接删；加了规则通过率不动，可能过度约束了，试着删减看结果是否持平或更好
- **解释原因** — "做 X，因为 Y 容易导致 Z"比"永远做 X，永远别做 Y"更可靠，模型理解目的后遵循得更稳
- **合并重复工作** — 每次运行都独立写出一个相似的辅助脚本，就把脚本固化进技能的 `scripts/`

循环：提改进 → 审查并应用 → 新 `iteration-<N+1>/` 重跑全部用例 → 评分汇总 → 人工审查 → 重复。

反馈持续为空、或迭代间不再有实质性提升，就停止。
