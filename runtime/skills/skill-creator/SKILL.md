# 技能铸造师（Skill Creator）

创建、审查和改进 MindX 技能。

## 何时使用

- 用户要求创建新技能、优化或重构现有技能
- 用户要求审查技能质量、排查技能缺陷或做技能体检
- 需要判断某个经验是否值得沉淀为技能
- 为插件补齐技能文档

## 核心原则

### 技能是LLM专用文档

技能是给 LLM 执行的专用文档，不是给用户看的，绝对不能引入日常笔记性的内容，要防止多余的噪声分散 LLM 的注意力。

### 技能三层结构（每个 skill 的完整形态）

| 层            | 定位                 | 职责                                                              |
| ------------- | -------------------- | ----------------------------------------------------------------- |
| `SKILL.md`    | 工作指导             | 决策路由：何时用、怎么判断、按什么顺序推进、走到哪步读哪个文件    |
| `references/` | 参考资料，作业指导书 | 具体怎么做：领域权威资料全文收纳（含出处 frontmatter 与行号索引） |
| `scripts/`    | 算力简化             | 高频重复、长时费算力、含技术含量的专业操作三类优先脚本化          |

**正文自足率**：SKILL.md 一次加载要能解决 60%-80% 的常规任务——高频必用的模板、判定、格式规范直接写在正文；只有低频细化内容才路由到 references/scripts。判定法：写完技能模拟 LLM 执行一次常规任务，数它要额外 Read 几次——常规任务超过 1 次额外读取，就是把高频内容错误下沉了。某一步需要外搜或凭记忆猜，就是三层没装完。

**行数上限**：正文上限 300 行。上下界一起构成体量控制：自足率 60-80% 防过分简约，300 行防过度膨胀。超行时先压低频内容，不动高频模板。

### 正文骨架三段

SKILL.md 正文按三段组织：**何时使用 / 核心决策路由 / 纪律边界**。决策路由是骨架核心——把执行者要做的判断写成 if/else 式路由；每条路由必须落到具体动作（命令、文件、判定标准），禁止只给方向。

### 六条写作纪律

1. **从真实专业知识出发**：优先从实际对话中的纠正、输入输出格式、项目约定提取；泛泛的最佳实践文章是最差素材。
2. **补充智能体缺少的，省略它已知的**：每块内容问「没有这条，执行者会在这里出错吗」，不会就删。
3. **参考资料自包含**：权威资料预置进 `references/`，本地优先、外搜兜底（活口不是禁令）；引来源给具体 URL，核验后收纳。
4. **先给选项再问问题**：执行者面对开放输入时给 2-4 个贴近上下文的候选选项，不扔填表题（句式见下方速查）。
5. **脚本化判定**：有程序能确定性解决的操作优先写脚本，不留给 LLM 现场推理（要点见下方速查）。
6. **校准控制程度**：脆弱操作给刚性指令（精确命令+禁止修改），灵活任务给目标描述；提供默认方案而非选项菜单。

## 创建技能速查（常规任务在此解决，勿再读文件）

### SKILL.md frontmatter 模板（每次创建必用）

```yaml
---
name: <kebab-case 技能名，与目录同名>
description: <「何时使用」+ 触发词，中文，见下方好坏对照>
metadata:
  name_zh: <中文名>
  version: 1.0.0
  author: Ray
---
```

description 好坏对照：

```yaml
# 差：功能介绍体，不含触发场景
description: 一个用于管理技能的强大工具。

# 好：何时使用 + 触发词列举
description: 管理 MindX 技能。当用户要「列出技能、安装技能、
  删除技能、同步技能库」时使用；提到技能仓库时主动使用。
```

### references frontmatter 规范（每次建参考文件必用）

```yaml
---
updated: YYYY-MM-DD        # 最近一次核验/更新日期，必填
source: <官方文档 URL>      # 有外部出处才填；自产文档不写
scope: <版本/平台限定>      # 版本敏感的资料必须填，其余可选
---
```

正文 ≥300 行的 references 必须带「## 目录」行号索引，用 `scripts/gen_reference_toc.py` 自动生成（幂等，可重跑）。

### 脚本要点（写 scripts/ 时必用）

- 三类操作优先脚本化：高频重复、长时费算力、含技术含量的专业操作
- 禁止交互式提示（智能体无 TTY，会挂死）：输入全部走命令行参数/环境变量/stdin，缺参数时输出带用法的清晰报错
- `--help` 写全：用法、选项、示例——这是智能体了解接口的主要途径
- 结构化输出走 stdout（JSON 优先），进度/警告走 stderr；退出码区分失败类型

### 失败模式写法示例（纪律边界或决策路由中编码）

```
## 失败模式（现象→原因→动作）

- 现象：搜索返回空。原因：glob 层级不够或同义词没换。
  动作：换写法再搜；仍空则答「没查到」，禁止升级为「不存在」。
```

### 选项先行句式（主题不明时必用）

```
用户未指明关键输入时，禁止自行猜测。先给 2-4 个贴近当前上下文的
候选选项让用户选，每项附「其他（自由输入）」兜底。
```

## 创建工作流

### 步骤 1：理解与信息收集

先回答三个问题（答案写进设计稿，不写进技能正文）：

- 这个技能解决什么问题？（一句话）
- 谁在什么场景触发它？（列出触发词——将来直接进 description）
- 执行者做完的标志是什么？（验收标准，步骤 4 验证时对照）

素材收集两条路：

- **从实际操作中提取**：完成任务的真实对话里的有效步骤、你做过的纠正（「用库 X 不用 Y」「要检查边界 Z」）、输入输出格式、项目特定约定。
- **从现有项目产物综合**：内部文档、操作手册、API 规范、schema、代码审查评论、修复补丁、真实失败案例。项目特定材料永远优于通用参考资料。

缺领域上下文时先问用户要，禁止纯 LLM 通用知识硬编。

### 步骤 2：设计（三层分配 + 查重）

逐条内容问它回答什么问题，按问句分配去处：

| 内容回答的问题       | 去处                        |
| -------------------- | --------------------------- |
| 「接下来该做什么」   | SKILL.md 正文（决策路由）   |
| 「这一步具体怎么做」 | `references/`（作业指导书） |
| 「重活能否程序化」   | `scripts/`（算力简化）      |

- 查重：`mindx skill list` 找同类技能，能进化既有技能就不新建。
- 画决策路由清单：执行者的每个分支——正常路径、失败路径、输入不全路径——各写一条路由。

### 步骤 3：创建

- frontmatter 按「创建技能速查」模板写；description 用触发场景 + 触发词，禁功能介绍体。
- 正文按骨架三段写：何时使用 = 触发场景清单；核心决策路由 = if/else 式、每条落到具体动作；纪律边界 = 禁令 + 失败模式三段式。
- 权威资料全文进 references（frontmatter 规范见速查）；重活按脚本要点进 scripts。

### 步骤 4：验证循环

```bash
mindx skill validate --path <技能目录>
```

确定性自查唯一实现，禁止心算代替；发现问题修复后重跑直到全绿。validate 通过后人工对照六项自检：

1. 触发准确性：description 含触发场景与触发词
2. 自包含：不依赖外部记忆或笔记文件
3. 具体性：无软化词，脆弱操作有精确指令
4. 失败模式：现象→原因→动作三段式
5. 体积：正文 ≤300 行
6. 正文自足率：模拟执行一次常规任务，额外 Read ≤1 次

### 步骤 5：落位验证

```bash
mindx skill add <技能目录绝对路径> && mindx skill list
```

`skill add` 会把技能装入受管注册表并自动重载（`reload` 子命令不存在，注册只能走 add）。

确认注册后，用一条真实触发语句验证 description 生效（技能确实被唤起）。

### 步骤 6：进化记录

按 notes-convention.md 在技能 `notes/` 追加履历一条：文件名 `YYYY-MM-DD-<skill>-规则{修正|增强}-<主题>.md`，内容含触发原因、修正内容、效果；**档案必须带 frontmatter**（version / pub_date / sha 防篡改签名 / modifier / modifier_id——身份经 CLI 实查社区账号，禁止编造，规范详见 notes-convention.md）。

## 优化与评估

- **触发不准**（该触发不触发/不该触发乱触发）：按 optimizing-descriptions.md 改 description，用真实查询样本测试。
- **输出质量不稳**：按 evaluating-skills.md 构建评测（evals/trigger_queries.json + 评分清单），跑真实样本对照。
- **进化修复**：缺陷修复后按 notes-convention.md 留痕，版本号递增。

## 审查已有技能

按四步走：

**A. 全量清点**：`mindx skill list` + 目录扫描，建立技能清单（名称、版本、行数、三层完整度）。

**B. 机器校验**：逐个跑 `mindx skill validate --path`，全部结果分三类归档——硬错误（error 级全修）、依赖问题（引用断链用 `mindx/runtime/skills/retrospect/scripts/refcheck.py` 核查）、质量问题（size 超限、软化词、frontmatter 缺失逐条列）。**软化词告警逐条人工核对再动作**：词面匹配有误报（名词`建议`≠软化句式），误报判定的依据是语义而非词形。

**C. 正文人工对照**：三层完整度、决策路由完整性（正常/失败/输入不全三路径都有路由）、references 关联（正文提到的文件实存）、scripts 路由（正文提到的脚本实存且可执行）、正文自足率（高频内容是否被错误下沉）。

**D. 报告分级输出**：硬错误/依赖问题/质量问题的分级清单，每条给出依据和修改方案；机械低风险项（如补 frontmatter）用户确认后直接修复，结构性手术（拆分下沉）需用户拍板。「同一规则被连续忽略时硬化」只适用于真规则被真忽略，不适用于词面误报。

## 文件结构约定

```
<skill-name>/
├── SKILL.md              # 必需：决策路由正文（≤300 行，自足率 60-80%）
├── references/           # 作业指导书：权威资料全文收纳
│   └── *.md              # frontmatter(source+updated)，≥300 行带行号目录
├── scripts/              # 算力简化：确定性操作脚本
│   └── *.{py,sh}         # 自包含依赖声明，智能体友好接口
├── evals/                # 可选：触发测试与质量评测
│   └── trigger_queries.json
└── notes/                # 进化履历：每次规则修正/增强一条
    └── YYYY-MM-DD-<skill>-规则{修正|增强}-<主题>.md
```

## 技能位置与进化

- 项目技能落位 `.agents/skills/<name>/`，全局技能落位 mindx 仓 `runtime/skills/<name>/`
- 技能进化走螺旋：使用中发现缺陷 → notes 记录 → 修复 → 版本递增 → 履历留痕
- 已被技能吸收的 memory 条目移入 `.agents/memory/.archive/`，notes 素材删除

## 写作风格

- 祈使句 + 第二人称，精确指令；禁软化词（`建议`/`考虑`/`适当`/`酌情`），代之以明确动作与判定标准
- 代码示例直接可执行；路径用相对技能根目录
- 中文正文，技术名词保留英文

## 编写反模式

| 反模式                     | 症状                                                                | 防线                                                             |
| -------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **过分简约**               | 为行数好看把高频模板与判定全下沉，写一份基本技能要多次 Read         | 正文自足率 60-80%，常规任务额外 Read ≤1 次                       |
| **过度膨胀**               | 操作细节、参考资料全文堆进正文                                      | ≤300 行上限，低频细化内容下沉 references                         |
| **功能介绍式 description** | 写「是什么」不写「何时用、何时触发」                                | description 写触发场景 + 触发词                                  |
| **软化词**                 | `建议`/`考虑`/`适当`/`酌情` 代替明确动作                            | 明确动作 + 判定标准                                              |
| **无失败分支**             | 只写正常路径，出错后执行者自行发挥                                  | 失败模式按「现象→原因→动作」三段式编码                           |
| **写死环境专属路径**       | 全局技能正文硬编码只有项目拥有人才有的仓/目录，其他用户环境执行即死 | 专属资源走环境探测分支：存在则用、不存在问用户、确认无则如实停止 |
| **凭印象收纳**             | 引用外部规范/CLI 用法未核验                                         | 核验后收纳，写明 source                                          |

## 纪律与边界

- **禁止覆盖未读文件**：改任何 SKILL.md 前必须先 Read 全文（军规）
- **禁止心算校验**：质量判定以 `mindx skill validate` 输出为准，人工只做语义核对
- **禁止错误下沉**：高频必用内容必须留正文（自足率 60-80%），只有低频细化内容才路由 references；发现 >300 行先压低频内容，不动高频模板
- **禁止重复造轮子**：创建前先查同类技能（`mindx skill list`），能进化就不新建
- **参考资料核验后收纳**：引用外部规范/CLI 用法前必须核验真实性，禁止凭印象写
- **进化留痕**：每次规则修正/增强必须追加 notes 履历（格式见 notes-convention.md）
