# 技能创建器

创建、审查和改进 MindX 技能。

## 何时使用



* 用户说 "我需要一个能处理 X 的技能"、"帮我写个技能"
* 工作流需要可复用的指令，且能附加到多个智能体
* 用户说 "检查一下这个技能"、"审查这份 SKILL.md"、"这个技能为什么没触发 / 输出不对"
* 现有技能触发不准、边界不清、需要优化
**已有合适技能时不要使用。**

## 核心原则

### 技能三层结构（核心心智模型）

一个完整技能由三层构成，各司其职，缺一层都是不完整技能：

| 层            | 定位           | 职责                                                                                                                                                                                                                                                                                                                                                 | 回答的问题            |
| ------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| `SKILL.md`    | **工作指导**   | 决策路由：何时用、怎么判断、按什么顺序推进、走到哪一步读哪个文件（渐进式披露）                                                                                                                                                                                                                                                                       | "接下来该做什么"      |
| `references/` | **作业指导书** | 具体怎么做：全量收集该领域权威资料（官方规范/API/模板/最佳实践，全文收纳+中文翻译+frontmatter 更新日期+行号索引）                                                                                                                                                                                                                                    | "这一步具体怎么做"    |
| `scripts/`    | **算力简化**   | 四类操作优先脚本化：①高频重复操作 ②长时费算力的复杂操作 ③**含技术含量的专业操作**——一个程序能解决非常复杂的专业问题（如格式解析、算法计算、协议转换）时，优先写 script 而不是让 LLM 现场推理 ④**确定性操作**——需要可重复执行、不容执行抖动、结果必须可信可断言的操作（检验、盘点、处置、发布、部署、签名、带鉴权的调用），即使单次很简单也必须脚本化 | "哪些重活不用 LLM 干" |

三层构成完备编写规范：正文只写决策与路由，不写操作细节；操作细节全部进 `references/`（全量域索引——运行时的决策路径被锁定在最短路径上，本地即查，不引导外搜）；高频重活、专业重活与确定性操作进 `scripts/`（判断标准：有程序能确定性解决的操作优先脚本；结果需要可信断言的操作必须脚本——**Agent 默认不会主动考虑写 scripts，创建时必须按下述工作流的动作面判定强制执行**，不留给 LLM 现场发挥）。写技能时先想清楚三层各自装什么，再动笔。

### 先给选项，再问问题

收集需求时，不要直接问开放式问题：



1. **用户没说细节时**（如 "帮我创建个技能"），从当前对话中提取经验和模式作为技能主题。直接跳到[信息收集](#信息收集)。

2. **理解意图**，给出 2-4 个具体选项

3. **让用户选择或调整**

4. 所有选项都不合适时，再问开放式问题

**示例**：用户说 "我需要一个处理数据库的技能"：

> 我可以创建一个数据库技能。哪种类型最合适？
> **SQL 审查器**
>
>  — 检查查询正确性、性能和注入风险
> **模式设计器**
>
>  — 设计表结构、索引和迁移方案
> **查询优化器**
>
>  — 为慢查询建议索引和重写方案
> **其他**
>
>  — 描述你的具体需求

### 基于真实专业知识

好技能来自领域经验，不是通用建议。源材料可以是：



* **当前对话** — 用户的纠正、有效的步骤、智能体之前不知道的约定

* **项目文档** — 内部文档、API 规范、代码审查评论、操作手册、事故报告

* **领域知识** — 常见模式、失败模式、边界情况

用户提供的上下文不够时，主动要求提供相关源材料。技能的质量取决于构建它时所依据的上下文。

### 精简上下文

完整的 SKILL.md 会占用智能体的上下文窗口，每个 token 都会分散模型的注意力。



* **只补智能体不知道的，省略它已经懂的** — 不用解释什么是 PDF

* **重过程，轻声明** — 教*怎么做*，而非*做什么*

* **给默认方案，别列一堆选项** — 选定一种方法，简要提及替代方案即可

* **越容易出错的操作，规定越要具体** — 脆弱操作写详细，创造性任务留空间

### 参考资料自包含（references 收纳）

专业技能的参考资料与专业规范必须预置进 `references/`，运行默认读本地，禁止让智能体一上来就去外搜——技能不自带资料，LLM 要么凭记忆猜（写错），要么现场去搜（浪费运行次数与时间，搜回来的资料还可能与本技能方法论不匹配）。要点：

* **资料全部收纳** — 专业规范、API 手册、标准、模板、检查单、权威数据，能预置的全部放 `references/`，正文只写"何时加载哪个文件"
* **本地优先，外搜兜底** — 需要外部事实时先给 `{base_dir}/references/` 内的本地文件路径；外搜是"活口"不是禁令——仅当本地参考资料不足或过时（资料缺失、版本失效、规范更新）时才允许外搜，并在产出中标注补到了什么
* **引来源，不引搜索** — 确实需要外部链接时给出具体 URL 与用途，不写"自己查一下"
* **核验后收纳** — 引用外部规范/CLI 用法前必须核验真实性，核验结论连同来源 URL 写进 references，禁止凭印象写

## 参考文档索引

深度参考材料在 `references/` 目录，**按需加载，不要一次全读**。用 `{base_dir}` 引用：



| 文档                                    | 何时加载                                                                                                                                              |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `references/schemas.md`                 | 编写或校验 frontmatter 时 — MindX 字段数据模型，`metadata` 扩展键（`requires` / `install` / `name_zh` / `version`）的完整定义、校验规则与正文模板变量 |
| `references/spec.md`                    | 需要 agentskills.io 通用格式规范细节时 — 注意文首的 MindX 差异说明，与 schemas.md 冲突时以 schemas.md 为准                                            |
| `references/best-practices.md`          | 编写或审查技能正文时 — 真实专业知识、上下文精简、指令设计的完整模式                                                                                   |
| `references/optimizing-descriptions.md` | 触发评估不达标、需要系统性优化 description 时 — 触发机制、评估查询设计与优化循环细节                                                                  |
| `references/using-scripts.md`           | 技能需要附带可执行脚本时 — 脚本引用方式与 "为智能体使用设计" 的细节                                                                                   |
| `references/evaluating-skills.md`       | 运行评估或依据评估结果改进技能时 — 测试用例设计、断言好坏标准、评分原则与盲评、benchmark 汇总、人工审查与迭代循环                                     |
| `references/notes-convention.md`        | 对已有技能进化、需要写进化记录时 — 记录模板、字段语义与反模式                                                                                         |

## 信息收集

编写前，先确认以下信息都已明确。如果不确定，提供假设选项让用户确认。

### (a) 技能名称

小写连字符，基于名词，注册表中唯一。如：`git-commit-helper`。

### (b) 触发条件 → `description` 字段

什么情况下激活？哪些用户查询模式表明相关？这决定 LLM 路由。

### (c) 工作范围和边界

技能处理什么？什么超出范围？输出格式是什么？

**产出类技能（产出文档、报告、作品等成规模交付物）还要定产出落点纪律——落点沿用优先，专用目录兜底**：用户工作目录已有目录结构或 AGENTS.md 时，沿用既有规范，禁止无视另立一套；仅当产出内容多、涉及领域广、且工作目录没有统一规范时，技能才定义专用目录结构并要求目录根建 AGENTS.md（写目录地图、当前进度、更新规则）。这是兜底不是先决条件——无条件「必建专用目录」会在已有约定的项目里制造冲突。

### (d) 必需工具 → `allowed-tools` 字段

需要哪些 MindX 工具？保持列表最小化。

### (e) 运行时要求 → `metadata.requires`

是否需要 PATH 上的可执行文件（如 `python3`、`git`）？是否需要环境变量（如 `API_KEY`）？

## 工作流

进入工作流前先 `TaskCreate` 建立任务清单（创建/审查各阶段一项，含每步产出），推进中用 `TaskUpdate` 标记完成状态，中断恢复时用 `TaskList`/`TaskGet` 读取进度，不凭回忆对齐工作点。

### 设计阶段

#### 步骤 1：检查现有技能



```
mindx skill list --json          # 全局库（可加 -f <关键词> 过滤）
mindx skills discovery           # 项目级库
```

检查是否存在同名或领域重叠的技能。存在则通知用户，让他们决定。



```
mindx skill get <proposed-name>
```

#### 步骤 2：确认需求

逐项检查[信息收集](#信息收集)中的所有项目，(a) 到 (e) 全部明确后才能继续。

### 创建阶段

#### 步骤 3：创建技能目录

在项目级技能库中创建目录（落位规则见[技能位置与进化](#技能位置与进化)）：



```
<ProjectDir>/.agents/skills/<skill-name>/
  SKILL.md
```

#### 步骤 4：读取模式参考

读取 `references/schemas.md` 获取完整的 frontmatter 规范。

#### 步骤 5：编写 SKILL.md

**动作面脚本化判定（先于一切正文编写）**：列出技能的全部机器动作，逐项过确定性四问——会被重复执行吗？结果需要 PASS/FAIL 式断言吗？涉及鉴权、签名或协议细节吗？是线上状态变更吗？任一为真必须先写 `scripts/` 再写正文。脚本硬性要求：写操作内建执行后校验（动作后回读线上状态确认生效），检验类输出结构化 PASS/FAIL/SKIP 与有意义退出码，破坏性动作带显式确认阀。SKILL.md 随附**「执行铁律」节**：表格列出每个脚本的用途与关键参数，声明执行一律调脚本、references 文档仅作背景知识、不作为执行时拼命令的来源。

编写技能主体。关键关注点：

`description`**&#x20;字段**（决定技能何时触发）：



* 用祈使句式："当... 时使用此技能"

* 聚焦用户意图，别写实现细节

* 宁可触发积极一些，也别漏掉该触发的场景

* 长度控制在 1024 字符以内

`metadata.requires`：声明需要的二进制文件、环境变量和运行时版本。依赖未满足不阻断装载，但技能运行前的准备流程会卡住 —— 声明要准确，完整定义见 `references/schemas.md`。

**工作流**：带具体、可执行指令的编号步骤。

**注意事项**：这是技能中最有价值的部分。记录智能体在没有提示时容易犯的错误：



```
## 注意事项

- `users` 表使用软删除。查询必须包含 `WHERE deleted_at IS NULL`。
- `/health` 端点即使数据库关闭也返回 200；用 `/ready` 做完整健康检查。
```

测试中发现问题时，把修正方案补充到注意事项里。

**计划 - 验证 - 执行**模式用于破坏性或批量操作：



```
1. 在 `plan.json` 中创建计划
2. 验证：`script/validate.py plan.json`
3. 验证失败则修改并重新验证
4. 执行：`script/apply.py plan.json`
```

**清单**用于多步骤工作流跟踪进度。

**验证循环**："做工作 → 验证 → 修复 → 重新验证 → 继续。"

脚本设计详见[脚本设计指南](#脚本设计指南)。

### 落位与验证阶段

#### 步骤 6：落位与确认

技能目录已在 `<ProjectDir>/.agents/skills/<skill-name>/`，项目级实时读盘无需安装。`mindx skills discovery` 确认可见。

#### 步骤 7：自检验证

`mindx skill validate --path <技能目录>` 支持任意技能目录（含项目级）。对新建技能运行自检；通过后告知用户技能已可在本项目使用，全局可用由用户通过界面安装。

### 优化触发

`description` 字段决定技能是否会被触发，需要系统地优化。

#### 步骤 8a：创建触发评估查询

创建 `evals/trigger_queries.json`，包含约 20 个查询：



```
[
  { "query": "review this SQL query for injection risks", "should_trigger": true },
  { "query": "what's the weather today?", "should_trigger": false }
]
```



* **应触发**：措辞、明确性、详细程度要有变化

* **不应触发**：用近似匹配 — 共享关键词但需要不同技能的提示

* 分为**训练集 (60%)** 和**验证集 (40%)** 防止过拟合

#### 步骤 8b：测试触发率

把技能挂载到智能体上。每个查询运行 3 次，观察是否调用了 `Skill` 工具。应该触发的查询，触发率 >= 0.5 才算通过；不该触发的查询，触发率 < 0.5 才算通过。

#### 步骤 8c：优化



* 应触发失败 → 描述太窄 — 扩大范围

* 不应触发误触发 → 描述太宽 — 增加具体性

* 避免从失败查询添加特定关键词（过拟合）

* 用训练集重新测试，然后检查验证集验证泛化能力

迭代直到训练查询通过或改进停滞（约 5 次迭代）。

### 评估输出质量

详细方法论（断言好坏标准、评分与盲评、benchmark 汇总、人工审查、迭代循环）见 `references/evaluating-skills.md`。主干步骤：



1. **创建测试用例**：在 `evals/evals.json` 写 2-3 个用例，每个含 `prompt`（真实上下文、覆盖边界）、`expected_output`、可选 `files`。第一轮不写断言，看过输出再加。

2. **运行基线对照**：每用例跑两次 —— 用技能与不用技能（或旧版本快照），分别保存到 `iteration-N/eval-ID/{with,without}_skill/`，每次运行记录 `timing.json`（token、耗时）。

3. **评分**：对每条断言判 PASS/FAIL 并附具体证据，写入 `grading.json`。机械检查用脚本，主观判断交给 LLM。比较两个版本时用盲评。

4. **汇总与审查**：计算 `benchmark.json` 的通过率 delta 与 token 开销；人工审查产出 `feedback.json`。删除两种配置都恒过的断言，排查两种配置都恒挂的断言。

通过率提升显著且 token 开销可接受、人工反馈持续为空，才算有价值的技能。

### 迭代

#### 步骤 10：从信号改进

三个信号源：



* **失败的断言** — 具体差距：缺少的步骤、不清晰的指令

* **执行记录** — 事情出错的原因：模糊的指令、不必要的步骤、浪费的工作

* **触发失败** — 错误的查询触发或遗漏

把所有信号连同当前 SKILL.md 一起交给 LLM 来改进：



* 从反馈中提炼通用规律 — 解决根本问题，别只打补丁

* 保持技能精简 — 少而精的指令胜过面面俱到的规则

* 解释原因 — 讲清楚 "为什么" 比死板的规定更有效

* 合并重复工作 — 智能体每次运行都写相同的辅助函数时，把它移到 `scripts/` 里

修改后，重新运行自检验证和相关评估阶段。如果没有更多反馈或改进已经停滞，就停止迭代。

## 审查已有技能

用户要求检查、审查、修正已有技能时走本流程。本技能承载了 SKILL 编写标准的唯一事实，审查就是把标准逐条套用到目标技能上。

### 步骤 A：定位与装载



1. 全局库技能：按[技能位置与进化](#技能位置与进化)先 `mindx skills fetch <name>` 取到项目级副本，所有修改在副本上进行

2. 项目级技能：直接读取 SKILL.md 全文

### 步骤 B：确定性机器校验

跑 `mindx skill validate --path <技能目录>`（唯一实现：skillstore.CheckQuality，输出 JSON 报告，退出码 0 = 通过 / 1 = 发现问题）。覆盖项：



* [ ] frontmatter 解析与字段合规（name 规范、description 长度与触发语义）

* [ ] 软化词扫描（HASP：`建议…`/`可以考虑…`/`根据情况…`/`是可选的`，逐行定位）

* [ ] 体积（正文 >150 行告警）

* [ ] 引文格式（`[ref:ID]` 须 ref\_ 前缀）

* [ ] 正文 .md 链接可达性（含 `{base_dir}` 引用）

frontmatter 的深度字段语义（`requires`/`install`/ 模板变量）仍以 `references/schemas.md` 为准，机器校验之外人工核对。

### 步骤 C：正文质量审查

对照核心原则与反模式清单：



* [ ] 上下文精简：只补智能体不知道的，没有解释智能体已懂的概念

* [ ] 有 "注意事项" 且记录了真实的易错点，而非正确的废话

* [ ] 职责单一、边界明确，没有 "一个技能想做所有事" 的迹象

* [ ] `references/` 下每个文档都在正文中有关联（何时加载）

* [ ] **references 新鲜度**：每份 reference 是否带核验日期与适用范围；来源 URL 是否仍可达；引用的版本/参数/规范是否已更新（对照官方变更记录）。**顺序链：日期超期只是触发复核的软信号，必须对照官方源确认内容陈旧才预警/更新，未确认陈旧不动作**——领域知识持续变化，陈旧 references 会让技能持续腐烂，LLM 默认读本地反而更难暴露过时

* [ ] 破坏性或批量操作有计划 - 验证 - 执行模式或 `--dry-run`

* [ ] 动作面脚本化：检验、盘点、处置、发布等确定性操作已固化进 `scripts/`（存在"LLM 临场拼命令"即质量缺陷——Agent 默认不会主动写 scripts）；脚本内建执行后校验（写操作回读、检验有断言与退出码），破坏性动作有确认阀

### 步骤 C2：运行效果核查（决策量表，可用时）

修订既有技能时，在正文审查之后跑一次运行期数据，与文本审查结论互证：



```
mindx metric report --skill <技能名> --window-days 30 --json
```



* **无数据**（新技能、窗口内零调用或 daemon 未开计量）：静默跳过本步，不阻塞审查

* **有数据**：看该技能下钻行的聚合评价（p 因子赞踩占比）与返工标记 —— 这是它在真实会话里的表现，比盲评更接近实际效果

* **互证规则**：运行差但文本审查无问题 → 优先怀疑触发面（描述与实际用途错位）与运行环境，而非指令措辞；运行好但文本有明显问题 → 该问题降为可选改进项，不为改而改。量表是信号不是证明，结论仍以步骤 D 的综合判断为准

### 步骤 D：输出报告并修复

按严重程度分级输出：**硬错误**（装载失败）→ **依赖问题**（运行前准备会卡）→ **质量问题**（触发不准 / 输出差）。每条给出依据和修改建议，用户确认后直接修复。



* 触发问题转入[优化触发](#优化触发)

* 输出质量问题转入[评估输出质量](#评估输出质量)

* 修复后重新运行步骤 B 自检确认

## 技能位置与进化



* 本技能创建的技能一律写 `<ProjectDir>/.agents/skills/`，禁止写全局库 `~/.mindx/skills`

* 优化全局库技能：先 `mindx skills fetch <name>` 取到项目级再修改，禁止直接读写全局库

* 进化的触发来源有两类：对话回观发现的技能问题，与复盘产出的技能修订提议（`.agents/notes/` 中缺口类记录）—— 两者都按上述流程修正并追加履历

## 脚本设计指南

技能可以在 `scripts/` 目录中放置脚本，供智能体在执行时调用。

### 一次性命令

当现有包就能完成所需工作时，直接在 SKILL.md 中引用即可：



```
npx eslint@9 --fix .
uvx ruff@0.8.0 check .
go run golang.org/x/tools/cmd/goimports@v0.28.0 .
```

固定版本号。注明前提条件（Node.js 18+、Python 3.10+）。

### 自包含脚本

脚本可以直接在文件内声明依赖，无需单独的清单文件：

**Python (PEP 723)** — 用 `uv run` 运行：



```
# /// script
# dependencies = ["beautifulsoup4>=4.12,<5"]
# ///
from bs4 import BeautifulSoup
```

**Deno** — `npm:` 导入说明符：



```
#!/usr/bin/env -S deno run
import * as cheerio from "npm:cheerio@1.0.0";
```

**Bun** — 导入路径中带版本：



```
#!/usr/bin/env bun
import * as cheerio from "cheerio@1.0.0";
```

### 为智能体使用设计



* **不要交互式提示** — 智能体无法使用 TTY，所有输入通过命令行参数、环境变量或标准输入传入

* `--help`**&#x20;是主要接口** — 写清描述、参数说明和示例

* **结构化输出** — 优先输出 JSON；数据走标准输出，诊断信息走标准错误

* **退出码要有意义** — 不同失败类型用不同退出码

* **尽量幂等** — "不存在则创建" 比 "重复执行就报错" 更安全

* **支持试运行** — 破坏性操作提供 `--dry-run` 选项

* **输出大小可预期** — 大输出做截断或提供 `--offset` 参数

## 写作风格



* **直接下达指令**："做 X"、"检查 Y"、"返回 Z"

* **具体胜过模糊**："列出文件" 比 "处理文件" 更清晰

* **示例驱动**：给出输入 / 输出格式示例

* **由主到次**：最重要的指令放前面，细节放后面

* **输出模板** — 提供 markdown 或 JSON 模板。智能体对具体结构的模式匹配能力远强于理解大段文字

* **清单** — 用 `- [ ]` 跟踪进度

* **验证循环** — 执行 → 验证 → 修复 → 重新验证

* **注意事项** — 记录智能体没有提示时容易犯的错误

* **渐进式披露** — 深度参考材料（专业规范、API 手册、模板、检查单）一律预置到 `references/` 目录的单独文件中，告诉智能体*什么时候*去加载；默认读本地，本地参考资料不足或过时才允许外搜（见「参考资料自包含」原则）

## 反模式



* 通用名称（`helper`、`utils`、`assistant`）

* 描述写得像营销文案，而不是触发路由信号

* 一个技能想做所有事 — 应该拆分成多个

* 缺少边界 — 导致错误触发和越界操作

* 在 `allowed-tools` 中声明了技能根本不会用到的工具

* 过度规定 — 灵活任务应留给智能体自行判断

* 没有领域特定上下文的泛泛技能

* 列了一堆平级选项却不给默认值

* 描述针对特定测试查询过拟合，缺乏泛化能力
* 无条件要求专用产出目录 — 用户工作目录可能已有结构与 AGENTS.md；落点沿用优先，产出多、领域广、无统一规范时才建专用目录与 AGENTS.md 兜底
* 确定性操作（检验、盘点、处置、发布、部署、签名、带鉴权调用）只写文档示例让 LLM 临场拼命令 — 结果每次执行都可能抖动；Agent 默认不会主动写 scripts，必须在创建工作流强制判定
* 脚本只执行不校验 — 写操作无回读验证、检验无断言与退出码，留下"命令成功≠生效"的悬案

## 重要说明



* **除非另有说明，所有字段都是给 LLM 看的。** 写得清楚明白。

* **技能是操作指令**，不是功能开关。

* **少即是多。** 专注的技能胜过包罗万象的技能。

* **问开放式问题前先给选项** — 加速需求收集。

* **宣布完成前必须测试。** 验证 + 触发测试 + 至少一次手动评估。

* **触发优化 ≠ 输出评估。** 技能可能正确触发了但输出很烂，也可能输出不错但根本没被触发。两者都要测。

* **从小处开始。** 第一轮评估用 2-3 个测试用例，后续再逐步扩展。

* **每次评估用干净的上下文** — 不要残留上一次运行的状态。
